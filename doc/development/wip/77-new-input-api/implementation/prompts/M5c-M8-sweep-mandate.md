## What this is

The remaining roadmap **M5c → M7 → M8** runs as milestone sessions governed the way brainlab
governs its sessions: serial handover prompts, a running track, human gates, wrap-and-handover.
One milestone ≈ one session. **The human reviews at EVERY milestone boundary — unconditional**;
the next milestone starts only after explicit approval. **M5b no longer exists** as a deferred
item — its content is inside M5c.

**A milestone is not one prompt — it is carved into multiple independently-gated chunks.** The
milestone boundary is the *coarse* gate; inside it the sweeper splits the slice into the smallest
independently-valuable-and-reviewable chunks and holds a human go/no-go **between every chunk**
(`agents/sweep.md` rules 1–3). This matters most for **M5c** — the widest slice in the plan (≈ 2× M4
by PERT); running it as a single prompt would defeat the reviewed-in-between discipline. Carve it.

## Guardrails (new — each one an anti-body to the M4 failure mode)

1. **No in-slice design rulings, ever.** A corpus contradiction, spec gap, or platform
   surprise = **stop + one gate round with the human**. An outcome ledger containing a
   "design rulings made in-slice" section is itself a gate failure.
2. **Citation-or-stop outcome ledgers.** Every non-obvious decision bullet carries one corpus
   ref (`spec.md §N`, `ratified-model.md`, `doc A §N`, ruling id, remark id). Uncitable ⇒ it
   is a judgment call ⇒ stop. Review must be ref-checking, never archaeology.
3. **Surprise-first reporting.** Outcome ledgers open with a mandatory **"what will surprise
   the architect"** section — deviations, reconciliations, new names, new public surface —
   before the file list. Prose budget for the rest.
4. **In-code human `REVIEW` comments are design inputs**, not test-triage items: reconcile
   each against the corpus; a contradiction escalates. A `>> REVIEW` marker is removed only
   by the slice that resolves it, with a ledger line citing the resolving contract point.
5. **No new public surface without a named consumer** in the slice. Test-only ⇒ test-scoped.
6. **Pinned remarks are checklist items.** The M4-pushback SCOPE remarks and the ~18 QUALITY
   rows are pinned in `spec/M5c-dispatch-chain.md`; each gets an explicit disposition
   (`fixed` / `dissolved-by-rework` / `note-only`, with remark id) in the outcome ledger —
   asserted, never re-discovered.
7. **Nested-checkout discipline (Gate-3, 2026-07-06).** `src/examples/balloons/`,
   `src/examples/keyboard/`, `src/examples/maze/` are **copied-in checkouts** with their own
   nested `.git`, untracked by this repo. **Never commit inside them; never touch their
   `.git`.** Migrations there (maze in M5c, balloons in M8) are delivered as **uncommitted
   working-tree changes**, listed file-by-file in the outcome ledger — the human carries the
   patch upstream. (`keyboard` is pure-native: unaffected, nothing to do.) The commit-locally
   authorisation in this mandate covers **this repo only**.

## Roles, topology, cycle (changed session35 — see execution model above)

**Three roles, one image, one escalation plane.** All three run **inside M0** (repo root = cwd):
- **PM / opus-sweeper** (`agents/sweep.md`, Opus): carves the milestone spec into small
  independently-reviewable chunks, writes each commission to disk, spawns the two sub-agents, holds
  the human gate between chunks. Makes **no design rulings** — those escalate.
- **Implementor** (`agents/dev.md`, Sonnet): one cold run per chunk — test-first, implement, commit
  locally, record the outcome ledger. Also the mechanical grind (running `busted`, transcribing the
  ACs into red acceptance tests; cheaper-model rule `design/agents/process.md` §9.2).
- **Reviewer** (`agents/review.md`, Opus): reviews each finished chunk (diff + ledger) against its
  spec + the rules; verdict only, never rewrites feature code.

**Budget discipline:** pick the smallest model that does the mechanical job; don't churn usage limits.

The **design/escalation plane is a separate brainlab architect session** — it owns the milestone
specs (functional slices) and takes escalations (spec gap, corpus contradiction, any in-slice design
decision). It does **not** drive the sweep; the sweeper drives the sweep and reaches up only when a
question stops being a scheduling call and becomes a design call.

- **Milestone artifacts:** commission prompts in `implementation/prompts/MN….md` (tangible, per
  chunk — never inlined into a sub-agent's context), outcome ledgers in
  `implementation/outcomes/MN….md`, reviews in `implementation/reviews/`.
- **Sweep handover** is the **in-image session lineage** `implementation/sessions/sessionNN/`
  (bind-mounted from the brainlab `…/77-new-input-api/SWEEP/` dir — see
  `implementation/docker/compose.yml`): running track + successor prompt, as before. This is the
  sweeper's own lineage, distinct from the architect session that authors specs and fields escalations.
- **Cycle:** boot → re-entrance guardrail (track/report presence) → track worthy items
  (`[project]`/`[behavioural]`, behavioural stays raw) → do the task, **iterate to explicit
  approval** → wrap (report, successor prompt, repoint CURRENT PROMPT, end session).
- **Milestone loop:** orient (roadmap entry + slice spec + doc A + carried rulings) → author
  the implementation prompt (7-section template, `implementation/README.md`), **present it
  for approval before executing** → execute (test-first: red suite precedes implementation)
  → record the outcome ledger (guardrails 2–3 shape) → hold the gate → on approval, commit
  locally (Conventional Commits, no push; independently revertible commit set) → wrap.
  Mid-milestone stops: scope ambiguity, spec gap, irreversible choice, suite won't converge —
  decided **with the human**, never papered over.

## The `design/` rule

Frozen `design/spec/*.md` slices are never edited. You may extend `design/` (adjacent `MN-NN`
slice, spec-gap clarification) **only with the human's prior approval obtained at a stop**.
Never retroactively rewrite design to match what you built.

## Human reversal is always in-bounds (session35)

**Decisions are revertible.** The human may reopen ANY prior ruling — a closed gate, a frozen
slice, an already-landed milestone — when implementation surfaces a hidden problem he could not
see beforehand (humans are good at spotting hidden problems, but not always before the code
exists). A reversal triggers a **gate round** (+ the E11 re-estimate / adjacent-slice machinery
if the milestone set moves), never an "it's frozen" refusal. **Freezing exists to stop *agent*
derivation-drift, not to bar the *human* from changing course.** This is exactly why
report-don't-fix + surprise-first reporting matter: surface the tension early and cheaply so a
late reversal costs a gate round, not a rebuild. (The E29 re-derivation itself was one such
reversal — see `reviews/m4-architect-pushback.md`.)
