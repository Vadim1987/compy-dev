## The two filters (non-negotiable — this is the whole point)

The drift happened because reverse-engineered behaviour was frozen as `preserve` without being subtracted
against what the redesign is *authorized to change*. Apply **both** filters to every kept (PRESERVE) row:

1. **Subtract documented change-intents.** A behaviour the design is authorized to change is **not** a
   regression contract, no matter that the code does it today. The keyboard overlay gate (`if
   get_user_input() then …`) that M4 **deletes**, the widget-presence routing it implements, the
   un-gated pointer "BOTH" — these are change-intents' targets. They must **not** appear as PRESERVE.
   Source of change-intents = the **design layer** (`design.md`, esp. §2 routing unification + §5
   enter/escape + §6 legacy removal; `spec/M4.md`, `M5.md`/`M5-01-split.md`; `decisions.md`). Cross-check
   every PRESERVE row against it: *where is the authorization to change this?* If there is one, it is not
   PRESERVE.
2. **State each kept behaviour at intent / surface altitude, never mechanism.** Filter 1 alone
   over-freezes accidents (e.g. pointer-BOTH — no change-intent named pointer routing, yet it must
   change). Stating the behaviour at intent altitude ("the active mode owns input exclusively") makes the
   accident visibly not-a-requirement; at mechanism altitude ("the mouse path reaches both") it hides.
   Every PRESERVE assertion is an **observable outcome / public-callback receipt**, phrased as a contract
   on `route` / `sink` / `widget`, never a method-name spy, never `love.state.user_input`/`.C` as
   behaviour, never overlay-gate vocabulary.

A row that survives both filters is a regression contract. A row that fails filter 1 is acceptance
(forward `pending`) or deletion. A row that needs mechanism wording to state is a MECHANISM-GUARD (label
it honestly) or it does not belong.
