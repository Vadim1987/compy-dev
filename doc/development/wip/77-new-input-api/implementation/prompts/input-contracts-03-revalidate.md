## Why this exists (the governing premise — read carefully)

The compy input architecture was built ad-hoc, with **no up-front design doc**, so **the current
implementation is the canonical specification** of the framework's input behaviour. Feature #77 will
**rewrite the routing** (overlay-gate removal, a new `ProjectInputController`, slot ownership/restoration,
three-level dispatch, framework submit/cancel chains) across milestones **M4 → M8**. The contracts note
exists so we can claim the rewrite preserves the framework. **Two ways that note can be wrong, and you hunt
both:**

1. **It mis-distils the implementation** — a contract that the code does not actually guarantee, a real
   guarantee dropped, a citation that does not hold, an outcome/mechanism confusion.
2. **It pins the wrong things as "preserve-forever"** — a behaviour the feature design *intends to change*
   stated as a `[stable-now]` contract to keep (a bug/limitation frozen as a guarantee), **or** conversely
   a genuine guarantee the planned design would silently **break**. This is the human's primary concern:
   *we made implementation decisions for the desired features — do they still hold against the now-formalized
   contracts?*

A contract note that survives both checks is trustworthy enough to (a) promote to `internals/` and (b) drive
the `M4-0-02` contract-level test rewrite. One that does not gets corrected first.

For each stable-now contract, answer: **does the planned rewrite preserve it, change it, or break it?**
