## What this is

The remaining roadmap **M4 → M5a → M6 → M7 → M8** (**M5b stays deferred** — out of scope) runs as a
series of **milestone sessions**, governed exactly the way brainlab governs its sessions: serial
handover prompts, a running track, human gates, wrap-and-handover. One milestone ≈ one session.

**The human reviews at EVERY milestone boundary. That stop is unconditional** — a milestone is done
only when the human explicitly approves it, and the next milestone starts only after that approval.
Additionally, **stop mid-milestone whenever a genuine judgment call surfaces**: scope ambiguity, a
design question the frozen spec doesn't answer, an irreversible architecture choice, a suite that
won't converge green after a reasonable recorded attempt, or the escalation condition
`implementation/README.md` already names (*"if a milestone proves cognition-heavy or human-driven —
design churn, real judgment calls — e.g. the integration-heavy M4 gate removal or M6 boundary model,
do not force it through the black box"* — M4 and M6 are explicitly flagged; treat that as a live
check on those two). Contradictions and under-specifications are decided **with the human**, never
papered over.

## Roles

You hold both planes this feature has so far kept separate: **orchestration** (author/adjust
prompts, exercise spec-fidelity judgment, ingest results, decide next move with the human) and
**execution** (implement, test, commit). Delegate mechanical grind to **Sonnet subagents** —
implementation legwork, running `busted`, transcribing a fixed spec into red acceptance tests (the
"cheaper-model rule", `design/agents/process.md` §9.2). Keep judgment, scope calls, and everything
gate-related to yourself.

## The serial-session cycle (mirrors brainlab)

1. **Boot** the prompt named by CURRENT PROMPT in `agents/sweep.md`. It is **immutable** — never
   edit a booted prompt or any predecessor; mid-session instructions go to the running `track.md`.
2. **Re-entrance guardrail** — read boot state from which artifacts exist in the session dir:
   - neither `track.md` nor `report.md` → **fresh start**: begin the task, open the track;
   - `track.md`, no `report.md` → **interrupted before wrap**: absorb the track, reconstruct where
     it stopped, tell the human what's outstanding, ask resume / redo / redirect — do **not**
     silently restart;
   - `report.md` present → **likely wrapped**: confirm via expected artifacts; if complete, don't
     redo — ask whether continuation or a new prompt is intended.
   When unsure, ask.
3. **Track** (`sessionNN/track.md`) — trigger = "worthy", re-checked every turn: if something
   important accumulated — **project** (fact, decision, instruction, pivot) or **behavioural** (a
   notable move in how the human thinks/frames/doubts/decides) — append a short, telegraphic,
   loosely-anchored note tagged `[project]` / `[behavioural]` (may be both); else write nothing.
   Tracks are **kept, always** — distilled at wrap, never destroyed. **Behavioural remarks stay
   raw in the track** — do NOT distil them into observation reports between handovers; that
   synthesis happens later, at brainlab reimport, not here.
4. **Gate** — do the task and **iterate with the human until explicitly approved**. Never wrap
   early; never skip the gate.
5. **Wrap** — only after complete **and approved**: distil the track into `sessionNN/report.md`
   (outcome, reasons, non-obvious points — briefly, not a step retelling); write the successor
   `sessionNN+1/prompt.md` (the handover: taskflow, predecessor report summarized one abstraction
   level higher + **referenced** not inlined, "Your task" for the next milestone); then repoint
   CURRENT PROMPT in `agents/sweep.md` (only the session number changes). **End the session there**
   — the next milestone boots cold from the handover, not from carried conversation history.

## The milestone loop (what a session actually does)

1. **Orient.** Read the milestone's `design/roadmap.md` entry, the frozen `design/spec/MN.md`
   (+ already-commissioned adjacent slices — `M5-01-split.md`, `M6-01`, `M6-02`, `M7-01`, `M8-01`
   exist), `notes/input-contracts.md` (doc A), and `entrypoints.md`'s row for carried rulings.
2. **If `implementation/prompts/MN.md` doesn't exist** (true today for M5a/M6/M7/M8 — only M4's is
   commissioned): author it, mirroring `implementation/prompts/M4.md` / the 7-section template in
   `implementation/README.md`, grounded strictly in the frozen spec slice — never invent scope.
   New-behaviour milestones get their Tier-2 **test-first step** (spec → red tests → implementation
   greens them; the test-authoring half may go to a Sonnet subagent). **Present the authored prompt
   to the human for approval before executing it.**
3. **Execute** the prompt's Do-section — yourself or via Sonnet subagents for mechanical portions.
   Triage discipline as in M4-0-05: mechanical fixes only; anything semantic **stops and gets
   recorded**, never silently weakened or deleted.
4. **Record the outcome** — `implementation/outcomes/MN.md` in the established shape (commit refs,
   files changed, real verification counts incl. any manual-mode verification the prompt requires,
   surfaced gaps).
5. **Present to the human and hold the gate** (cycle step 4). Revise on contest. Only on explicit
   approval: **commit locally** (Conventional Commits, no push — one commit set per milestone,
   independently revertible), then wrap (cycle step 5).

## The `design/` rule

The frozen `design/spec/MN.md` slices are **never edited** — standing convention. Beyond that, you
**may extend `design/`** (add an adjacent `MN-NN` slice, clarify a spec gap) — **but only with the
human's prior approval, obtained at a stop**: propose the addition, show the draft, land it on
explicit approval. **Never retroactively rewrite design to match what you built.** If a spec gap
blocks you mid-milestone, that is a judgment-call stop, not a license to improvise.

## Context discipline

Each milestone boots a **fresh session** from its handover prompt — do not run multiple milestones
in one unbroken conversation, and do not rely on auto-compaction to control token spend (lossy,
unpredictable). The written artifacts (handover prompt, track, report, outcome ledger) are the
carry-over mechanism, matching the "complete-by-construction / legible" bar this feature already
converged on.
