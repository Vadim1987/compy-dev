## Why this exists (the governing premise — read carefully)

The compy input architecture was built ad-hoc, with **no up-front design doc**. Therefore **the current
implementation is the canonical specification** of the framework's input behaviour. Feature #77 is about to
**rewrite the routing implementation** (overlay gate removal, a new `ProjectInputController`, slot
ownership/restoration) across upcoming milestones. We cannot guarantee the new API does not break the
framework unless the framework's input contracts are **written down first**. This note is that contract.

The single most important discipline of this task:

> **Separate OUTCOME from MECHANISM.**
> - **OUTCOME = the contract** to preserve: for a given `(mode, widget-state)`, *which consumer receives
>   each event, and under what exclusivity*. This is binding; the rewrite must keep it true.
> - **MECHANISM = the current realization**, free to change: the `if love.state.user_input then …` gateway,
>   the slot-swap via `set_handlers`, the `{ M, C, V }` shape, the `app_state` branching.
>
> Document **outcomes as contracts**. Describe mechanism **only** as "current realization (non-binding)",
> clearly marked, so a reader never mistakes today's implementation for the guarantee.

A contract written at outcome level survives the rewrite; one written at mechanism level is worthless (it
goes red the moment the mechanism changes, guarding nothing).

## The target shape (the judgment to apply — embed this, do not improvise around it)

Structure the note as follows.

### 1. Premise + the outcome/mechanism rule
State the canonical-implementation premise and the outcome-vs-mechanism distinction (above), so the reader
knows how to read every entry.

### 2. The two activation families (orthogonal axes)
Input routing is governed by two **independent** activations — model them as two axes, not one chain:
- **(A) Mode activation** — the application `app_state` (console/REPL, editor, project running, inspect,
  project_open, snapshot, shutdown). Mode determines the **base sink** (which consumer owns the event slot).
- **(B) Widget activation / reset** — an input **widget** (the overlay singleton today) is shown / reset /
  hidden, **orthogonally** to mode. While active it **overrides** the base sink. Capture both the
  activation step *and* the reset semantics (what a re-activation does to existing state).

Make the two-step nature explicit: first a mode is active, then a widget may be (de)activated on top of it.

### 3. The contract table — `(mode × widget-state)` per event
For each event type (keypressed, textinput, keyreleased, mouse*, touch*, wheelmoved), give the **outcome**:
which consumer receives it for each relevant `(app_state, widget active?)` combination, and the
**exclusivity rule**. Pin the canonical asymmetries the inventory found, e.g.:
- keyboard/text delivery is **exclusive** (overlay *or* base sink, never both);
- mouse/touch deliver to **both** overlay and base handler;
- `app_state == 'inspect'` **suppresses** the overlay;
- global shortcuts are **non-exclusive** (they fire, the key still reaches the sink).
(Verify each against the inventory; do not assume — these are illustrative of the *kind* of fact to pin.)

### 4. Cross-cutting contracts
The held-key set (`keys_pressed`) and its lifecycle; combo serialisation; the legacy solicitation path's
guarantees (incl. warn-on-suppression); slot **restoration** on project stop.

### 5. Forward contracts (do-not-exist-yet — clearly fenced)
Some outcomes are **introduced by the upcoming rewrite**, not present today: project key/text events
reaching the project sink; slot restoration to the console on stop; legacy native-handler coexistence;
`isrepeat` reaching the keypressed path. **Tag every contract** as **stable-now** (holds against current
code; the rewrite must preserve) vs **forward / planned** (the rewrite establishes it). Keep the forward
ones in their own clearly-marked section so no reader mistakes intent for current guarantee.

### 6. Open questions
Only **genuinely** open items (e.g. should the base sink receive `keys_pressed`?). Do not relitigate
settled design; if the inventory or `user_input.md` raises a question already answered elsewhere, omit it.
