## The configure() semantics implemented

**Active session** — `UserInputController:configure(cfg)`
(`userInputController.lua`) builds a **filtered** table containing only
`prompt`, `highlighter`, `validator`, `on_text_entered`,
`on_limit_reached` (explicit key list, not a subtraction) and feeds it
to the pre-existing `apply_config`. `text`/`cursor`/`eval`/`result` are
never read off `cfg` here — even if present, there is no code path that
reaches them. Then `update_view()` refreshes the prompt on screen
immediately (mirrors `set_text`'s own re-render, M7-01 style).

**Hidden session** — the `compy.input.configure` wrapper
(`consoleController.lua`) branches on `love.state.user_input`: when
hidden it calls `stash_hidden_configure`, which (a) runs
`merge_output_keys` — writing any provided output-callback field into
the SAME sticky `state` slots `show()` already reads (so it also stays
sticky forever after, exactly like a value given directly to `show()`),
and (b) writes `prompt`/`text`/`cursor` into a **new** `state.pending`
table, but only for keys actually provided.

**Which fields persist in which mode (the AC-3/AC-4 subtlety):**

| Field | Active `configure()` | Hidden `configure()` |
|---|---|---|
| `prompt`/`highlighter`/`validator`/`on_text_entered`/`on_limit_reached` | Applied live immediately, AND written into `state` (sticky forever, like `show()`'s own field) | Written into `state` only (no active session to apply to); sticky forever once set |
| `text`/`cursor` | **Never applied, never persisted** — dropped in full (inert) | Stashed in `state.pending`; applied **once**, on the very next `show()`, then cleared |

## The hidden-persist mechanism (single-sourced)

`consoleController.lua`'s `get_compy_input()` closure now has one
`state` table (unchanged in nature — still the one closure-local place
show()/configure() both read and write) plus a `state.pending`
sub-table for the one-shot fields. Three small free functions do the
actual work, all operating on the same `state`:

- `merge_output_keys(state, cfg)` — the pre-existing show()-inline logic
  (validator/highlighter/on_text_entered/on_limit_reached), extracted
  unchanged so `configure()` can call the identical logic instead of
  duplicating it.
- `consume_pending(pending, cfg)` — called by `show()`: for
  `prompt`/`text`/`cursor`, an explicit `cfg` value at THIS show() call
  wins; otherwise the pending value (if any) is used. Either way
  `pending[k]` is cleared after — spent regardless of whether it ended
  up used, so a LATER bare `show()` never re-injects a stale draft (a
  dedicated test proves this: `hidden-configured text does not leak
  into a later show`).
- `stash_hidden_configure(state, cfg)` — called by `configure()` only
  when hidden: `merge_output_keys` for the sticky fields, then writes
  `prompt`/`text`/`cursor` straight into `state.pending`.

`show()` itself is now three lines: `merge_output_keys`, then
`consume_pending`, then `ui:show(next_cfg)` — the exact same call it
always made. There is no second table, no second code path, and no
back door that writes to the model directly while hidden (I
deliberately rejected that shortcut — see "what will surprise the
architect" below) — everything flows through the one `show()` call the
controller already knows how to apply.

**`cursor` reaching the model:** `apply_config` (pre-existing, 27-line
body — see tech debt below) had no `cursor` handling at all before this
chunk (not even for direct `show({cursor=…})` calls — a pre-existing
spec.md gap, since spec.md §3 documents `cursor` as a `show()` field).
Rather than grow the already-over-limit `apply_config`, I added the
`cursor` handling as three lines in `open_fresh` (the fresh-activation
caller, `userInputController.lua`), right after the `apply_config`
call — spec.md's "applied after text" ordering, and it keeps
`apply_config` completely untouched (report-don't-fix). This also means
a bare `show({cursor={l,c}})` now genuinely works (not just the
configure-fed path) — a side effect I flag below.

  refactor bigger than this additive slice.
- **F-0 (`submit()` deliver-then-hide ordering) — checked, does NOT
  naturally resolve via `configure()`.** The prompt asked me to note if
  `configure` makes a "reject-keeps-open" flow naturally expressible.
  I traced it: `on_text_entered` fires while the session is still
  active (AC-25 order), so a project's callback COULD call `configure`
  or `set_text` synchronously inside it — but `configure()`'s `text` is

  synchronous `self:hide()` that runs immediately after `deliver()`
  regardless of what the callback does. So F-0 remains genuinely open;
  `configure()` does not provide the escape hatch the tech-debt entry
  speculated it might. Not fixed (F-0 is explicitly report-don't-fix
  for this chunk); noting here that the speculation didn't pan out so a
  future architect doesn't re-derive the same dead end.

  putting the cursor handling in `open_fresh` rather than gating it
  behind the configure-only path. This closes a small pre-existing
  spec.md §3 gap (the `cursor` field was documented but never
  implemented for direct `show()` calls) essentially for free. Not a
  scope violation — it was necessary infrastructure for AC-3/AC-4 — but
  flagged since it is a slightly bigger surface change than "wire
  configure/clear alone" might suggest.
- `UserInputModel:set_text` 19-line body — carried unchanged from

## What will surprise the architect (surprise-first)

- **`cursor`'s wire format is a positional `{line, col}` array**
  (`cfg.cursor[1]`, `cfg.cursor[2]`), not `{line=, col=}` fields. spec.
  md §3 documents the type as literally `{line, col}`, which reads most
  naturally as a positional tuple, and it matches `set_cursor(line,
  col)`'s own positional signature. No AC or existing code pins the
  shape definitively (the internal `Cursor` class uses `.l`/`.c`
  fields, but that's model-internal, not project-facing vocabulary).
  Conservative and reversible: if the architect prefers named fields,
  it is a one-line change in `open_fresh`'s new branch. I did not stop
  for this — it is a naming/shape detail in the same spirit as M7-01's
  `set_cursor_pos` naming call, not a Contract-semantics divergence.
- **`clear()` reuses the pre-existing `UserInputController:clear()`
  method as-is** (content + error, via `model:clear_input()` +
  `clear_error()`) rather than adding a new same-shaped controller
  method the way `configure` got one. I checked: that method has four
  other live callers (`editorController.lua`), so I did not want to
  change its behaviour (e.g. adding `update_view()` inside it) for all
  of them. Instead the `compy.input.clear` wrapper in
  `consoleController.lua` calls `ui:clear()` then `ui:update_view()`
  itself — two existing public methods, composed at the call site, no
  new controller-level `clear`-shaped method. This is a deliberate
  departure from the prompt's literal "add thin controller methods for
  configure AND clear" phrasing; I judged the second one unnecessary
  once the reuse was available. Reversible if the architect wants
  parity with `configure`/`set_cursor_pos`/`set_text`'s one-controller-
  method-per-callable shape.
- **Hidden `clear_input()` already lands the cursor at `(1,1)`** with no
  changes needed — I traced `_update_cursor(true)`'s arithmetic
  (`self.cursor.l = #t` where `t` is the freshly-emptied single-line
  `InputText()`) before writing the AC-5 test, rather than assuming and
  adding a redundant cursor-reset. Confirmed correct by the passing
  test — no model touch needed, as the prompt anticipated but did not
  guarantee.
- **The `state.pending` table is genuinely new mutable state** added to
  the `compy.input` closure (previously just `handlers` + the four
  sticky output-key slots). It is intentionally invisible from the
  project side (not exposed on the `compy.input` surface, not
  assignable, not readable) — purely an implementation detail of the
  hidden-configure mechanism — but it is new long-lived per-namespace
  state where none existed before, worth knowing about if a future
  slice reasons about `compy.input`'s memory footprint or GC behaviour.
