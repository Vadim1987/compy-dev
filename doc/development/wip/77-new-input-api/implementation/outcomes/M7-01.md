## The model fix (before/after + caller safety)

`UserInputModel:set_text(text, keep_cursor)` (`userInputModel.lua`).

- **Before:** the tail called `self:jump_end()` **unconditionally**, so a
  truthy `keep_cursor` was silently ineffective — the guarded `not keep_cursor`
  branches above were overridden by the tail jump.
- **After:** when `keep_cursor` is truthy, the function now clamps the current
  cursor into the new content's range (new private `_clamp_cursor_pos`) and
  returns before `init_visible`/`jump_end`; falsy keeps the old
  `init_visible` + `jump_end` path exactly. Added `_clamp_cursor_pos` (clamps
  `l` to `[1,n]`, `c` to `[1, llen+1]`, matching `move_cursor`'s own bound) so
  the "clamped if the new text is shorter" clause of AC-8 holds.

**Caller-safety (lua-lsp `references` on `set_text`, cross-checked with grep).**
Enumerated every `set_text` call site (grep + LSP agree). Every existing caller
passes **exactly one argument** (`keep_cursor` is `nil`/falsy), so all keep the
old jump-to-end path — the change is behaviour-safe:

- `userInputController.lua:56` `self.model:set_text(t, keep_cursor)` — I
  widened the controller signature; its prior callers still pass one arg.
- `userInputController.lua:219/264` `apply_config` / `show` force path —
  one arg (`cfg.text`).
- `userInputModel.lua:436/448` `history_back`/`history_fwd` — one arg (both
  immediately call `jump_end()` themselves anyway).
- `consoleController.lua:758` legacy `write_to_input` → `overlay.C:set_text`
  — one arg.
- `editorController.lua:336/602` `_handle_submit` / `load_selection` — one
  arg (load_selection follows with `jump_home()`).
- Tests (`input_fixture`, `editor_session`, `editor_spec_fwd`,
  `user_input_model_spec`, `input_contracts_spec`) — all one-arg except the
  new keep_cursor rows I added.

No caller relied on the old unconditional jump-when-`keep_cursor`; none passed
a truthy second arg before this slice.

## AC-7 clamp finding (real divergence — flagged, resolved per spec)

The commission asked whether `move_cursor`'s fallback-to-previous satisfies
"clamp to the valid range". **It does not, for the column.** `move_cursor(y,x)`
falls back to the *previous* coord when `x` is out of range, not to the line
end. So `set_cursor(1, 999)` routed straight through `move_cursor` would land
at the previous column, not the line end — a divergence from the spec's "clamp
to the valid range" wording. I therefore did **not** route the new
`compy.input.set_cursor` through raw `move_cursor`; the controller method
`set_cursor_pos(line, col)` computes the clamped landing itself
(`min(col, llen+1)`, `min(line, n)`) and hands `move_cursor` an
already-valid pair. The discriminating test above proves the clamped landing
(col 6), not the fallback (col 2). For the **line**, fallback-to-previous and
clamp-to-1 happen to coincide on single-line inputs, but the explicit clamp is
used uniformly so the behaviour is single-sourced and predictable.

## What will surprise the architect (surprise-first)

- **`set_cursor_pos`, not `set_cursor`, on the controller.** I minted a new
  controller method name rather than overloading the existing
  `UserInputController:set_cursor(Cursor)`. Rationale above (different
  signature, a live unclamped caller). Conservative and reversible — if the
  architect prefers a single `set_cursor` with an overloaded signature, it is a
  local rename. No new noun leaks to the project surface: the project still sees
  only `compy.input.set_cursor(line, col)`.
- **`get_cursor` does not warn when hidden.** It returns `nil` silently, per
  spec.md §6 (only `set_cursor`/`set_text` carry the no-op+warn clause; a read
  reporting "nothing" is not a refused mutation). AC-9 says "every refused call
  … warns" — I read a nil-returning read as not a refused *call* in that sense.
  If the architect wants a warn on hidden `get_cursor` too, it is one line.
- **The explicit clamp in `set_cursor_pos`/`_clamp_cursor_pos` duplicates the
  shape of `move_cursor`'s bound.** This is deliberate (see the AC-7 finding):
  `move_cursor` fallback-to-previous is *not* clamp-to-range, so I could not
  simply delegate. The duplication is small and single-purpose; a future
  refactor could add a `clamp`-mode to `move_cursor` and collapse both, but
  that is a model change beyond this additive slice.
