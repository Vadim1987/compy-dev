## Trap-by-trap

### R1 (headline) — turtle: **PASS**
`love.update`'s per-frame `if not r:is_empty() then eval(r()) end` poll is
removed; `love.keyreleased('i')` now calls `compy.input.show{prompt="TURTLE",
on_text_entered=eval}`. `eval`'s signature already matches
`on_text_entered(text)`, so it is the direct callback — no wrapper. `deliver`
(`userInputController.lua:319-329`) fires `on_text_entered` exactly once per
`submit()`. Runs once per submit, not per frame. Clean.

### R1 — maze command path: **PASS on the once-per-submit axis**
`handle_editor_submit` is the `on_text_entered` callback; it calls
`process_input(lines, offset)` once per submit — same handler, same args as
the old `process_user_input`. `rearm_input` (the still-wired `ctrl_update`,
fired every frame) only ever calls `open_editor_input` (i.e. `show`), never
the command handler, and the `input_open` guard makes `show` fire once per
open, not per idle frame (headless run showed no `Log.warn` spam). No
per-frame re-eval, no per-frame re-show on the happy path.

### FINDING (corrective) — maze cancel path leaves the editor dead
**`src/examples/maze/main.lua:491-499` (`rearm_input`) + `:478-489`
(`handle_editor_submit`)** — violates **AC-32** ("hand-playable afterwards";
each command still reachable) and is a regression from the pre-migration
self-healing poll.

`input_open` is set `true` in `open_editor_input` and cleared `false` **only**
in `handle_editor_submit`. But `handle_editor_submit` runs only on **submit**.
The framework's tier-1 **escape → cancel** entry
(`projectInputController.lua:108`, `framework_cancel` →
`UserInputController:cancel()` → `hide()`, `userInputController.lua:158-160,
276-278`) dismisses the overlay **without** firing any maze callback — cancel
has no `on_text_entered`, and maze wires no `before_/after_cancel` hook. So
after an escape, `love.state.user_input` is `nil` but `input_open` stays
`true`, and `rearm_input`'s first line (`if input_open then return end`)
no-ops **forever**. The command editor never reopens.

Concrete failure scenario (readily hand-triggered — the editor is always up
while idle, and maze's own `love.keypressed` deliberately swallows escape at
`main.lua:559`, so a player who learned "escape is inert in maze" bricks the
prompt with one keypress):
1. idle → `rearm_input` → `open_editor_input()` → `input_open=true`, overlay shown.
2. player presses Escape → framework `framework_cancel` (tier-1, fires before
   the native since the widget `is_shown`) → `ui:cancel()` → `hide()`;
   `handle_editor_submit` never runs; `input_open` stays `true`.
3. every subsequent `love.update` → `rearm_input` → `if input_open then
   return end`. Editor gone. Level is unsolvable (commands are the only way to
   win), and `Tab` when not-won → `reset_level` which does **not** re-enter
   `editor()`, so it does not restore the prompt either. Player is stuck; only
   a level transition (`next_level → start_level → cur_controls()`) re-arms it,
   which is unreachable without commands.

The old code was self-healing here: `process_user_input` (every frame) saw the
reftable empty after a cancel and called `rearm_input`, which re-issued
`input_text` the next idle frame. The migration replaced that with a
one-shot + shadow-boolean latch that mirrors the overlay's shown-state but
desyncs on the cancel path.

This is **not** an SR1 "old feel differs" case — SR1 sanctions the one-frame
reshow-delay and timing shifts, not "the command editor becomes permanently
unusable." It is a correctness regression in code this chunk added.

**Fix is example-local (hence corrective, not escalate):** key the guard off
the *actual* overlay state instead of a shadow boolean that only submit
clears — e.g. `if love.state.user_input then return end` in `rearm_input`
(the legacy overlay flag is example-legal, present pre-migration, dies in M8),
or reset `input_open=false` when the overlay is observed gone. No `show{}`
capability is missing and no route-model change is needed — the surface as
landed is sufficient; the migration logic is just incomplete on cancel.

## Note (report-don't-fix, not this chunk's job)
The `submit()` deliver-then-hide ordering forces any example that wants to
"reshow on invalid input" to defer a frame rather than reshow synchronously
inside `on_text_entered` (the re-entry guard + trailing `hide` otherwise eat
it). The implementor surfaced this as a judgement call; it is a genuine API-
ergonomics wrinkle worth logging for the M7 live-reconfigure surface, but the
behaviour is landed/frozen chunk-3 sequencing — correctly *not* changed here.
Logged to `technical_debt.md`. It does **not** by itself require a route/
surface change (the deferred-reopen works); it is only the cancel-latch above
that must be fixed for AC-32.
