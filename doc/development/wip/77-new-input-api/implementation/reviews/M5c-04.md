## Findings

### F1 — AC-29 teardown misses the `highlighter` widget output (CONFIRMED, corrective)

`src/controller/controller.lua:283` `reset_widget_outputs` resets three of the four
widget outputs on the singleton (`validator`, `on_text_entered`, `on_limit_reached`)
but **not** `highlighter`. Unlike the other three, a project's `highlighter` is not
mirrored onto the `UserInputController` — `apply_config`
(`src/controller/userInputController.lua:209-210`) writes it onto
`self.model.evaluator.highlighter`. That evaluator is the **module-global singleton**
`InputEvalText` (`src/model/interpreter/eval/evaluator.lua:157`), and both the
singleton model and the `compy` namespace are built **once** (`prepare_env` runs only
in the `ConsoleController` constructor). `reset_compy_input`
(`controller.lua:273`) nils the `compy.input.highlighter` **surface slot**
(`INPUT_CALLBACK_SLOTS`, `controller.lua:263`) but never the mirrored evaluator copy.

Net: a project that calls `compy.input.show{highlighter=fn}` mutates
`InputEvalText.highlighter`, and stop's teardown leaves it set. The next project's
widget (shown without its own highlighter and without a fresh `eval` — `compy.input.show`
never passes `eval`) renders its text through the prior project's highlighter. This
violates AC-29 "every mutable field reset … **nothing installed by the project
survives it**" (a widget output per AC-16).

**Empirically confirmed** with a throwaway spec driving the real production path
(`F.activate_project` → `F.show_widget{highlighter=fn}` → `stop_project_run`): before
stop `model.evaluator.highlighter == fn`; **after stop it is still `fn`** (expected
nil). Fix is one line in `reset_widget_outputs` (clear
`ui.model.evaluator.highlighter`), so this is a corrective, not a §8 escalation.

### F2 — test gap: the teardown row omits `highlighter` (corrective, same root)

`tests/input/input_contracts_spec.lua:1547` (`stop resets the widget's own output
fields`) asserts `validator`, `on_text_entered`, and `on_limit_reached` reset but
**not** `highlighter` — which is exactly why F1 passes unnoticed. The prompt's Trap-3
list ("the four widget outputs") is only 3/4 covered. The corrective for F1 must add
the fourth assertion (test-first).
