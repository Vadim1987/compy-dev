## Spec compliance

  load-bearing pieces (`view.view` font stub, `love.handlers = { }`) are untouched.
  Suite still reports 685, so the removal carries no behaviour change, as the spec
  predicted (`lib.profile` has no load-time LÖVE2D dependency; the runtime path is
  gated behind `if love.PROFILE`, false in test).
- **Single source for the l/r fold** — `util/key.lua:10` now owns `mod_triples`,
  built by referencing the existing `ctrl_k` / `alt_k` / `shift_k` pairs plus the
  new `gui_k` (`:8`). This is a genuine single source: edit a `*_k` pair and the
  triples follow. `controller.lua` no longer carries the literal — the old
  four-row `COMBO_MODS` table is replaced by `Key.mod_triples` (`:136`).
- **`gui` pair added** — `gui_k = { "lgui", "rgui" }`, generic name `"gui"`, as
  specified. It did not exist in `util/key.lua` before.
- **Precedence preserved** — `mod_triples` order is ctrl → alt → shift → gui,
  identical to the old `COMBO_MODS`. `combo_string` (`controller.lua:138`) is
  otherwise unchanged, so folding, bare-key passthrough, and multi-modifier
  ordering are exactly as M1 left them. Every M1 `combo_string` test passes
  unchanged.

Worth calling out: `mod_triples` deriving its entries from `ctrl_k[1]`/`ctrl_k[2]`
rather than re-typing the LÖVE key names is the right move — it removes the third
copy the M1 review warned against instead of forking one more.

## Findings

1. **`COMBO_MODS` retained as an alias, not removed.** The spec contract says
   plainly: "`combo_string` consumes the exported triples instead of its own
   literal; `COMBO_MODS` is removed." The implementation instead keeps the
   identifier as a one-line module-local alias —
   `local COMBO_MODS = Key.mod_triples` (`controller.lua:136`) — and the loop
   still reads `COMBO_MODS` (`:140`). The acceptance criterion that matters
   ("`controller.lua` holds no second copy") is satisfied; the literal is gone.
   But the name the spec asked to delete is still there. Two defensible
   resolutions:
   - inline it — iterate `Key.mod_triples` directly in the loop, which matches the
     spec text literally and drops a line; or
   - if the local was kept deliberately (it caches the table reference, sparing a
     global + field lookup per `combo_string` call, and gives the rename one
     obvious home), then the spec wording is the thing that is slightly off and
     could be reconciled.

   Either way this is a low-severity bookkeeping mismatch with zero behavioural
   impact, not a defect. Flagging it so the spec and code agree on whether the
   name survives.

2. **`gui_k` currently has only one consumer.** It feeds `mod_triples` and nothing
   else — there is no `gui()` / `is_gui()` accessor paralleling `shift()` /
   `is_shift()`. Keeping it as a named local rather than inlining `"lgui"` /
   `"rgui"` into the triple is consistent with the established `*_k` pattern and
   reads as anticipating a future accessor, which is reasonable. Noting it only so
   the asymmetry (a pair with no accessor) is a known, intended state rather than
   an oversight.

3. **Cosmetic re-alignment in the `Key` table.** Adding `mod_triples` re-aligned
   the `=` column for all eight fields (`util/key.lua:53–62`), so the diff touches
   lines that did not otherwise change. It matches the surrounding alignment style
   and keeps the table tidy; just worth knowing the extra diff lines are
   whitespace, not logic.

  `util/key.lua` is 38); `combo_string` body is unchanged and within the 14-line
  limit. No new parameters or nesting introduced.
