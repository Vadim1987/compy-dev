## Verdict

Spec is met. All acceptance criteria are covered by tests, the change is purely
additive, and the suite is green (`busted tests/input` → 84 successes locally;
outcomes doc records 685 total). No behaviour change reachable in any app mode.
The findings below are minor — one genuine duplication worth folding away in M2,
the rest are notes, not blockers.

## Spec compliance

- **`Controller.keys_pressed` live set** — `controller.lua:174`, updated at
  `keypressed` (`:550`, add) and `keyreleased` (`:665`, remove). Both writes are
  the **first** statement in their handler, ahead of the overlay split at `:647`
  / `:671`. So the set stays correct even when an overlay (`love.state.user_input`)
  owns the event — the table is maintained on the single funnel, not per consumer.
  Matches the "before any downstream handler runs" requirement exactly.
- **Precise LÖVE names, no l/r folding** — confirmed by
  `does not fold lr variants in table`.
- **`combo_string` precedence / folding / bare key** — `controller.lua:143`,
  driven by the `COMBO_MODS` data table. Fixed order ctrl→alt→shift→gui, l/r
  folded, bare key passes through. All five spec examples have a matching test,
  plus multi-modifier ordering and ctrl-before-alt precedence.
- **Additive, existing tests still pass** — confirmed; no existing code path is
  altered, only two prepended writes and two new `Controller` fields.

Worth calling out as good: `COMBO_MODS` is data-driven rather than an
if-chain over modifier names, which is the direction `rules.md` ("no C accent")
asks for. The update placement (single funnel, before the overlay branch) is the
right call and avoids a class of stuck-key bugs the per-controller routing could
otherwise introduce.

## Waste

1. **Duplicated modifier groupings (the one real item).** `COMBO_MODS`
   (`controller.lua:136`) re-declares the l/r pairs `{lctrl,rctrl}`,
   `{lalt,ralt}`, `{lshift,rshift}` that already exist in
   [`util/key.lua:5`](../../../../../../src/util/key.lua) as `ctrl_k` / `alt_k` /
   `shift_k`. There are now two sources of truth for the same fold. They can't
   trivially be shared today — `util/key.lua` keeps its lists module-local and
   has no `gui` pair — so this is a reasonable interim, not a defect. Flagging it
   so M2 (singleton extraction) folds the two together rather than carrying a
   third copy forward.

2. **`combo_string` allocates a fresh `parts` table per call** (`controller.lua:144`).
   Inert in M1 — nothing calls it yet. But it is destined for the
   `compy.input.handlers[combo]` dispatch in M4/M5, i.e. once per keystroke. Not a
   per-frame hot path, so this is a note for whoever wires the consumer, not a
   change to make now: if dispatch ends up on a hot path, a reused buffer or a
   concat-free comparison would matter. Recording it here so it isn't rediscovered
   later.

3. **Dead profiler stub in the spec (actionable now).** The
   `package.preload['controller.profiler']` block exists only to keep
   `require('controller.controller')` from pulling the real profiler. Verified
   unnecessary: removing it leaves the full suite at 685/685. Its comment
   ("profiler may load lib.profile; stub to avoid LÖVE2D dep") is inaccurate —
   `lib.profile` is pure Lua (`os.clock`), no load-time LÖVE dependency — and the
   profiler's runtime path is gated behind `if love.PROFILE`, which the test sets
   to `false`, so the real `Prof` is never called either. This is the only test
   that requires the full controller, so the stub is not a shared pattern; it was
   carried in defensively. The other two boilerplate pieces are real: `view.view`
   calls `gfx.newFont()` at load, and `love.handlers = {}` is consumed by
   `setup_callback_handlers`. Recommend deleting the profiler block and its comment.

4. **Second commit is almost entirely additive prose.** `9536302` adds six
   one-line test comments, an internals subsection, and fills the outcomes doc.
   Proportionate and on-style (comments on their own lines, per `rules.md`); the
   "saved handler refs" comment in particular earns its place by explaining a
   non-obvious test ordering hazard. Not waste — noted only to confirm it was
   weighed.

## Minor notes (no action)

- Two bare-key tests (`escape`, `s`) exercise the same branch; the redundancy is
  negligible and arguably documents intent. Leave as is.
- **Focus-loss staleness** is a known LÖVE limitation of any `keys_pressed`
  mirror: if the window loses focus with a key held, `keyreleased` may not fire
  and the entry lingers. Out of M1 scope and not introduced here, but the M4/M5
  consumer should not assume the set is leak-free across focus changes.
- The outcomes doc's surfaced gaps (`gfx` implicit global, `table.protect`
  no-op, the `src/controller.lua` path mismatch in the design docs) are all
  correctly attributed as pre-existing and out of scope. No disagreement.

## Conclusion

Ship it. Two small, safe fixes worth doing: delete the dead profiler stub from
the spec (waste #3, verified), and consolidate the modifier-pair lists so the
l/r fold lives in one place — either now via an export from `util/key.lua`
(adds a `gui` pair there) or rolled into M2's singleton extraction, which is its
natural home. Everything else (combo_string allocation, focus-loss staleness)
is genuinely later, not now.
