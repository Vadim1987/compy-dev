## Verdict

**Not approved as it stands.** The core design — one widget built at
startup, reused, driven through `show`/`hide` — is the right shape and
most of the contract is met. But the milestone narrows
`love.state.user_input` from `{ M, C, V }` to `{ C }` while a live
consumer still reads `.V`: the running-project draw overlay at
[`controller.lua:401`](../../../../../src/controller/controller.lua)
calls `ui.V:draw()`. `show()` no longer populates `.V`, so any running
project that opens an input over its own `love.draw` hits
`attempt to index a nil value (field 'V')`. Two shipped examples
(`turtle`, `tixy`) match that pattern.

The full suite is green (696/0/0/0, verified locally with `busted
tests`), but no test drives the `love.draw` overlay, so the suite does
not exercise the broken path. The outcome ledger's G-3 records this
exact narrowing as "Verified safe" on the strength of a `src/` grep
that missed `controller.lua:401`.

One blocker (F-1) plus one behaviour change to confirm (F-2); both
have small fixes. Detail below.

## Spec compliance

What the spec asked for and what landed:

- **Singleton lifecycle.** `main.lua:360-365` builds the model, view
  and controller once in `love.load()` and stores the controller at
  `love.state.user_input_controller`. `prepare_project_env` no longer
  constructs per call (`ui_model`/`ui_con`/`view` upvalues are gone).
  Per-session allocation is genuinely removed. ✔
- **`show(config)` activates / sets `love.state.user_input`.** ✔ —
  with the shape caveat in F-1.
- **`show()` while active → no-op; `show({force=true})` reconfigures
  in place; neither fires cancel.** ✔ Semantics match the spec and the
  11 new tests cover them.
- **`hide()` deactivates without cancel; content preserved;
  `love.state.user_input` set to `nil`.** ✔ for the nil-ing; content
  preservation interacts with F-2.
- **`compy.input` table with `show`/`hide` mounted.** Present via
  `get_compy_input()`; deviation noted in F-4.
- **`oneshot` retained.** ✔ — `is_oneshot`/`model.oneshot` untouched,
  submit still drives through `oneshot` at
  `userInputController.lua:390`.

## Findings

### F-1 — Blocker: `show()` drops `.V`, but the draw overlay reads it

`show()` sets `love.state.user_input = { C = self }`
([`userInputController.lua:212`](../../../../../src/controller/userInputController.lua)).
The pre-M2 `input()` closure set `{ M = ui_model, C = ui_con, V = view }`.
The running-project draw wrapper is built in `set_love_update` and ends
with:

```lua
local ui = get_user_input()
if ui then
  ui.V:draw()       -- controller.lua:401
end
```

This wrapper is installed whenever a running project supplies its own
`love.draw` (`ldr ~= View.prev_draw`). With `.V` now absent, `ui.V` is
`nil` and `ui.V:draw()` raises at the first frame after the input is
shown.

Reachability is not theoretical. Checking the shipped examples for the
trigger (custom draw + an input call that routes through `show()`):

| Example | custom `love.draw` | input call | reaches overlay |
|---|---|---|---|
| `turtle` | yes | `input_text("TURTLE")` | yes — crashes |
| `tixy` | yes | `input_code(...)` | yes — crashes |
| `guess` | no | `validated_input(...)` | overlay wrapper not installed |

`turtle` and `tixy` both call into `input()` → `show()` and both render
through a custom `love.draw`, so both fault on the input frame. This
fails the milestone's headline acceptance — "Existing examples still
work (legacy globals untouched)."

The outcome ledger's **G-3** asserts: *"A grep over the full `src/`
tree finds no code outside of `consoleController.lua`'s now-removed
closure that reads `.M` or `.V`."* That is inaccurate —
`controller.lua:401` is exactly such a read, and it is the one the
overlay depends on. The grep that backed the "Verified safe" claim
missed it.

**Fix options (small either way):**
- Populate the field that the overlay already expects:
  `love.state.user_input = { C = self, V = self.view }`. The singleton
  already holds its view (`init_view` in `main.lua`), so this is a
  one-token change and keeps the overlay's `{ C, V }` contract intact.
- Or change the overlay to reach the view through the controller
  (`ui.C.view:draw()` / a `UserInputController:draw()` shim) and drop
  `.V` from the state shape entirely.

The first is the smaller, lower-risk move for M2; the second is a
cleaner end state but touches the overlay contract and is better done
deliberately (it could fold into M4 when the controller owns dispatch).
Whichever is chosen, add a test that drives the overlay so the suite
covers it (see the test-gap note).

### F-2 — Medium (confirm at runtime): stale text across oneshot sessions

With a per-call model (pre-M2) every input session started from a fresh
`UserInputModel`, so the widget opened empty unless `init` was given.
The singleton model now persists, and two facts combine:

- `UserInputModel:handle` does **not** clear `self.entered` on a
  successful oneshot submit (`userInputModel.lua:803-842`) — it pushes
  the `userinput` event, which clears `love.state.user_input` but
  leaves the model's text in place.
- `show()`/`apply_config` only set text when `cfg.text ~= nil`
  (`userInputController.lua:190`, `205`). A re-prompt with no `init`
  (e.g. `input_text("TURTLE")`) therefore preserves the previously
  submitted text.

Net effect: after the user submits once, the next prompt re-opens
pre-filled with the prior entry instead of empty. In `turtle`/`tixy`
the input is re-requested every idle frame, so this is user-visible.
The old behaviour was "empty each time."

This needs a runtime check to confirm (the trace is strong but submit
timing is involved), and it is masked today by F-1 crashing first.
Candidate resolutions: clear the model on a fresh `show()` activation
when no `text` is supplied, or clear `entered` on oneshot submit. Note
the spec deliberately says `hide()` *preserves* content and `show()`
preserves when no `text` is given — so the right place for the clear is
the submit/fresh-activation boundary, not `hide()`.

### F-3 — Low: G-3 documentation accuracy

Tied to F-1. The "Verified safe" conclusion in the outcome ledger is
incorrect because of the missed `controller.lua:401` consumer. Once
F-1 is fixed (whichever way), G-3 should be rewritten to record the
actual state shape and its real consumers (`controller.lua:401` for the
view, plus the `.C` reads it already lists).

### F-4 — Low: `compy.input` built per project-env, not "once at namespace setup"

The spec says *"`compy.input` table is created once at namespace
setup."* `get_compy_input()` is called from `get_compy_namespace()`,
which `prepare_project_env` invokes per project setup, so the table is
rebuilt each time. No functional impact — the `show`/`hide` closures
read `love.state.user_input_controller` dynamically, so they always hit
the live singleton regardless of when the table was built. This is a
wording deviation, not a defect; reconciling it is cosmetic. The
dynamic-lookup choice is the right one — it keeps `compy.input`
resilient to the singleton being (re)assigned.

### F-5 — Low: `force = true` re-applies only text

The fresh-activation path runs `apply_config` (eval, prompt, text,
result); the `force` path sets only text. This matches the spec, which
frames `force` purely in terms of content ("content replaced if `text`
given, else preserved"). Worth recording the consequence: a
`show({force=true})` cannot re-target `result` or swap the evaluator of
an already-active session. That is fine for M2's single-consumer model
and consistent with the contract — flagging it so the limitation is a
known boundary rather than a surprise when M7 extends `configure`.

## Rules check

- **Hard limits.** `apply_config` and `show`/`hide` are within the
  14-line body limit (`show` body is ~12 lines), nesting tops out at 3,
  no new line exceeds 64 chars, no helper takes more than its existing
  parameter count. `get_compy_input` is a flat table literal.
- **Formatting.** `{ C = self }` uses the spaced-brace form; comments
  are on their own lines; the singleton-API block carries a banner
  comment consistent with the file's existing section headers.
- **Design / "no C accent".** `apply_config` is a plain field-by-field
  applier, not a tag-dispatch; no string-keyed function dispatch
  introduced. The `compy.input` closures store and call behaviour
  directly. Consistent with the conventions.
- **File = console.** The singleton is created in `love.load()` and
  read via `love.state`; the `compy.input` closures resolve the
  controller at call time, so there is no load-order trap. ✔
- **Commit type.** `feat:` is correct for the new `show`/`hide`/
  `compy.input` surface; the two follow-ups are correctly `docs:`.

## Test coverage note

The 11 new tests in `tests/input/singleton_spec.lua` validate the
`show`/`hide` *method semantics* on ad-hoc controllers (`make_ctrl`
builds a fresh controller with a `render`-only mock view). They do not
exercise (a) the `main.lua` wiring that creates the real singleton, or
(b) the `love.draw` overlay that consumes `love.state.user_input`.
Both gaps are why F-1 passes CI. A regression test that asserts the
state shape carries whatever the overlay needs — and ideally drives
`ui.V:draw()` (or its replacement) against the singleton — should land
with the fix.
