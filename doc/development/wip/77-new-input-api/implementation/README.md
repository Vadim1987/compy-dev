# Feature #77 — Implementation (black-box execution ledger)

_Generated by LLM(Claude Opus 4.8): 2026-06-16 (session 05); Approved by human?: NOT YET;_

> The **implementation side** of feature #77. Deliberately **unmanaged**: no per-sprint SDLC
> instance, no session management, no progressive prompting. The design (`../design/`) is
> converged and frozen; implementing a milestone is **mechanical execution against a fixed
> spec slice**. See `../README.md` → "Why this split" for the rationale.

## The model

The implementation agent is a **black box**: it receives **one self-contained prompt** naming a
spec slice and where to record the result, does the job, commits, records the outcome, and then
**waits for the human to approve** (it does not blindly exit — the human may contest and demand
fixes). There is no progressive prompting and no SDLC chain on this side; all the design judgment
already happened in `../design/`. The one interaction it keeps is the **final approval loop**.

```
prompts/MN.md   ──▶   [ black-box implementation agent @ repo root ]   ──▶   outcomes/MN.md
(self-contained task)        (reads ../design, edits src/, writes tests)      (commits + verification + gaps)
```

- **`prompts/MN.md`** — the self-contained task handed to the black box. Drafted/reviewed here
  under session management, then handed over. One per milestone.
- **`outcomes/MN.md`** — the result ledger: commit refs (world-out), verification record, and any
  gaps the spec didn't anticipate. The black box writes the draft; the human fills commit hashes on
  commit.
- **Per-milestone, on activation only.** No `prompts/`/`outcomes/` entry exists until its milestone
  is picked up. We don't pre-shard the roadmap.

## Where the black box operates (project repo, project rules)

The implementation agent runs **inside the project repo** (`topics/git/`, root = its cwd), not under
brainlab session management. It follows the **project's own** rules, conventions, and toolchain:

- **Conventions:** [`agents/rules.md`](../../../../agents/rules.md) — the repo's **compiled,
  authoritative** ruleset (code hard-limits + style, design principles, commit conventions, and an
  index of `doc/development/*`). The repo-root `CLAUDE.md` auto-loads it, so the black box gets it for
  free; the prompts just point at it instead of restating conventions. (It is itself compiled from
  `doc/development/conventions/`.)
- **Tests:** under [`tests/`](../../../../tests/) by area (input work → `tests/input/`). Harness +
  coverage map in [`doc/development/tests.md`](../../tests.md) — note `mock.keystroke("C-return")`
  and `EditorSession`. Run with `busted tests` (or `just ut_all`).
- **Feature docs:** under [`doc/development/`](../../) (e.g. `internals/`, `keyboard.md`).
- **Commits:** the agent **commits locally** using the repo's existing committer config (it does
  **not** change git identity), following the Conventional Commits convention. A `pre-commit` hook
  (`just setup-hooks`) runs the suite. This is the project repo and the human owns it — local commits
  by the agent are explicitly authorised here. *(This overrides brainlab's `agents/git.md`
  "commits belong to the human", which governs the **session-managed** side, i.e. Claude — not the
  black box working in the project repo.)*
- **Toolchain:** lua, luarocks, busted, love2d, just — provided by the dev image (see **M0** below).
  So unlike the brainlab workspace, the black box **can run the tests** and must do so before
  committing; the outcome ledger records the real result, not a "pending" placeholder.
- **`../design/` is a frozen input** — the black box reads it, never edits it.

## Escalation — when the black box is the wrong tool

If a milestone proves **cognition-heavy or human-driven** (design churn, real judgment calls —
e.g. the integration-heavy **M4** gate removal or **M6** boundary model), do **not** force it
through the black box. Promote it to its **own subtopic** with full SDLC + session management, and
discuss the outcome back under session management (with Claude). The ledger is the default; the
managed lifecycle is the on-demand exception.

## The prompt template

`prompts/M1.md` is the **canonical template** — clone it for M2, M4, …, swapping the milestone
specifics. A prompt must be self-sufficient (the black box has no workspace context) and always
carry these sections:

1. **You are** — one-shot implementation agent, repo root = cwd; do the job, then **wait for human
   approval** (don't blindly exit).
2. **Read first** — the milestone slice (authoritative) + `spec.md §N` (context) + roadmap entry +
   the project conventions (`doc/development/conventions/`) + the real file paths it will touch.
3. **Do** — implement exactly the slice's Contract + Acceptance; scope discipline (don't reach into
   downstream milestones); write/extend tests under `tests/<area>/`; **run the suite** (`busted tests`);
   update `doc/development/` docs if warranted; **commit locally** (Conventional Commits).
4. **Record the outcome** — write `outcomes/MN.md` (commit refs, files, verification = real test
   result, surfaced gaps).
5. **Approval loop** — present a summary and **wait**; revise on contest; done only when the human
   approves.
6. **Boundaries** — stay within the slice's file list; on overreach, stop and record a gap; never
   edit `../design/`.
