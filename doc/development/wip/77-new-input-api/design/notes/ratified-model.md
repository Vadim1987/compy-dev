```
love.handlers.<event>                     (gateway — one per event type)
  │  keys_pressed bookkeeping (add on press / remove on release, before anything runs)
  │  global shortcuts — fire, NEVER consume (Ctrl+Q/S/T, restart, profile, Ctrl+Esc on release)
  ▼
ACTIVE ROUTE — exactly one, selected by mode          console | editor | project
  (never zero, never two; a widget never selects the route)
  ▼
THE CHAIN — one shape, all keyboard/text events, inside the active route:

   1. framework_handlers[combo]      non-overridable structural keys (Enter, Escape…)
   2. compy.handlers[combo]          project-registered per-combo handlers
   3. compy.input.on_key_pressed     generic project callback — DEFAULT: noop (+debug log)
   4. sink                           ALWAYS terminal, never removed by anything above:
                                       visible → text editing, returns limit signal
                                       hidden  → internal no-op (+debug log), mutates nothing

   truthy return at any tier = consumed → stop.  falsey = fall through.
   Overriding tier 3 NEVER removes tier 4 — there is no replace-semantics anywhere.
```

## The rules

- **Uniform signature:** the whole keypressed path carries `(k, keys_pressed, isrepeat)` — the
  sink included. `keys_pressed` is read-only downstream; combo serialisation folds l/r
  (`"ctrl+s"`), the held set does not (`lctrl`≠`rctrl`).
- **All event types, one shape (ruling 4):** `keyreleased` and `textinput` run the same chain;
  a tier that cannot apply collapses (textinput has no combo tiers — characters are not combos:
  tier 3 = `on_text_entered`, then sink). No event type gets its own routing rule.
  >> REVIEW: what if textinput comes while modifier handle is pressed? (Specific example: 'ctrl+v'). Assumption was we could use either combos or generic handler (on_key_pressed) to intercept it if it has special meaning
- **Project route lives only in `'running'` (ruling 3):** connected on run start, disconnected
  when the run stops *or returns non-blocking* (→ `'project_open'`, console route owns
  keyboard/text again). **Scope: keyboard/text slots only** — pointer/click paths are a separate
  pre-existing surface, untouched (`sapper`/`drawdebug` depend on them in `'project_open'`).

  >> REVIEW: drawdebug is trash (one-off thing), will be deleted from workspace. sapper is intentionally 'paper-and-pen' game -- it does not overload draw/update simply because it relies on compy defaults for doing this. We have 'drawing system' doc that explains the approach. So I do not think its conceptually different from other projects -- except its purposefully designed to utilize paper-and-pen drawing. So maybe its being playable even after 'inspect/pause' is an implementation mistake?
  >> REVIEW: I recall balloons were not responding to project stop shortcuts -- not sure if it was true, if it was problem, but certainly it was not intentional... 

- **Legacy natives = one auto-provisioned chain participant, not a routing mode (ruling 2
  applied to D-9):** if the project set native `love.keypressed`/`textinput`/`keyreleased` and
  no `compy.input` handler, tier 3 is provisioned with: *widget shown → yield (falsey, native
  not called — the key falls to the sink/widget); widget hidden → call the native.* Covers all
  three keyboard channels. Reproduces today's example behaviour exactly (turtle/maze verified).

  >> REVIEW: why not just wrap into the provisional compy.input. hook and use same chain? If technically not possible, why not break examples and fix them to new API (we have mandate for that). Exlusion (custom logic) seems unjustified, it breaks the design rule of predictability.

  **⚠ one precision point:** the rulings note said "returns truthy while shown"; that form makes
  the participant invoke the widget itself. The yield form above keeps the sink strictly
  terminal — same observable behaviour. Ratify the yield form (or overrule).

  >> REVIEW: I am not sure what is meant by 'yield' form there? Also need to check what is ruling note exactly about -- could it be misinterpreted? Mechanism of using return value to stop/enable propagation mirrors well-known scheme of DOM bubbling, and has no caveats I can think of. Using 'yield' is less obvious and trackable -- but if its preferrable, let me know why and how.

- **Predictability meta-rule (ruling 2):** anything "special" must be demoted to a variation of
  the common principle or escalated as a question — never encoded as an ad-hoc rule.
- **Semantic chains are call-order, not return values:** `before_submit → submit → after_submit`
  (and cancel likewise) order by position; the truthy convention governs only the dispatch chain.

  >> REVIEW: it may be useful to allow 'before submit' block the submission by return value but maybe in the future

- **Mouse/pointer/wheel:** outside the chain, characterized as-is (doc A §5.5-5.7); unification
  is a future design item, not #77.

  >> REVIEW: still worth leaving the path for it, if low-cost 

- **`inspect`:** owner-deferred (doc A §5.4); the chain does not decide it.

  >> REVIEW: worth a look at current implementation -- if we can serve it unambiguously within the same fundamental model, then why not

## The vocabulary (binding glossary — ruling 5; implementors mint no nouns outside it)

| Term | Means | Status |
|---|---|---|
| **route** | the one consumer an event is dispatched to, selected by mode | binding |
| **chain** | the four-tier dispatch inside the active route | binding |
| **tier** | one chain position (1-4 above) | binding |
| **sink** | *shorthand for the chain's terminal tier* — not a routing decision, not a first-class routing concept | binding as shorthand only |
| **widget** | the route-managed input surface (the singleton, project route) | binding |
| **participant** | any callable occupying a chain tier (incl. the auto-provisioned legacy one) | binding |
| **gateway** | `love.handlers.*` — platform entry, runs bookkeeping + shortcuts | binding |
| **slot / occupancy** | mutable `love.*` fields — *mechanism, non-binding*; "occupy" acceptable only as shorthand for "currently active route"; slot-reconfiguration-as-routing is a replacement candidate (routing table below fixed slots) | mechanism |
| **`keys_pressed` / combo string** | held-key set / its canonical serialisation | binding |
