## The diagram

```
love.handlers.<event>                     (gateway — one per event type)
  │  keys_pressed bookkeeping (add on press / remove on release, before anything runs)
  │  global shortcuts — fire, NEVER consume (Ctrl+Q/S/T, restart, profile, Ctrl+Esc on release)
  ▼
ACTIVE ROUTE — exactly one, selected by mode          console | editor | project
  (never zero, never two; a widget never selects the route)
  ▼
THE CHAIN — one shape, all keyboard/text events, inside the active route:

   1. framework_handlers.<event>[combo]   non-overridable structural keys (Enter, Escape…)
   2. handlers.<event>[combo]             project-registered per-combo handlers
                                            (uniform mechanism on every channel; one sub-table
                                             per event type — keypressed | keyreleased | textinput,
                                             ruled R14; press combos the common case)
   3. per-event generic callback          on_key_pressed | on_text_input | on_key_released
                                            — DEFAULT: noop (+debug log)
   4. sink                                ALWAYS terminal, never removed by anything above:
                                            visible → text editing; boundary/submit conditions
                                              surface through the widget's OWN outputs
                                              (on_limit_reached, on_text_entered…), never
                                              through chain return values (ruled R12)
                                            hidden  → internal no-op (+debug log), mutates nothing

   truthy return at any tier = consumed → stop: the event travels no further, the sink
   included, FOR THAT EVENT.  falsey = fall through.
   Consuming ≠ removing (ruled R13): configuration is permanent, flow is per-event.
   No tier override ever REMOVES a lower tier from the configuration — there is no
   replace-semantics anywhere. Tier 4 is permanently configured; whether it runs for a
   given event is decided per-event by the tiers above. (The sink is terminal, so its
   own return value has no chain meaning — nothing sits below it.)

WIDGET OUTPUTS — routing OUT of the widget (not chain tiers):
   the widget solicits text and reports results via its configured callbacks —
   on_text_entered (submit: text assembled + Enter), on_limit_reached (boundary),
   validator / highlighter (config). Set at show()/configure() — easy path, no
   chain wiring required by the project.
```

## The rules

- **Uniform signature:** the keypressed path carries `(k, keys_pressed, isrepeat)` — the sink
  included; textinput carries `(text, keys_pressed)`; keyreleased `(k, keys_pressed)`.
  `keys_pressed` is read-only downstream; combo serialisation folds l/r (`"ctrl+s"`), the held
  set does not (`lctrl`≠`rctrl`). Channel caveats (Ctrl-chords emit no textinput; Shift/AltGr do)
  are marked **in code** at the dispatch site (ruled R4).
- **All event types, one shape (ruling 4):** `keyreleased` and `textinput` run the same chain.
  The combo tier is one uniform mechanism available on every channel (ruled R2); a tier with no
  participants falls through. No event type gets its own routing rule.
- **Combo-tier structure is per-event (ruled R14):** the combo tiers are keyed
  event-type-first — `handlers.keypressed[combo]`, `handlers.keyreleased[combo]`,
  `handlers.textinput[combo]` (and `framework_handlers.*` likewise). One flat `[combo]` table
  serving all channels (the old spec's shape) is a **known derivation-drift attractor** and is
  forbidden. Naming tweakable per R3; the per-event structure is binding.
- **The mutable/immutable API boundary (ruled R3):** the project-mutable dispatch surface is
  exactly the `handlers` table(s) + the `on_*` callback fields; everything else on `compy.input`
  is callable API, protected against assignment (errors loudly). Naming tweakable
  post-implementation; the boundary is not.
- **Two directions, two surfaces (ruled R1):** the chain routes events *into* the active route;
  the **widget reports out** via its configured callbacks (`on_text_entered`, `on_limit_reached`,
  validator/highlighter). `on_text_entered` is widget vocabulary (submit-time, assembled text) —
  it is **not** the per-character chain callback (that is `on_text_input`). Soft target, worth
  proving: a project should get soliciting input working with nothing but
  `show{...callbacks...}` — no chain knowledge.
- **Run-end boundary = status quo (ruled R5):** a run stays `'running'` while the project hooked
  `update`/`draw`; otherwise it drops to `'project_open'` when `main.lua` returns. The project
  route (keyboard/text) is connected **only while `'running'`** (ruling 3); pointer natives
  remain slot-hooked until stop — today's behaviour, adopted as the design constraint
  (pen-and-paper projects like `sapper` depend on it; the kbd/pointer asymmetry is recorded
  as characterized status quo, its unification future work).
- **Predictability meta-rule (ruling 2):** anything "special" must be demoted to a variation of
  the common principle or escalated as a question — never encoded as an ad-hoc rule.
- **Semantic chains are call-order, not return values:** `before_submit → submit → after_submit`
  (and cancel likewise) order by position; the truthy convention governs only the dispatch chain.
  Reserved future extension (R9): `before_submit` *may* later gain a veto return; the design
  must not preclude it (the FR-1 validator already covers block-bad-input-at-submit).
- **Mouse/pointer/wheel:** outside the chain, characterized as-is (doc A §5.5-5.7). The chain
  shape is event-type-generic by construction, so pointer can adopt it later at no model cost
  (R10); not #77.
- **Cursor/text control (R99):** FR-8/9/10 are widget-surface API — `get_cursor` / `set_cursor` /
  `set_text` / `configure` / `clear` (M7 slice, D-8 2D cursor contract). Widget vocabulary, not
  chain vocabulary.

- **Legacy natives = pure wrap (ruled R7):** a project's native
  `love.keypressed`/`textinput`/`keyreleased` auto-provision as **plain tier-3 participants** —
  no widget-aware gating, no custom logic; the chain treats them like any other participant.
  Consequence (FR-6's letter): native handlers see events while the widget is shown. The two
  affected examples (**turtle**, **maze** — the only natives-plus-widget users) are **migrated**
  under the SR1 break mandate ("only text fields break") — per the ruling, breaking-and-fixing
  affected examples is not merely permitted but *expected*; preserving their old behaviour would
  be effort burn. D-9's "zero example changes" clause is formally lifted for these two;
  pure-native projects (pong, life, paint, clock, keyboard) are unaffected.
- **`inspect` is a mode→route line, nothing more (ruled R11):** inspect = the **console route
  active, bound over the project environment**; project route disconnected (ruling 3's shape);
  the project widget unhonoured because its owning route is inactive. Matches the current
  implementation exactly (`suspend()` restores all slots to console). Deferred remains only
  inspect's adoption of the future migrated console surface.

## The vocabulary (binding glossary — ruling 5; implementors mint no nouns outside it)

| Term | Means | Status |
|---|---|---|
| **route** | the one consumer an event is dispatched to, selected by mode | binding |
| **chain** | the four-tier dispatch inside the active route | binding |
| **tier** | one chain position (1-4 above) | binding |
| **sink** | *shorthand for the chain's terminal tier* — not a routing decision, not a first-class routing concept | binding as shorthand only |
| **widget** | the route-managed input surface (the singleton, project route) | binding |
| **widget outputs** | the widget's outbound callbacks — `on_text_entered` (submit), `on_limit_reached`, validator/highlighter config | binding |
| **participant** | any callable occupying a chain tier (incl. auto-provisioned natives) | binding |
| **gateway** | `love.handlers.*` — platform entry, runs bookkeeping + shortcuts | binding |
| **slot / occupancy** | mutable `love.*` fields — *mechanism, non-binding*; "occupy" acceptable only as shorthand for "currently active route"; slot-reconfiguration-as-routing is a replacement candidate (routing table below fixed slots) | mechanism |
| **`keys_pressed` / combo string** | held-key set / its canonical serialisation | binding |
