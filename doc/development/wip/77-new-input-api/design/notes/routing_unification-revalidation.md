## 2. Commissioned check #1 — ruling 3's deferred consequence (non-blocking runs)

**Question.** Ruling 3 disconnects the PIC outside `'running'`. Does any example rely on project
handlers staying live after a non-blocking run returns (`sine`/`life`-class)?

**Lifecycle fact** (`consoleController.lua:253-262`): after project `main.lua` returns,
`app_state` stays `'running'` iff the project hooked `update` or `draw` (`user_is_blocking`,
`controller.lua:941-943`); otherwise it drops to `'project_open'`.

**Census of all 15 examples** (grep over `src/examples/*/main.lua`, verified by reading the
edge cases):

| Class | Examples | Consequence under ruling 3 |
|---|---|---|
| Native kbd handlers **and** update/draw → stay `'running'` | life, pong, paint, turtle, maze, keyboard, clock | Unaffected — PIC connected throughout their lifetime. |
| No kbd handlers, no update/draw → drop to `'project_open'` | **sine** (pure draw-once script, zero handlers), sapper, drawdebug | Nothing keyboard-shaped to disconnect. `sine` literally defines no handler of any kind. |
| Widget/polling users with update/draw → stay `'running'` | repl, guess, valid, tixy, balloons | Unaffected. |

**Verdict: no example relies on keyboard/text handlers after a non-blocking return.** The
`life`-class stays `'running'` (blocking by definition of `user_is_blocking`); the `sine`-class
has nothing wired.

**⚠ The one real constraint found — the disconnect must be scoped to keyboard/text slots:**
- **sapper** (native `love.mousepressed`, `sapper/main.lua:696`, **no** update/draw) and
  **drawdebug** (`love.singleclick`, `drawdebug/main.lua:18`) land in `'project_open'` and
  **remain playable there via the pointer/click paths** — the pointer slots keep the project's
  natives until stop (`hook_pointer`, gateway `handlers.mousepressed` → `love.mousepressed`),
  and click detection polls the project `compy` table regardless of state
  (`controller.lua:496-525`).
- Ruling 3 as stated ("PIC simply not connected outside `'running'`") is keyboard/text-scoped by
  construction (PIC occupies only those slots) — but the re-derived spec must say so explicitly,
  or a faithful implementor could "unify" pointer disconnection in and break sapper/drawdebug.

**Runtime caveat.** This container has no `love`/`busted` (the M0 image does), so the census is
static — but it is exhaustive over the example set and the lifecycle code path is unambiguous.
A 3-minute manual confirmation in the M0 image, if wanted at the gate: run `sine` (expect: returns
to REPL prompt, typing echoes in console), then `sapper` (expect: minefield still clickable after
load), then `life` (expect: `r`/`+`/`-` respond — it stayed `'running'`).

## 3. Commissioned check #2 — D-9 / the pong-paddle leak, as a chain participant

**Question.** Under a pure chain, a legacy project's native handler would receive keys while the
widget is shown (typing into a prompt also moves the paddle). The rulings note reconciles this as
an auto-provisioned **chain participant**. Verify this reproduces today's example behaviour.

**Who is actually exposed** (census): the leak needs a project with **both** native keyboard
handlers **and** widget solicitation — that is **turtle** and **maze** (pong itself never
solicits, so it can never show the widget; the "paddle" is the archetype, not the instance).
Native-handler channels in use across examples: `keypressed` (7 examples), `keyreleased`
(clock, keyboard, maze, turtle), `textinput` (keyboard). **The accommodation must cover all
three channels**, not keypressed alone.

**Sharpest concrete case — turtle** (`turtle/main.lua:49-58`): native `love.keyreleased` fires
`input_text("TURTLE")` on the `i` key. Today, with the widget shown, typing `i` into the prompt
does **not** re-trigger `input_text` (the widget diverts all three channels; natives see
nothing). Under an unaccommodated chain, every typed `i` would re-invoke `input_text` —
re-minting the polling reftable `r` mid-session (the pending submit would fill an orphaned
handle) plus warn-spam from the suppressed re-`show()`. The leak is real and behaviour-changing;
the accommodation is mandatory, not cosmetic.

**The participant reproduces today's behaviour — in the yield form:**

> Auto-provisioned when the project set natives and no `compy.input` handler (M4's detection
> logic, `projectInputController.lua:80-91`, is the right trigger):
> `participant(k, keys, isr) = if widget_shown then return nil --[[yield: fall through to the sink; native not called]] else return native(k, …) end`

| Scenario | Today (gate / M4 split) | Chain + yield-form participant |
|---|---|---|
| Widget shown, any key/char/release | widget consumes; native sees nothing | participant yields → falls to terminal sink → widget consumes; native not called ✓ |
| Widget hidden, native present | native receives | participant calls native; native's `nil` return falls to sink → sink hidden → internal no-op ✓ |
| Widget hidden, no native (e.g. `sine`) | nothing happens | no participant provisioned; default noop tier → sink no-op ✓ |

**⚠ One precision point for ratification.** The rulings note phrases the participant as
"returning **truthy** while the widget is shown". Truthy-while-shown reproduces behaviour **only
if the participant itself invokes the widget** (M4's `native_split` shape) — which re-creates a
second sink invocation above the terminal sink. The **yield form** (falsey-while-shown, native
suppressed, key falls through to the sink) reproduces the same observable behaviour while keeping
the sink strictly terminal — strictly closer to ruling 1 ("sink always last") and ruling 2 (no
special mechanics; the participant is just a handler that declines). **Recommended: ratify the
yield form.** Either form passes the behaviour test; only one keeps the model clean.

## 4. Residue — true statements that must survive into the re-derivation

- The pointer/mouse path is **not** part of the keyboard chain today and no ruling folds it in
  (pushback C6/C22 = future design item, explicitly not #77). The re-derived spec must leave it
  characterized (doc A §5.5-5.7), not "unified" opportunistically.
- `keys_pressed` proxy widening, `show({force=true})` semantics, D-5 both-scopes limit reporting,
  C1/C2/C3 conventions — round-2 stakeholder rulings recorded in the old corpus remain valid
  inputs (salvage list for Stage 2).
- `inspect`-mode ownership stays owner-deferred (doc A §5.4) — the chain model does not decide it.
- The gateway → mutable-slot dispatch, `userlove` sandbox, `{M,C,V}` handles, slot-swap-as-routing
  are **mechanism, non-binding** (doc A §1, ruling 5) — free to change under the routing-table
  direction (`Controller._keyboard_route`), never to be specified as contract.
