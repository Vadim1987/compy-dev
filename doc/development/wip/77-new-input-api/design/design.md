## §0 The ratified model (verbatim from `notes/ratified-model.md`, rev round-4 — RATIFIED 2026-07-05)

```
love.handlers.<event>                     (gateway — one per event type)
  │  keys_pressed bookkeeping (add on press / remove on release, before anything runs)
  │  global shortcuts — fire, NEVER consume (Ctrl+Q/S/T, restart, profile, Ctrl+Esc on release)
  ▼
ACTIVE ROUTE — exactly one, selected by mode          console | editor | project
  (never zero, never two; a widget never selects the route)
  ▼
THE CHAIN — one shape, all keyboard/text events, inside the active route:

   1. framework_handlers.<event>[combo]   non-overridable structural keys (Enter, Escape…)
   2. handlers.<event>[combo]             project-registered per-combo handlers
                                            (uniform mechanism on every channel; one sub-table
                                             per event type — keypressed | keyreleased | textinput,
                                             ruled R14; press combos the common case)
   3. per-event generic callback          on_key_pressed | on_text_input | on_key_released
                                            — DEFAULT: noop (+debug log)
   4. sink                                ALWAYS terminal, never removed by anything above:
                                            visible → text editing; boundary/submit conditions
                                              surface through the widget's OWN outputs
                                              (on_limit_reached, on_text_entered…), never
                                              through chain return values (ruled R12)
                                            hidden  → internal no-op (+debug log), mutates nothing

   truthy return at any tier = consumed → stop: the event travels no further, the sink
   included, FOR THAT EVENT.  falsey = fall through.
   Consuming ≠ removing (ruled R13): configuration is permanent, flow is per-event.
   No tier override ever REMOVES a lower tier from the configuration — there is no
   replace-semantics anywhere. Tier 4 is permanently configured; whether it runs for a
   given event is decided per-event by the tiers above. (The sink is terminal, so its
   own return value has no chain meaning — nothing sits below it.)

WIDGET OUTPUTS — routing OUT of the widget (not chain tiers):
   the widget solicits text and reports results via its configured callbacks —
   on_text_entered (submit: text assembled + Enter), on_limit_reached (boundary),
   validator / highlighter (config). Set at show()/configure() — easy path, no
   chain wiring required by the project.
```

The model's **rules** (uniform signatures; combo tier uniform on every channel; the
mutable/immutable API boundary; two directions/two surfaces; run-end boundary = status quo;
predictability meta-rule; semantic chains are call-order; pointer outside the chain; cursor
control as widget-surface API; legacy natives = pure wrap; inspect = mode→route line) and the
**binding glossary** are in [`notes/ratified-model.md`](notes/ratified-model.md) — read them
there; they are not restated here to keep a single mutation-proof copy. That file is canonical.

## Summary — the design at a glance

**What it adds.** A persistent, callback-driven input widget for Compy projects — one
configurable edit area with `show`/`hide`/`configure` lifecycle, widget-output callbacks
(submit, boundary, validator/highlighter), and programmatic cursor/content access — plus a
**project input route** with a uniform four-tier dispatch chain for keyboard/text events
(per-combo handlers, per-event generic callbacks, the widget's editor as the permanent
terminal sink). The legacy text-input globals (`input_text()` etc.) are **removed** — no
backward compatibility (D-1 discarded by stakeholders); their examples migrate. Console/editor
migration to the same chain is a named follow-on (FR-11/12 are expressiveness targets only).

**The architectural change — routing unification.** The overlay gate (route-by-widget-presence)
is gone. Mode selects **exactly one active route** (console / editor / project); inside the
active route every keyboard/text event runs **one chain shape** (§0). Widget visibility is
state on the widget, never a routing condition. Native `love.keypressed`/`textinput`/
`keyreleased` handlers a project defines are **wrapped as plain tier-3 participants** — no
special-casing (ruled R7); the two examples this visibly changes (turtle, maze) are migrated
under the SR1 break mandate.

## §1 Problem and scope

Unchanged from the requirements: the current input API is polling-based and fragmented —
projects poll a reftable to detect submits, cannot react to key events while a prompt is
shown, and cannot hide/show a prompt without tearing it down. This feature replaces it with
the configurable widget + event-driven chain above. Out of scope: multiple simultaneous edit
areas, touch (no separate work — rides the existing mouse handlers), built-in-keyboard
function keys (OS-intercepted), mouse behaviour changes, and the actual console/editor
rewrite ([`requirements.md`](requirements.md) §4).

## §2 Architecture — gateway, routes, chain

Elaboration of §0, platform-grounded (evidence: the Stage-1 verdict table,
[`notes/routing_unification-revalidation.md`](notes/routing_unification-revalidation.md)):

- **Gateway** (`love.handlers.<event>`): runs `keys_pressed` bookkeeping first (add on press /
  remove on release, l/r unfolded — before any consumer), then the global shortcuts, which
  fire but never consume (doc A §6.3, §6.1). Then dispatches to the active route.
- **Active route**: exactly one, mode-selected; inter-route dispatch is EXCLUSIVE for every
  event type (doc A §3 — ratified invariant). Today the editor is reached via the console
  route's internal fork; the three-sibling symmetry is the target shape, and console/editor
  migration onto the chain is the named follow-on (D-7 rollout unchanged).
  **Scope discipline (Gate-2 closing ruling, 2026-07-06):** no further architectural
  simplification/unification is pursued in this pass beyond the ratified model — "we should
  not pursue ideal architecture on all facets in one pass." The console/editor migration is
  the designated venue for the next simplification round, and the moment to engage
  stakeholders on what could change or drop on the dev-facing facets of those modes.
- **The chain** runs inside the active route with the same four-tier shape on all three
  keyboard/text channels (`keypressed`, `textinput`, `keyreleased` — ruling 4). A tier with no
  participants falls through. Combo tables are keyed **event-type-first**
  (`handlers.keypressed[combo]` etc., R14); one flat table serving all channels is forbidden
  (the old spec's shape — a known derivation-drift attractor).
- **The sink** is the widget's text editor, permanently configured as tier 4. Its
  hidden-check is **internal** (no-op + debug log; mutates nothing — doc A §3C, hidden widget
  never consumes); there is no external gating wrapper (the M4 `native_split`/`sink_keypressed`
  shape is superseded).
- **Mechanism is free.** The shared `dispatch(...)` function, slot-swap vs. routing-table
  realization, `userlove` sandbox, `{M,C,V}` handles — all non-binding mechanism (ruling 5,
  RU-10); the contract never names them. `Controller._keyboard_route` (a routing table below
  fixed slots) is the sound direction, not a requirement.

## §3 The widget and its outputs — two directions, two surfaces

The chain routes events **into** the active route; the widget reports **out** via its
configured callbacks (ruled R1 — "routing out of the widget, not into it"):

- **Widget outputs**: `on_text_entered(text)` at submit (text assembled + Enter),
  `on_limit_reached(direction, scope)` at a cursor boundary (D-5: direction up/down/left/right
  × scope input/line), `validator` / `highlighter` as behaviour config.
- **Configured at `show()`/`configure()`** — the easy path. A project gets soliciting input
  working with nothing but `show{...callbacks...}` — zero chain knowledge (NFR-4; R1's soft
  target, worth proving in the examples).
- **`on_text_entered` is widget vocabulary**, not chain vocabulary. The per-character chain
  callback is **`on_text_input`** (tier 3 on the textinput channel). The two names are never
  interchangeable — the R1 trap this corpus already fell into once.
- **Boundary/submit conditions never travel as chain return values** (ruled R12): the sink is
  terminal, so its return has no chain meaning; the widget's own outputs are the reporting
  surface. (Today's console drives history off a limit *return value* — under this model that
  becomes the console route wiring `on_limit_reached`, a proof case, when it migrates.)
- **Submit/cancel are framework-tier** (tier 1: Enter, Escape) with **call-order semantic
  chains**: `before_submit → submit → after_submit`, `before_cancel → cancel → after_cancel`
  (D-4). The framework owns the middle step; hooks cannot suppress it (a `before_submit` veto
  is a **reserved future extension** — R9 — the design must not preclude it; blocking bad
  input at submit is already the validator's job, FR-1). Escape now genuinely dismisses
  (cancel step hides the widget) — fixing the known clears-but-doesn't-dismiss limitation.
- **Ephemerality is route policy, not widget nature (Gate-2 round-1 concern, resolved).** The
  uniform, binding part of submit — for every present and future chain adopter — is its
  **shape**: the widget never owns submit; the owning route's tier-1 `framework_handlers`
  does, wrapped in the D-4 hook chain. Deactivate-on-submit is **not** part of that shape: it
  is the **project route's** middle-step policy (deliver via `on_text_entered`, then
  auto-close — today's `oneshot=true` UX, kept because it is the project common case and the
  legacy-mapping expectation). When console/editor migrate onto the chain they mint their own
  tier-1 submit steps — evaluate-and-stay-shown, flush-to-buffer-and-stay-shown — exactly the
  per-controller split already named in
  [`notes/enter_escape_routing.md`](notes/enter_escape_routing.md); their widget sessions are
  **truly persistent** (the session simply continues — state, content, cursor intact; no
  re-show involved). The re-`show()` idiom (spec §5) is the project-route minority path only,
  never the migration template. Least astonishment holds at the level users experience it:
  *within* a context submit always does the same thing; *across* contexts Enter has always
  meant different things (evaluate / pretty-print-replace / answer-the-prompt) — that
  difference is the routes' job, now explicit in route-owned tier-1 tables instead of
  flag-encoded in the widget. If a persistent project-route mode is ever genuinely needed, it
  is an **additive route-policy extension** (R9-adjacent: reserved, not built, not precluded).
- **Cursor/text control is widget-surface API** (R99): `get_cursor` / `set_cursor` /
  `set_text` / `configure` / `clear` under D-8's 2D `(line, col)` contract — FR-8/9/10.
  Contract detail in [`spec.md`](spec.md); ships as its own slice (currently M7).
  **Ephemerality does not idle this surface** (Gate-2 round-1): a session spans the whole
  composition — minutes, for `input_code`-style multiline entry. Its consumers: the live
  `highlighter` while composing (the `input_code` flagship case); validator-reject flows
  jumping the cursor to the error position (today's evaluate-fail path does exactly this);
  widget-output wiring such as `on_limit_reached` → `set_text`/`set_cursor` (history
  navigation — the console proof case, equally available to any project); draft restore
  (`show{text=…, cursor=…}`); and the console/editor migration as the heaviest future
  consumer (the editor's Escape load-selection *is* `set_text`). "Only for wrong inputs" would
  undersell it — error-jump is one consumer among several.

## §4 Run lifecycle and route connection

- **Run-end boundary = status quo, adopted as design constraint (ruled R5):** a run stays
  `'running'` while the project hooked `update`/`draw`; otherwise it drops to `'project_open'`
  when `main.lua` returns.
- **The project route (keyboard/text) is connected only while `'running'`** (ruling 3).
  **Scope precision (Stage-1 finding, binding):** the disconnect covers the keyboard/text
  slots **only** — pointer natives stay hooked until project stop. Pen-and-paper projects
  (`sapper`) remain pointer-playable in `'project_open'`; no example relies on keyboard/text
  handlers there (exhaustive census, revalidation §2). An implementor must NOT "unify" pointer
  disconnection in.
- **On project stop**: every slot restores to the framework default; project `handlers` tables
  and `on_*` callbacks reset to defaults; no project participant remains wired (doc A §6.4).
  If the widget is shown, it is silently hidden — no cancel chain (the project is gone and
  cannot observe one).
- **`inspect` is a mode→route line, nothing more (ruled R11):** inspect = the console route
  active, **bound over the project environment**; project route disconnected (ruling 3's
  shape); the project widget unhonoured because its owning route is inactive. This matches the
  current implementation exactly (`suspend()` restores all slots to console).

## §5 Legacy natives — pure wrap (ruled R7)

A project's native `love.keypressed` / `love.textinput` / `love.keyreleased` handlers
auto-provision as **plain tier-3 participants** in the project route's chain — no widget-aware
gating, no lifecycle-split, no custom logic. The chain treats them like any other participant
(truthy = consume, falsey = fall through to the sink).

Consequence (FR-6's letter, accepted): native handlers see events **while the widget is
shown**. The two examples with both natives and widget solicitation — **turtle** and **maze**
— change behaviour and are **migrated** under the SR1 break mandate ("only text fields
break"); per the ruling, breaking-and-fixing affected examples is *expected*, and preserving
their old behaviour would be effort burn. D-9's "zero example changes" clause is formally
lifted for these two. Pure-native projects (pong, life, paint, clock, keyboard) are unaffected
— their natives simply run as tier-3 participants with the widget never shown.

**Sequencing constraint (carried to the roadmap re-cut):** the behaviour change arrives with
the dispatch-chain slice, so turtle/maze migration must ride that slice or land immediately
adjacent — never deferred to the legacy-removal milestone, else an interim window ships
misbehaving examples.

## §6 The mutable/immutable API boundary (ruled R3)

The project-mutable dispatch surface is **exactly** the `handlers` per-event tables plus the
`on_*` callback fields. Everything else on `compy.input` is callable API, protected against
assignment (errors loudly — C2 warn-don't-swallow discipline applies to the error path).
Naming is tweakable post-implementation ("stakeholders need to see the implementation to feel
if it fits"); the boundary is not. Exact enumeration in [`spec.md`](spec.md) §7.

## §9 Deviations table

Departures introduced **in this derivation** (not mandated verbatim by a ruling or upstream
doc), each with its why — the Gate-2 review surface alongside §8:

| # | Deviation | Why | Risk if wrong |
|---|---|---|---|
| D-a | The framework **submit step invokes `on_text_entered(text)`** (sequence: `before_submit` → validator → deliver via `on_text_entered` → deactivate → `after_submit`) — composing R1's widget output with D-4's semantic chain. The **deactivate** step is **project-route policy**, not widget nature (§3) — console/editor mint their own middle steps at migration and keep their widgets shown | One submit sequence, not two competing notification paths (predictability meta-rule); the widget output is *what the submit step delivers through* | If the human intended `on_text_entered` fully independent of the D-4 chain, the spec §5 sequence needs reordering — semantics of each callback unchanged |
| D-b | Widget-output callbacks are **both** `show()`/`configure()` config keys **and** assignable `compy.input.on_*` fields — one underlying field, two ergonomics | R1 mandates the config path ("easy path"); R3's boundary already makes `on_*` fields mutable; two disjoint rule-sets would be a special case | Minor API-surface growth; retractable to config-only without touching the model |
| D-c | `on_text_entered(text)` — single argument, no `keys_pressed` | Widget outputs are not chain tiers, so the uniform-chain-signature rule does not bind them; submit-time modifiers are available via `before_submit(keys_pressed)`; pedagogical minimum (NFR-4) | Additive fix if needed (append an argument later — non-breaking for existing callers) |
| D-d | Combo tier on the **textinput** channel keys on `combo_string(text, keys_pressed)` (delivered text as the trigger token) | R2 mandates the uniform mechanism on every channel; `combo_string` needs a trigger token and text is the channel's trigger; Ctrl-chords never appear (channel caveat, marked in code per R4) | Rarely-used corner; mechanism-level, swappable without model change |

Nothing else in this doc departs from §0 or the cited upstream.

## §11 Salvage register — pre-E29 records that survive

Round-2 stakeholder rulings and settled records carried over from the old corpus (valid
inputs, independent of the removed semantics):

- **`keys_pressed` proxy widened** to read-indexable + iterable, writes blocked (round 2).
- **`show()` while active = no-op unless `force = true`**; `force` reconfigures in-place, no
  cancel chain; warn-on-suppression (round 2; doc A §6.6).
- **D-5 boundary reporting**: `on_limit_reached(direction, scope)` — both scopes, four
  directions (round 2).
- **`ProjectInputController` naming** (not `ProjectController`) — states the responsibility;
  avoids collision with `ProjectService`'s role (round 2).
- **Combo format**: modifier-first fixed precedence (ctrl, alt, shift, gui), l/r folded,
  `+`-joined; registration normalised on assignment; matcher = marked extension seam.
- **D-8 cursor contract**: 2D `(line, col)`, 1-based source-line coordinates.
- **Legacy-removal mapping table** (old spec §5): `input_text`/`input_code`/`validated_input`/
  `user_input`/`write_to_input` → their `compy.input.*` replacements.
- **C1/C2/C3 doc-rules** (semver-not-milestones; warn-don't-swallow; no milestone ids in
  tests) — in force ([`agents/process.md`](agents/process.md) §9.3).
- **Combo-tier repeat semantics**: provisional leaning (fresh-only at combo tiers;
  `on_key_pressed` sees repeats) — **not ruled**; owner constraint: existing combos keep
  current behaviour unless explicitly altered; settle near implementation (doc A §9).
