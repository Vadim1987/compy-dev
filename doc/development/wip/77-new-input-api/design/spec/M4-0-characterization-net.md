## Scope

Two coupled parts. The net cannot be written without the harness work — that coupling is the whole
reason M4-0 needs a spec, not a bare "generate tests" prompt (a prompt would hit the infra wall and
stub it, reproducing the overlay-test-vs-stub debt this strategy exists to kill).

| | |
|---|---|
| **Depends on** | M2 (stable singleton); the existing busted harness (`tests/mock.lua`, `tests/helpers/editor_session.lua`) |
| **Protects** | M4–M7 — each preserves observable behaviour *by contract*; the net is their guardrail |
| **Evolves at** | M8 — legacy globals removed, examples migrated; characterization baselines re-pinned |
| **Risk** | Medium-infra, low-design. The work is harness capability, not new feature logic. Chief trap: a synchronous harness baking in an event order the device doesn't honour (P1) → false-green. |

### Infra-feasibility verdict (the load-bearing question)

**Feasible — a modest harness-extension job at keypress granularity.** Traced in E9 against real code:

- **The base precedent is the raw-handler pattern, NOT `EditorSession`.** `tests/input/keys_pressed_spec.lua`
  already drives input at **keypress/keyrelease granularity through the *production* event slots**: it
  installs the real handler closures via `setup_callback_handlers` and calls
  `love.handlers.keypressed('s')` / `keyreleased('s')` directly — exactly the slot M4 rewrites, exactly
  the scale this feature lives at. **`EditorSession` is *not* the base**: its `press` is
  `function(...) controller:keypressed(...) end` (`editor_spec.lua:41`) — the *editor controller*'s
  method, bypassing `love.handlers`, driving block-navigation movement combos *above* single keystrokes.
  It is reused only for the editor block-nav coverage item, not as the harness.
- **All three production slots already exist.** `setup_callback_handlers` installs
  `love.handlers.keypressed` (`controller.lua:554`), `.textinput` (`:660`), `.keyreleased` (`:669`). So
  driving a full project input flow is "call the installed closures" — no new dispatch infra.
- **Narrow gaps:**
  1. **A keypress-level driver helper** on the raw-handler pattern (press / release / type / repeat over
     the installed `love.handlers.*` slots). Light — *not* an `EditorSession` generalisation.
  2. **`textinput` emission is unwired in the *mock*, though the handler exists.** `mock.keystroke`
     fires only `keypressed`; the repo's only textinput testing (`tests/editor/editor_spec.lua:136+`)
     calls `controller:textinput('x')` **directly** (A8 anti-pattern). The driver must drive the
     installed `love.handlers.textinput`, **order-independent** relative to keypressed (P1).
  3. **No `isrepeat` emission.** Harvest wrapper is `function(k)` — confirms E20's "incidental drop". The
     driver must emit a repeat.

## Part A — harness extension (keypress-level, on the production slots)

- **`tests/helpers/input_session.lua` (new)** — a small driver at **keypress/textinput/keyrelease
  granularity**, built on the `keys_pressed_spec` raw-handler pattern: install the real handlers via
  `setup_callback_handlers`, then drive `love.handlers.{keypressed,textinput,keyreleased}` (the slot M4
  rewrites). **Not** an `EditorSession` generalisation — that helper is editor-block-nav-specific and
  bypasses the love slots.
- **`tests/mock.lua` — extend:**
  - **textinput emission** — a way to emit a `textinput(t)` event, *independently orderable* relative to
    `keypressed` (so a test can assert the D-6 two-channel split without assuming sequencing — see P1).
    Either a new `mock.type(s, ...)` / `mock.textinput(t, ...)` sibling or a `keystroke` option; the
    contract is: **keypressed and textinput are separately injectable and order-independent.**
  - **`isrepeat` (+ `scancode`) emission** — `mock.keystroke` must be able to emit a *repeat* press
    (`keypressed(k, scancode, isrepeat=true)`) so the net can assert repeat handling.

## Part B — characterization coverage (behavioural, via the driver / real API)

All assertions go through the driver or the real `compy.input` surface — **never** asserting
implementation internals (this is the A8 [test-the-contract] correction). Captured **green against
current code** except the one forward assertion noted.

- **Example input flows:** tixy `input_code`, balloons `input_text`, turtle `input_text` + Esc dismiss,
  editor REPL submit.
- **`keyboard` example** (new-style, hand-rolled workaround for all four pains): pin what *survives*
  migration — auto-repeat debounce ("hit"/"knock" once-per-press), release-boundary staleness — the
  exact P1/P2 surface later milestones must keep working. Best characterization showcase.
- **editor `is_at_limit` vertical block-navigation** — **M6 rewrites `is_at_limit`** (horizontal + line
  scope); pin the existing vertical whole-input semantics now so M6 can't regress block-nav.
- **D-9 native coexistence** — `pong`'s `love.keypressed` still reaches the project after the M4 gate
  removal (the `ProjectInputController` lifecycle-split wrapper).
- **`maze`** — three migration surfaces in one: legacy `user_input()`/`input_text()` + `is_empty()`
  polling idiom (**M8** removal target), native `love.keypressed` indirection (**D-9**), manual
  edge-tracking + Shift-held modal + Shift+Enter multiline (`keys_pressed` replacement case).

### The one forward (red-until-fixed) assertion — `isrepeat` threading

Pure characterization captures *current* behaviour, and current behaviour **drops `isrepeat`**. The E20
regression-undo (thread `isrepeat` + `scancode` through the harvest wrapper, `controller.lua:554`) is a
**change**, landing in **M4** when `ProjectInputController` takes the slot. M4-0 therefore carries **one
Tier-2-style assertion** — *`isrepeat` reaches the keypressed path* — **red until M4 threads it**, then
green. This is the guardrail for the regression-undo; everything else in the net is green-now
characterization. Flagged explicitly so it is not mistaken for a broken baseline.

## Acceptance

- Harness can **drive a project input flow** through the real `love.keypressed`/`love.textinput` slots
  (a `ProjectSession`-style driver exists and is used by the net).
- Harness can emit **`textinput` independently of `keypressed`, in either order**, and can emit a
  **repeat** (`isrepeat=true`).
- The net **does not encode keypressed→textinput ordering as an invariant** (P1 — a synchronous harness
  must not go false-green on a sequence the device doesn't honour). One comment states order-independence
  is intentional.
- Characterization baselines for all listed flows/examples are **green against current code**.
- The `isrepeat`-arrives assertion is present and **red** (it flips green in M4); no other assertion is
  red against current code.

## Notes

- **Sizing (feeds E16/E11 recalc):** M4-0 ≈ *harness extension + characterization suite*. The extension
  is **modest** — the three production slots (`keypressed`/`textinput`/`keyreleased`) already exist via
  `setup_callback_handlers`, so the work is a keypress-level driver helper + two `mock` emitters
  (order-independent textinput, isrepeat), not new dispatch infra. Still larger than a prompt-only net
  (it's specced infra), but **smaller than an `EditorSession`-style session build**. Chief input to the
  E16 recalc; numbers owned by E16/E11.
- **Execution model:** M4-0 is itself a candidate for the test-first cheaper-model step — but the harness
  extension carries real design (driver shape, event-injection API), so it runs as a specced execution
  prompt, not a bare generation. It precedes the M4 implementation prompt.
