## The boundary to close

Neither `M2`'s `show({ force = true })` (re-applies only `text`) nor `M7.md`'s `configure()`
(live-updates `prompt`/`highlighter`/`validator`, **no-ops other fields while active**) lets a caller
re-target an **active** session's `result` sink or swap its **evaluator**. Today those are fixed at
`show()` for the session's lifetime. M7 builds the reconfiguration surface, so M7 is where this is
decided — one way or the other.

## Contract — decide and close (not "anticipate")

Make an **explicit decision** and implement it; do not leave the boundary open:

- **Option A — allow it.** Extend `configure()` (and/or `force`) so an active session's `result`
  sink and/or evaluator can be re-targeted, with tests for the live-switch. Choose this only if a
  real consumer needs it (M8 example migration is the place such a need would show up).
- **Option B — forbid it, deliberately.** Record that a session's `evaluator` and `result` are
  **fixed at `show()`** by design; `configure()`/`force` intentionally never change them while
  active (callers `hide()` then `show()` to re-target). Document the constraint where the
  `configure()` contract is described, and make sure `configure()`/`force` behaviour is consistent
  with it (no silent partial application that looks like a bug).

Default to **Option B** unless M7/M8 work surfaces a concrete need for A — it is the smaller, KISS
outcome and matches the current single-consumer model. The point of this slice is that the choice is
**made and written down**, closing the boundary, not that A is implemented.
