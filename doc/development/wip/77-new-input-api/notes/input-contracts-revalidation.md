### R4 — §3.1–3.3 keyboard EXCLUSIVE preserved; drop fixed
(confirms F-A). The *exactly-one-consumer* outcome
survives: after M4 the `ProjectInputController` becomes the
keypressed/textinput **slot occupant** (M4 "the singleton is
always the sink, never a routing destination"), and M5a's
`on_key_pressed` default **is** the text-editing sink — so a
key still reaches exactly one effective consumer. What changes
is the present *realization* that a running project's keys are
**dropped** while the widget is active; M4 routes them to the
project controller instead. The note frames this exactly right
in F-A — read §3.1–3.3 as "exactly one consumer," not as
"preserve project-key-drop." **Confirm F-A.**

One guard for the test rewrite: the note's EXCLUSIVE is
**per-event-type** (keypressed-consumers; textinput-consumers).
M5a/D-6's "two independent channels, no suppression" concerns
keypressed-vs-textinput (two *different* LÖVE events firing for
one character) — it does **not** weaken per-event EXCLUSIVE.
The M4-0-02 tests should assert EXCLUSIVE per event, not
conflate the channels.

### R5 — §4.6 "no cancel chain" superseded at m6 (confirms
F-D). M6 (D-4) introduces named `before_/after_` submit and
cancel chains; from _0.1.0-m6_ `hide()`/Escape **do** fire a
cancel chain, and Escape dismisses unconditionally. The
note's F-D fence ("stable-now-until-superseded, not
preserve-forever") is correct. The submit **outcome**
(successful submit deactivates the widget) is preserved; its
mechanism (pushed `userinput` event, `oneshot`) changes —
correctly on the mechanism side. **Confirm F-D.**

### R6 — §4.6 "force → text-only, other config ignored":
**missed bug-as-contract candidate** (not in the s26 seed).
The note pins, as a `[stable-now]` reset-semantics contract
(§2 + §4.6), that `show({force=true})` applies *only* the
`text` subset and **ignores other config**. The code does do
this today, with a comment deferring "a full live reconfigure"
to the m7 `compy.input` API (`userInputController.lua:241-243`).
But the design wording is in tension with it:
- **D-2** (status.md ledger + roadmap M2): "Block by default;
  `show({force=true})` **reconfigures**."
- **M7** adds `compy.input.configure()` as the live mid-run
  reconfigure path (prompt/highlighter/validator).

So "other config ignored on force" is plausibly a **limitation
the design intends to relax** (whether via a richer
`force=true` per D-2's words, or via `configure()` taking that
role), not a guarantee to keep forever. Pinning it unqualified
risks freezing a limitation — the same failure mode F-A/F-D
guard against elsewhere.
**Recommendation:** add a forward caveat to the §4.6 force
clause, parallel to F-D, e.g.:

> _[stable-now; reconfigure scope FORWARD]._ The "other config
> ignored on `force`" fact describes **today**. Live
> reconfiguration of `prompt`/`highlighter`/`validator` arrives
> as `compy.input.configure()` at _0.1.0-m7_ (M7, D-8/D-2);
> read "text-only on force" as a present limitation, not a
> preserve-forever contract.

Preserve-vs-revise is **UNCERTAIN** pending a design read of
whether `force=true` itself widens or `configure()` owns
reconfigure — flag to the orchestrator, do not pin either way.

### R7 — §5 forward-coverage scope (confirms the §6.1 seed
item). §5 enumerates only the M4/M5 forwards (5.1 project
sink, 5.2 named restore, 5.3 D-9 coexistence, 5.4 `isrepeat`).
It omits the M6/M7 outcomes the design introduces: named
submit/cancel chains (D-4), `compy.before_exit` (M6-02),
`on_limit_reached(direction, scope)` boundary callbacks (D-5),
and `set_text`/cursor/`configure`/`clear` (M7).
**Ruling: acceptable M4/M5 scoping for the note's immediate
job** (driving the M4-scoped contract-test rewrite) — *not* a
defect now. But the note is a "candidate to promote to
`internals/` at feature close," and a promoted contract record
that stops at M5 would be incomplete.
**Recommendation:** add one explicit scope line to §5 ("forward
set covers the _0.1.0-m4/m5_ horizon only; m6/m7 outcomes —
chains, `before_exit`, boundary callbacks, `set_text`/cursor —
are enumerated before `internals/` promotion"). Extend §5 at
promotion, not before M4 testing.

## Part C — §6.1 seed rulings

### (F-B) wheelmoved widget-bypass (§3.7) — **incidental /
accidental by-omission.** There is no `handlers.wheelmoved`
(grep confirms; inventory §1); wheel reaches only the slot
because the gateway never grew a wheel entry. The descriptive
notes treat wheel as a normal forwarded pointer event:
`design/notes/event_routing.md:319-324` lists `wheelmoved`
among events "forwarded to project-defined LÖVE2D handlers" and
then says "both receive **mouse events**" without carving wheel
out — i.e. nobody noticed the overlay never sees wheel (the
same omission as `user_input.md`, inventory §11.1). That is
evidence the bypass was **never designed**, not evidence of an
intended asymmetry. No M4–M8 milestone touches wheel, so it
persists by inaction.
**Ruling: incidental — preserve-by-inaction, don't enshrine.**
Keep §3.7 as a present-state fact but relabel it
"`[stable-now]`, incidental by-omission; intended shape is
symmetric (BOTH), so revise deliberately if/when wheel is
unified, do not pin as a guarantee." Agrees with the note's
F-B framing; sharpened from "unresolved" to "incidental."

### (F-C) `inspect` suppresses the widget (§3.4) —
**incidental mechanism; the OUTCOME is real and design-silent
— possible silent break.** The suppression lives entirely
inside `get_user_input()` (`controller.lua:20`: return nil
under `inspect`), whose sole job is to override the overlay
gate during inspect so REPL keys reach the console. M4
**removes that gate and `get_user_input`** — and **no M4–M8
spec mentions inspect-state routing or this suppression.**
- The *outcome* (during inspect, input reaches the console
  base sink, not a stale project widget) is genuine and worth
  preserving — REPL-against-halted-project depends on it.
- It is likely preserved *by construction*: suspend→inspect
  runs `save_user_handlers` + `set_default_handlers`
  (inventory §3), so the slot is console-owned during inspect
  regardless of a set `user_input`. Once the overlay gate is
  gone, slot ownership alone gives the same outcome.
- But the new `show()`/slot interaction during inspect is
  **unspecified** — if the post-gate model lets a shown widget
  re-occupy the keypressed slot, inspect keys could be grabbed.
**Ruling: incidental at mechanism level; keep §3.4 as a
`[stable-now]` *outcome* contract ("under inspect, keyboard/
text/pointer reach the console base sink, not the project
widget"), drop the mechanism-coupled framing, and add it to
the M4 verification checklist** as a silent-break vector. This
is the one §6.1 item I would not leave as "unresolved": the
outcome should be pinned, the mechanism let go.

### (F-E) within-event widget-then-sink ORDER (§3.5/§3.6) —
**incidental, not a guarantee.** The contract is that **both**
widget and base sink receive the pointer event; the
widget-first ordering is an artifact of the gateway calling
the overlay before the unconditional `love.*` slot call
(`controller.lua:692→695`, `:713→716`, `:729→732`). No
consumer depends on the widget seeing the event before the
sink — the widget's touch handlers are no-ops
(`userInputController.lua:614,625,636`) and mouse is used for
its own UI. Mouse/touch routing is untouched by the rewrite,
so the order persists incidentally.
**Ruling: incidental — do not pin "widget first" as a
guarantee.** §3.5 ("Order is widget-then-sink") and §3.8
("widget first") currently read as contracts; soften to
"(current realization: widget before sink; the *guarantee* is
that both receive it — order is incidental, not owed)."
Agrees with the note's F-E framing.

**Cross-event order correctly NOT pinned (confirmed).** The
note honours the E20/E9 ruling: the textinput-before-keypressed
cross-event order is **not** asserted anywhere as a contract
(§6.1 flags it only to say it is not pinned, "no event-order
guarantee owed"). I checked — no §3/§4 row pins it. Correct;
do not conflate with F-E's within-event point.
