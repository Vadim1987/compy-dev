## New finding this pass surfaced: `input-contracts.md`'s own keyreleased section is incomplete

Checked §3.3 of the corrected contract record against [[keyreleased-isrepeat-events]]'s traced
behavior. The doc characterizes **one** keyreleased gap correctly — the overlay-widget-diverts-the-
release case, analogous to keypressed/textinput's overlay gate. It says nothing about the
**separate, additional gap** this session traced independently: even with **no widget/overlay in
play at all**, `ConsoleController:keyreleased` has **no `app_state == 'editor'` fork** (unlike its
`keypressed`/`textinput` siblings), so a release **always** reaches console's own instance —
never editor's, never search's, regardless of which mode is actually active on screen. That's a
different mechanism (a missing fork inside `ConsoleController`, not the `get_user_input()` overlay
gate) producing a related-but-distinct symptom, and it survived:
1. The original implementation.
2. `prompt13`'s cold review (blessed the correction).
3. The independent Opus review (`reviews/M4-0-04.md`) — which *did* catch the missing editor-
   keypressed sibling test but not this.
4. This human review pass's own comment — which correctly senses "inconsistent" but frames it as
   the same widget-gate issue the doc already names, not the separate CC-internal fork gap.

Worth folding into `input-contracts.md` §3.3 before this is promoted to `internals/` — not urgent
for M4-0-04 itself (the doc is frozen/blessed and this task's own boundaries forbid editing it), but
flag it forward so it doesn't get silently lost.

## Is this overinvestment?

**On process volume: yes, most likely.** `input-contracts.md` is a ~750-line document, product of
at least three named editorial passes (s26, s27, prompt12) plus a cold revalidation, to establish
authoring ground rules for one milestone's *test-only* slice. The prompt itself demands a
two-filter methodology, four provenance-tagged buckets, mandatory perturb→red→restore "teeth"
proof, an outcome ledger, and an independent Opus review — and now a fourth, manual pass. The
artifact under all this ceremony is: `tests/` files, easily reverted, zero production blast radius.
Compare to `M4` itself (the actual behavior change this suite protects), whose own spec says *"Risk:
**Highest**. Gate removal touches the main dispatch path"* — the ceremony invested in the **safety
net** now measurably exceeds, in review-cycles, what's been invested in scoping **the change it's
guarding**.

**On underlying motivation: no — the need was real, and this session independently validates it.**
Every concrete thing this exercise was built to catch — the widget-presence-as-routing drift, the
pointer-BOTH artifact, the keyreleased inconsistency (twice over now), search's total absence from
the design's own awareness — turned out to be genuinely present when traced independently this
session, not imagined risk. A characterization net before touching a "Risk: Highest" dispatch path
is the right instinct.

**Recommendation:** stop adding review passes; triage what exists. Concretely, before another
full pass:
1. Apply the two already-known Opus-review fixes (small, mechanical, already-scoped).
2. Decide search explicitly — a `pending('search mode routes keys/text to the search widget')`
   naming the gap costs one line and closes the loop the M4-0-04 prompt's own "sibling coverage"
   instruction opened but didn't finish.
3. Relabel "held-key set lifecycle" as Bucket C or fold it into the existing MECHANISM-GUARD
   `describe`.
4. Add the one-line causality tightening to the pointer-selection test.
Everything else in the REVIEW list (doc-links, subgrouping, prose trimming) is real but cosmetic —
land it opportunistically, don't gate the milestone on it. The suite doesn't need to be perfect
before M4 lands; it needs to catch the surprises it was built for, which — per this review — it
mostly already does.

## Revision after human pushback (2026-07-01, same day): readability is not cosmetic here

**The human's correction:** the suite's scope is not "protect the M4 slice" — it's the safety net
for the **whole M4-and-onward implementation arc**, precisely because the current architecture is
tangled and full of canonical-but-undocumented behavior that's easy to break without noticing. Its
job is simultaneously to **document** these canonical behaviors and to **enforce** them, in a form
a human supervisor (dev team, architect, anyone) can actually verify. If the suite isn't legible,
nobody can confirm what it guarantees — which means it doesn't actually provide the guarantee it
exists for, no matter how methodologically rigorous its construction was.

**This overturns the "cosmetic, land opportunistically" framing above for the doc-link / prose /
subgrouping / jargon items.** Those aren't polish on top of a working artifact — they're the
artifact's actual success criterion, on par with correctness. Re-triaged with that lens:

- **The internal decision-ledger shorthand (`D-α`, `D-C`, `R1`–`R7`, `F-A`–`F-E`) leaking into test
  comments is the sharpest concrete instance of this.** The human's own reaction — *"'D-alpha',
  seriously?"* — is the tell: even the domain expert who commissioned this doesn't recognize the
  code without going back to the design-session ledger. These IDs are process artifacts of *how the
  contract record was produced* (which review pass raised which question); they carry zero meaning
  to a developer six months from now deciding whether a test failure is a real regression. They
  belong in `input-contracts.md`'s own provenance trail (where they already are), not repeated in
  test comments meant to explain *why this test exists* to a reader with no session history.
- **Mode-subgrouping (`describe('console mode', ...)` etc.) is not a style preference under this
  framing — it's a structural aid to the exact fear driving the suite.** A reader scanning
  `describe` blocks per mode would see at a glance whether editor/search/project all have parallel
  coverage; flat, mixed-mode `it` blocks are exactly the shape that let the missing
  editor-keypressed test and the missing search coverage go unnoticed through three prior review
  passes. Restructuring by mode doesn't just read better — it would have made both of those gaps
  visually obvious without needing a fourth review pass to catch them by hand.
- **Explaining keypressed vs. textinput inline** (one of the REVIEW comments): this session spent
  real effort establishing that split precisely ([[keypressed-vs-textinput]]) — worth two or three
  plain-English sentences in the suite itself (or a one-line pointer to
  `internals/user_input.md`/`notes/keypressed-vs-textinput.md`) rather than assuming the reader
  already has that model. Cheap, and directly serves "can a human verify what this tests."
- **§-id citations without a doc link** — same issue at smaller scale: `input-contracts.md` is 750
  lines; "§3.1" with no path means a verifying reader has to go hunt for it. A relative link costs
  nothing and is the difference between "traceable" and "traceable in theory."

**Revised recommendation:** don't sequence this as "fix the two known bugs, then stop." Treat
legibility as its own pass, with its own bar to clear — specifically: **could a developer or
architect with no memory of this design process read the suite and correctly state what each
`describe` block guarantees and why?** Concretely, in rough priority:
1. Apply the two already-known Opus-review fixes (unchanged from above — still real, still small).
2. Strip session-internal IDs (`D-α`, `R1`–`R7`, `F-A`–`F-E`) from test comments; replace with
   plain-language rationale + a doc-linked citation (`-- see notes/input-contracts.md §3.1`).
3. Restructure into per-mode `describe` nesting where the suite currently mixes modes in one flat
   block — this is the change most likely to make coverage gaps self-evident on sight, which is the
   whole point.
4. Decide search explicitly (still open, still one line) — subgrouping by mode from (3) would
   surface this gap visually even before someone writes the fix.
5. Add the short keypressed-vs-textinput explainer once, near the top, rather than re-explaining
   per test.
6. Relabel "held-key set lifecycle" as mechanism (still valid, unchanged).

This is a bigger lift than "ship the two fixes" — and that's the correct size for a document meant
to carry trust across an entire M4–M8 arc, not a one-milestone test-only patch. The original
"overinvestment" framing measured cost against *this commit's* blast radius; measured against the
suite's actual job — being the durable, human-checkable record of canonical behavior for everyone
who touches input handling from here through M8 — the legibility work is not excess, it's the part
that was still missing.
