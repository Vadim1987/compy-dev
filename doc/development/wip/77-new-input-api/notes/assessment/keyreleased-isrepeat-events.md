# keyreleased routing, isrepeat, text assembly, and the 'userinput' event

_Generated by LLM (Claude Sonnet 5): 2026-07-01; Approved by human?: NOT YET;_

Follow-on to [[keypressed-vs-textinput]] and [[shared-input-widget-singleton]]. Four separate
questions, answered by direct code inspection (no `src/` changes): does anything assemble
press+release into a "keystroke"? Is `isrepeat` considered or ignored, and by whom? Does
`on_text_entered` (a design-planned callback) already exist? How is a submitted line actually
assembled — live character-by-character mutation, or replay of a keystroke log — and what role do
"events" play, given access to them seemed to differ by mode?

## 1. Nothing assembles press+release into a keystroke

`Controller.keys_pressed` (`controller.lua:554-558,669-675`) is the only press/release pairing in
the codebase: a live `{keyname → true}` set, added-to on `keypressed`, removed-from on
`keyreleased`. It is **not currently consumed by anything** — `Key.ctrl()`/`shift()`/`alt()`
(`util/key.lua:33-52`) query `love.keyboard.isDown()` directly, bypassing it entirely. Grepping the
whole tree for `keys_pressed`/`combo_string` outside `controller.lua` itself returns only two
`DEFERRED` comments in `userInputController.lua` — it's infrastructure laid down ahead of the
combo-dispatch work (`design/design.md` §3, "behaviour-neutral", 0.1.0-m1), inert today.

There is no click/hold-duration/debounce timer for keyboard anywhere (contrast with mouse's
`click_count`/`click_timer` single/double-click assembly, `user_input.md`'s "Framework-level click
handling"). `keyreleased` is used for exactly two narrow, independent jobs (see §2) — never paired
back up with the originating `keypressed` beyond that.

## 2. `keyreleased` routing has a real gap (currently inert, still worth flagging)

`keypressed`/`textinput` get careful three-way routing (console / editor / project, established in
[[keypressed-vs-textinput]]). `keyreleased` does not:

- `handlers.keyreleased` (`controller.lua:669-682`) checks the project overlay first, same as the
  other two channels — consistent so far.
- Otherwise it falls to `love.keyreleased` = `CC:keyreleased` = `ConsoleController:keyreleased`
  (`consoleController.lua:1090-1093`):
  ```lua
  function ConsoleController:keyreleased(k)
    self.input:keyreleased(k)
    self.input:update_view()
  end
  ```
  **No `if love.state.app_state == 'editor' then self.editor:keyreleased(k) ...` fork** — unlike
  every other handler on this controller. `EditorController` and `SearchController` don't define a
  `:keyreleased` method at all — grepped, zero hits.
- Net effect: editor's and search's own `UserInputController` instances **never** receive
  `keyreleased`, ever, regardless of which mode is actually live on screen. Only console's (possibly
  backgrounded) instance ever sees it.

**Is this observable?** Checked `UserInputController:keyreleased` (`userInputController.lua:501-519`)
— its only two behaviors are: release character-selection on Shift-release, and clear an error on
Space-release. Neither currently bites:
- Editor's and search's own instances both construct with `disable_selection = true`
  (`editorController.lua:12,16`), so the selection-release job is moot for them regardless of
  routing.
- Their error state is also clearable via **any** `textinput` character, unconditionally
  (`editorController.lua:291-292`, mirrors console's own `consoleController.lua:1001-1002`) — and
  Space is itself a text-producing key, so pressing Space while erred clears it via the `textinput`
  channel even though the `keyreleased` channel never reaches that instance.

So the gap is currently **inert, not silently broken** — but it's a genuine asymmetry against the
otherwise carefully mirrored keypressed/textinput routing, worth keeping in mind if either job
(selection-release semantics, or the error-clear key set) changes for editor/search in the future,
since `keyreleased` would silently not participate.

## 3. `isrepeat` is stripped at the very first hop, not chosen to be ignored downstream

None of console/editor/search/project *decide* to ignore repeats — they never get the chance.
LÖVE calls its `keypressed` slot with `(key, scancode, isrepeat)`. Compy's outermost override,
`love.handlers.keypressed = function(k)` (`controller.lua:554`) — a single-parameter function —
discards `scancode`/`isrepeat` right there, before `love.keypressed` (=`CC:keypressed`) or any mode
fork runs. Grepped `isrepeat`/`scancode` across `src/`: the only hits are the two names themselves
in this one function signature area and doc comments — no consumer anywhere reads either value
today. This exactly matches `notes/stakeholder-3-input/assessment.md`'s P2 finding
("the harvest wrapper is literally `handlers.keypressed = function(k)` ... no comment, no
rationale") — confirmed here independently by reading the code path end to end. Threading
`isrepeat` back through is planned (M4/M5), not yet done.

## 4. `on_text_entered` / `on_key_pressed` / etc. don't exist yet — confirmed, not assumed

Grepped `src/` for every design-planned callback name (`on_text_entered`, `on_key_pressed`,
`before_submit`, `after_submit`, `before_cancel`, `after_cancel`, `on_limit_reached`): **zero
matches.** `compy.input` today (`consoleController.lua:347-358`, `get_compy_input`) exposes only
`show`/`hide` — nothing else, not even as stubs. So there is currently no "assembly" happening at
that layer either, because that layer doesn't exist yet; all four current consumers (console,
editor, search, project) still do their own if-chain-style handling, exactly as
[[shared-input-widget-singleton]] described for the console/editor follow-on.

## 5. How a submitted line is actually assembled

No consumer buffers a keystroke log and replays it at Enter. `textinput` mutates the model's
persistent text immediately and continuously — `UserInputModel:add_text` inserts each character as
its event arrives (`userInputController.lua:488-498`, `editorController.lua:287-302`,
`searchController.lua:143-145`). Enter (`keypressed`, not `textinput`) is a purely discrete control
signal, handled by each owning controller's own submit path
(`ConsoleController:evaluate_input`, `EditorController:_handle_submit`, or the generic
`UserInputController:keypressed`'s `submit()` local for the project overlay, gated by `oneshot` —
see §6) — each one reads `get_text()` (the model's *current* state) at the moment Enter fires and
runs the evaluator against that. The live model state **is** the submission; there's nothing else
to assemble. Search is the odd one out: it has no evaluator at all (`nil`, `searchModel.lua`
construction) — its Enter jumps to the currently-**selected result**, unrelated to replaying the
typed query text.

## 6. `oneshot` and the `'userinput'` event — the only pub/sub-like mechanism in this code, and it's narrowly scoped

`oneshot` is a `UserInputModel` constructor flag, `true` **only** for the one project singleton
(`main.lua:363`); console (`consoleModel.lua:15`), editor's main input (`editorModel.lua:14`), and
search (`searchModel.lua:31`) all construct with it false/omitted. It gates two things inside the
generic `UserInputController:keypressed`/`UserInputModel:handle`:

1. **Auto-submit-on-Enter** inside the *generic* sink (`userInputController.lua:438-454`) — this is
   *why* the project overlay needs no owning controller to submit for it, while console/editor each
   implement their own separate Enter-handling instead of relying on this path.
2. **The `'userinput'` LÖVE custom event** (`userInputModel.lua:803-821`): after a successful
   evaluate, `if self.oneshot then love.event.push('userinput') end`. `love.event.push` *queues*
   rather than acting synchronously, so the current frame's `love.update()` still observes
   `r:is_empty() == false` before anything tears down. Next tick, LÖVE dispatches it to
   `love.handlers.userinput` (`controller.lua:737-742`), whose entire body is: if the overlay is
   still active, clear it (`love.state.user_input = nil` — identical to calling `hide()`). That's
   the whole mechanism by which the overlay auto-dismisses itself one tick after a successful
   project-overlay submit.

**This answers the "events are limited by mode" observation directly**: it's not that access to
this event is *restricted* per mode — it's that **only the project-overlay path ever engages with
it at all**. Console and editor never construct `oneshot=true`, so they never push `'userinput'`
and have no equivalent auto-hide (unsurprising — they aren't `show()`/`hide()` lifecycle objects to
begin with). There is no other event bus, signal, or callback dispatch mechanism in the current
input code beyond this one hardwired, single-purpose push — everything else planned (`handlers`,
`on_key_pressed`, `on_text_entered`, `before/after_submit`, `before/after_cancel`,
`on_limit_reached`) is still just design vocabulary (§4).
