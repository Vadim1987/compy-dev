# Should console/editor/search share ONE reconfigurable UserInputController?

_Generated by LLM (Claude Sonnet 5): 2026-07-01; Approved by human?: NOT YET;_

Follow-on to [[keypressed-vs-textinput]]. That note established there are (at least) four
independent `UserInputController` instances in the current code: console's own (`consoleController.lua:44`),
editor's own main input (`editorController.lua:12`), editor's nested **search** sub-widget's own
(`editorController.lua:16`), and — after #77 — the project-overlay singleton
(`design.md:174-181`). The question raised: since at most one of these is ever the "live" widget
on screen at a time, would collapsing all four into one reconfigurable singleton (generalizing
what #77 already does for the project overlay) be architecturally better than four objects doing
the same job?

## The invariant holds, and is worth stating precisely

At any given moment, at most one of the four is receiving `keypressed`/`textinput`:

- Console's own input is live whenever `app_state ~= 'editor'` and `cfg.mode ~= 'play'`
  (`consoleController.lua:994-1010,1013-1087`).
- Editor's main input is live only in `app_state == 'editor'` **and** `EditorController.mode ==
  'edit'` (`editorController.lua:287-302,809-828`).
- Editor's search input is live only in `app_state == 'editor'` **and** `mode == 'search'` — same
  gate, different branch.
- The project singleton is live only while `love.state.user_input` is set, which (per
  `design.md:196-201`) is scoped to `app_state = 'running'`/`'project_open'` — states where
  console's own input and editor are both inactive by construction.

So the four are indeed mutually exclusive occupants of one visual/interaction slot, not four
things competing for it.

## What that separation currently buys for free — verified, not assumed

I checked whether switching contexts today explicitly saves/restores the inactive widget's state,
or whether it's simply untouched:

- `ConsoleController:edit()` (`consoleController.lua:939-968`) and `:finish_edit()`
  (`:976-988`) — the console→editor round trip — never read or write `self.input` (console's
  own instance). The in-progress REPL draft (text, cursor, history position) just sits there,
  unreachable while `app_state == 'editor'`, and is exactly as the user left it on return.
- `EditorController:_search_mode_keys` (`editorController.lua:485-503`) — the edit→search round
  trip — never touches `self.input` (editor's main instance) either; entering/leaving search only
  calls `self.search:clear()`/`set_mode(...)`.

**This is instance-separation doing implicit state-preservation work, at zero code cost.** Nothing
explicitly stashes or restores per-context state today — it's simply that the untouched instance
isn't in the call path while another context is active.

## What a merge would have to reproduce

Collapsing to one object turns that free property into an obligation. A single reconfigurable
`UserInputController` would need an explicit save/restore (or a small context stack) of, per
logical slot: text buffer, cursor, selection, evaluator/validator, history (console only),
`oneshot`/`disable_selection` flags, and error state — on every `show()`/`configure()`-style
context switch, so that returning to console after a trip through the editor resumes the exact
prior draft rather than whatever the editor left in the shared buffer.

This is a **harder problem than the one #77 already solved** for the project singleton: that
singleton has exactly one occupant type (the project's own overlay calls), so `show()`/`hide()`
never has to hand back a *different* prior context's state — there's nothing else to resume. A
console/editor/search-inclusive singleton would be multiplexing four distinct, independently
stateful roles through one object, not just persisting one role across activations.

## Relation to owner intent and the named follow-on

`design/notes/input.md`'s owner clarification (item 1) explicitly wants unification: *"what I
would like to see is an API that allows for an easy implementation of interfaces that are similar
to either the command console or the editor. Ideally, these should also be re-implemented using
the same API."* — real, standing support for convergence.

But the **currently drafted** follow-on (`design.md:415-423`) is narrower than instance-merging:
*"it replaces if-chains in `ConsoleController` and `EditorController` with handler registrations;
the underlying methods ... are unchanged."* That's API-surface parity (`compy.input.handlers[combo]`
style dispatch instead of if-chains) — it says nothing about the four instances becoming one, and
its own FR-12 walkthrough (`design.md:441-451`) stops at "Ctrl+F → mode-switch handler," never
addressing what search's *own* instance does once inside. A literal shared singleton would be a
further step beyond what's currently drafted, not something the existing follow-on text already
implies.

## Relation to the stakeholder-3 pains — orthogonal, confirmed

Checked `notes/stakeholder-3-input/compy-input-quirks.md` and `assessment.md` (the four pains: P1
event order, P2 stripped `isrepeat`, P3 chord/textinput suppression, P4 no exit-cleanup hook) —
none of them bear on this question in either direction. All four are about the semantics of events
as delivered **to project game code** running under `ProjectInputController`; they say nothing
about how the framework's own console/editor/search widgets share (or don't share) an instance.
Merging or not merging changes none of P1–P4's analysis or fixes. Same for `design/notes/input.md`
and `stakeholder2_structured.md` beyond the one unification wish quoted above — neither discusses
instance topology.

## Verdict

Architecturally appealing and consonant with stated owner intent, but it is a **distinct, harder
design question** than either (a) the console/editor migration follow-on as currently drafted, or
(b) anything #77 itself needs to decide. It should be flagged explicitly for whoever scopes that
follow-on — including, per [[keypressed-vs-textinput]], the previously-unaddressed question of
what happens to editor's nested search sub-widget — rather than assumed to fall out of "migrate
console/editor to the same API" for free. The real cost center, if pursued, is designing the
save/restore (or context-stack) mechanism that today's four-instance separation gets for nothing.
