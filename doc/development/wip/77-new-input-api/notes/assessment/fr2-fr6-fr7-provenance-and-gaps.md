## Provenance: FR-2 — the *need* is rooted, the *word* "teardown" isn't, and the *resolution* was never re-confirmed

Three separate things get conflated under "FR-2/teardown," worth pulling apart:

1. **The underlying need is stakeholder-rooted**, same source, same item:
   > "Calls should be provided for setting up an edit area (with an optional initial text, cursor
   > position, highlighter and verifier) and **for removing the edit area**, for querying and
   > changing the cursor's position, and changing the text."

   And separately, item 2 raises hide/show as its own distinct pain point ("it is not easy to hide
   or show the input area"). So the *ticket itself* asks for two different things: something called
   "removing," and something called hide/show — not one thing wearing two names.

2. **The word "teardown" is not in the verbatim record at all** — grepped `input.md`, zero matches.
   It first appears in the *design-process* vocabulary (`decisions.md`, `spec.md`,
   `decisions-record.md`), used for a **different** concept: the framework's own internal, always-run
   cancel/submit structural step (`design/notes/decisions.md:443-487`, "the framework's teardown
   runs..."). It's specifically **this** usage, inside the D-4 question, that stakeholder2 found
   opaque (`stakeholder2_structured.md:54`, `"I'm not sure what's meant here by 'the framework's own
   teardown'"`) — a D-4 (submit/cancel notification) confusion, not an FR-2 one. The human's memory
   of "S2 asking what teardown is" is accurate, but it points at the wrong place — not at FR-2.

3. **FR-2's actual resolution was reinterpreted mid-design, and I can't find a stakeholder
   re-confirmation of it.** The early architecture-assessment artifact (`design/context.md:95,341`,
   which is the "reconstruct + correlate" step per `design/notes/requirements.md:19-31`'s stated
   process) gap-analyzed FR-2 as needing **"a project-callable remove path"** — a literal function.
   The later, final resolution (`design/notes/decisions-record.md:107-114`) instead declares:
   *"The overlay input widget becomes persistent (addresses FR-1, FR-2, FR-3, FR-4, NFR-1)... Projects
   call `show`, `hide`, and `configure` on it rather than creating it."* — i.e., FR-2 got folded into
   `hide()` + persistence, with **no separate `remove()`** ever built (confirmed: `design.md`'s
   `compy` API table has `show`/`hide`/`configure`/`clear`/`set_text`/`get_cursor`/`set_cursor` —
   no `remove`). I checked every stakeholder round in the record (SR1, SR2, SR3) for an explicit
   "yes, hide-without-remove is enough" — **found none.** SR2's D-2 discussion is about
   `show()`-while-active blocking, not about whether `hide()` alone satisfies "removing." So: the
   human's instinct — *"I believe stakeholders would be absolutely happy about just
   hiding/showing... but no more than that"* — may well be correct in outcome, but as far as the
   visible record goes, that's an **assumption riding on the persistence redesign**, not something
   any stakeholder round explicitly signed off on. Worth flagging before treating it as settled.

**What would "teardown" even mean now, given the persistent-singleton design?** With the widget
never destroyed, there's no object-lifecycle event left to call "remove." The most coherent reading
left is: (a) `hide()` for visibility, plus (b) releasing the *project's own* registered surface —
`compy.input.handlers`, callbacks, etc. — which the design already plans to happen automatically on
project stop (`design/design.md:209-214`, `stop_project_run`/`clear_user_handlers`), not as a
project-callable "remove." That's plausibly *why* no separate `remove()` exists in the plan — but
again, that reasoning is mine, constructed after the fact from the persistence decision, not
something I found stated as the resolution's own rationale anywhere in the record.

## Design question: is `show(force)`'s narrow (text-only) scope well-reasoned? Is there a "full rewire" path?

There already is one, and it isn't `show(force)` — it's three separate, already-planned, independently
callable functions: `compy.input.configure(config)` (highlighter/validator/label — explicitly
**not** text, per `design.md:234`: "exception to `configure()`'s text-immutability"),
`compy.input.set_text(text, keep_cursor)` (content), and `compy.input.set_cursor(line, col)`
(position) — each meant to be live-callable on an *already-active* widget, with no `force` flag at
all (they aren't gated by the `show()`-while-active guard in the first place — that guard is
specific to `show()`). So "completely rewire an active widget" = call `configure()` +
`set_text()` + `set_cursor()` together, not a single big-bang method. `show(force)`'s own scope
(text-only) reads less like a deliberate design choice about *what a full reconfigure should cover*
and more like a narrow, single-purpose escape hatch for one case: re-triggering an already-active
session with fresh initial text, kept deliberately thin because the *real* general reconfigure
surface is those three other calls. The code comment agrees: `userInputController.lua:241-243`,
*"a full live reconfigure is the compy.input API arriving in 0.1.0-m7... other fields are ignored
here by design."*

**Possible redundancy worth flagging, not resolving here:** once `set_text()` exists as its own
top-level call, does `show({force=true, text=...})` still need to patch text at all? Both would do
almost the same thing (replace content on an active widget) through two different entry points.
Not urgent — `set_text` isn't built yet either — but worth someone deciding when M7 is scoped,
rather than shipping both without noticing the overlap.

## FR-6 — current-state gap, precisely: keyboard is exclusive, mouse never was

`concerns.md`'s framing ("keypressed events are fully consumed... no mechanism to receive key
events the widget did not handle") undersells how total the current exclusion is. Traced
`controller.lua`'s `handlers.keypressed`/`handlers.textinput` exactly:

```lua
local user_input = get_user_input()
if user_input then
  user_input.C:keypressed(k)          -- overlay gets it
else
  if love.keypressed then return love.keypressed(k) end   -- project gets it
end
```

This is **not** "unconsumed events get dropped" — it's binary and total: while the overlay is
active, the project's own `love.keypressed`/`love.textinput` are **never called at all**, consumed
or not; while it's inactive, the project gets 100% with no widget in the way. There is no
in-between today, which matches `design.md:79-83`'s own framing of "the overlay gate."

**Mouse never had this problem — confirmed, not assumed.** `handlers.mousepressed`/
`mousereleased` (`controller.lua:689-719`) call the overlay conditionally, but call
`love.mousepressed`/`mousereleased` (the project's own handler) **unconditionally**, outside the
`if user_input` branch entirely:
```lua
local user_input = get_user_input()
if user_input then user_input.C:mousepressed(...) end
if love.mousepressed then return love.mousepressed(...) end   -- always runs
```
Both get every mouse event, always. This is exactly why `design.md`'s scope note that touch/mouse
"needs no separate work" (already covered by existing mouse handlers) holds up — mouse was never
gated the way keyboard was, so there's nothing to fix there; FR-6 is a keyboard-only gap.

## FR-7 — the signal already exists and already propagates through *most* of the stack; it's dropped at exactly one point

Traced the boundary-hit ("limit") signal end to end. `UserInputModel:cursor_vertical_move(dir)`
(`userInputModel.lua:585-670`) returns `true` when the cursor is already on the first/last line and
can't move further in that direction. That return value threads through `vertical()`'s local in
`UserInputController:keypressed`, and the **function itself returns it** (`return ret`,
`userInputController.lua:481-482`) — from *both* the editor-mode and non-editor branches of its own
internal `app_state` fork, so the signal is available at every call site.

Who actually reads it:
- **Console** (`consoleController.lua:1058-1066`): `local limit = input:keypressed(k); if limit
  then ... history_back()/history_fwd() ... end` — captures it, uses it for history navigation.
- **Editor** (`editorController.lua:803-805`): `if passthrough then input:keypressed(k) end` — a
  **bare call**, return value discarded. Editor doesn't need it — it computes boundary state
  independently via `inputView:is_at_limit('up'/'down')` at the top of `_normal_mode_keys`
  (its own view-level check, a *third* mechanism alongside the model's `is_at_limit`
  and `cursor_vertical_move`'s inline `limit`) — another instance of the "each mode reinvented its
  own way" pattern from [[cursor-and-reset-operations]] §5/§7.
- **Project overlay** (`controller.lua`'s `handlers.keypressed`): `user_input.C:keypressed(k)` — also
  a **bare call**, return value discarded, and there is no `on_limit_reached` callback to hand it to
  even if it weren't. This is the one point that matters for FR-6/FR-7: the signal is computed, and
  the plumbing to carry it out of `UserInputController:keypressed` already exists — it's dropped at
  the **project dispatch site specifically**, exactly matching `context.md:345`'s own gap-analysis
  line: *"FR-7 | Signal exists internally, discarded at overlay dispatch | Small — needs threading
  through the dispatch."* Confirmed accurate, precisely, down to the exact call site.
