# Console/editor keypressed vs textinput — how they route and divide labor

_Generated by LLM (Claude Sonnet 5): 2026-07-01; Approved by human?: NOT YET;_

Research note from a code-inspection session (no `src/` changes). Triggered by orientation
reading for the `M4-0-04` review
([`implementation/reviews/M4-0-04.md`](../implementation/reviews/M4-0-04.md)), which flags that
the editor route has **zero** `keypressed` regression coverage despite a claim otherwise (its
Finding 1). This note answers the two follow-up questions the review raised: *do console/editor
actually use `keypressed`/`textinput` at all, and if so, how do they split the work between them.*
It complements — doesn't replace — [`internals/user_input.md`](../../../internals/user_input.md),
which has now been corrected in the two places this note's findings touch (see "Doc fix" below).

## Do console and editor listen to keypressed/textinput?

Yes, both — directly, and both rely on them heavily; neither is vestigial.

## Routing chain (top-down)

1. `love.handlers.keypressed`/`textinput` (`controller.lua:554,660`) is the true native LÖVE
   entry point. It runs global power-shortcuts first (quickswitch, restart, profiler,
   project-state-change), then checks for an active **project** input request
   (`love.state.user_input`). If one exists, that wins EXCLUSIVELY
   (`user_input.C:keypressed(k)`).
2. Otherwise it falls through to `love.keypressed`/`love.textinput`, bound by
   `controller.lua:187-237` (`set_love_keypressed`/`set_love_textinput`) to
   `CC:keypressed`/`CC:textinput` — i.e. `ConsoleController`.
3. `ConsoleController:keypressed`/`:textinput` (`consoleController.lua:994,1013`) is the
   console/editor fork: `if love.state.app_state == 'editor' then self.editor:keypressed(k) /
   :textinput(t) else <console handling> end`.

**Console mode** (the `else` branch) does history nav (PageUp/PageDown), the terminal-test state
machine, Ctrl+L clear, Enter→evaluate directly, then forwards to `self.input:keypressed/:textinput`
— a `UserInputController` instance (`consoleController.lua:44`). Disabled entirely when
`cfg.mode == 'play'`.

**Editor mode** (`self.editor`, an `EditorController`): `textinput`
(`editorController.lua:287`) forwards to its own `UserInputController` (`editorController.lua:12`)
in `mode == 'edit'`, or to `self.search:textinput` in `mode == 'search'`. `keypressed`
(`editorController.lua:809`) is richer: Ctrl+M/Ctrl+F switch mode, then dispatch to
`_reorg_mode_keys`/`_search_mode_keys`/`_normal_mode_keys`. `_normal_mode_keys` handles
scroll/copy/cut/paste/navigate/delete/submit/load/clear directly and only passes the key through
to `self.input:keypressed` if nothing consumed it (`passthrough` flag,
`editorController.lua:803-805`). `_search_mode_keys` forwards to `self.search:keypressed` (a
`SearchController`, itself wrapping another `UserInputController`).

All three routes (console, editor-edit, editor-search) bottom out in the same
`UserInputController` primitive, just wrapped with different mode-specific logic on top.

## Does keypressed carry textual input, or only control input?

Both LÖVE2D and compy give partial answers here — worth keeping separate:

- **LÖVE2D-guaranteed:** `love.textinput` fires only for keys that produce OS-processed character
  output (IME/layout aware). `love.keypressed` is **not** selective — it fires for every physical
  key, textual or not. Pressing `q` fires both `keypressed('q')` and `textinput('q')`.
- **compy's own convention (not platform-enforced):** `keypressed` handlers never treat `k` as
  insertable text. `UserInputController:keypressed` (`userInputController.lua:275-483`) only
  matches `k` against a fixed set of named control keycodes (`"backspace"`, `"up"`, `"left"`,
  `"escape"`, …) or modifier+letter shortcuts (Ctrl+C/V/X/Y/D — copy/paste/cut/delete-line/dup-line,
  not insertion). A bare `keypressed('q')` with no modifier matches nothing and falls through
  untouched — there's no explicit "ignore textual key" guard, it's an absence of a matching branch.
  All literal character insertion (`UserInputModel:add_text`) is reachable only from `textinput`
  handlers (`userInputController.lua:488`, `editorController.lua:287-302`,
  `searchController.lua:143`), plus two `keypressed`-triggered paths that insert **existing**
  content, not the pressed key: clipboard paste (Ctrl+V) and `load_selection` (Escape in editor
  mode, loads buffer text into input) — neither derives its text from `k`.

This holds uniformly across console, editor-edit, and editor-search — none of the three deviates.

## Doc fix

`internals/user_input.md` previously stated the LÖVE2D-side claim imprecisely (implying
`keypressed` was itself restricted to non-character keys) and carried an open owner-question
flagging doubt about exactly this ("there's evidence that KP *is* fired for character-keys too").
That doubt was correct. Corrected in place (`internals/user_input.md`, "Text Input Widget" section
and the "UserInputController keypressed (shared)" section) — the resolved fact plus the
LÖVE2D-vs-compy-convention distinction are now folded into the doc directly rather than left as an
open question.

## Relevance to M4-0-04

This confirms the review's Finding 1 concern is structural, not cosmetic: editor `keypressed` and
`textinput` are functionally disjoint code paths (control-channel vs character-channel), so
`textinput`-only editor coverage cannot stand in for `keypressed` coverage — the missing editor
keypressed-EXCLUSIVE test leaves the *entire* editor control surface (backspace, arrows,
Ctrl-shortcuts, mode switches) with no regression protection.
