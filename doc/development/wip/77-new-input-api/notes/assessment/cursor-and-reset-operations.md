# Cursor manipulation and "reset" across console/editor/search/project

_Generated by LLM (Claude Sonnet 5): 2026-07-01; Approved by human?: NOT YET;_

Follow-on to [[keypressed-vs-textinput]], [[shared-input-widget-singleton]], and
[[keyreleased-isrepeat-events]]. Asked in the context of two concrete stakeholder-driven
requirements: **FR-8/FR-9** (get/set cursor position, explicitly requested by the stakeholder —
`design/requirements.md:105-109`) and the **balloons dynamic-prompt-reset pain** (architect-surfaced,
`design/notes/requirements.md:46-64` / `design/notes/concerns.md:28-42`: no way to relabel or reset
an already-active edit area's content+cursor without a full teardown). Investigated with the
`lua-lsp` MCP server this time (see side-note at the end) alongside direct reads.

## 1. The cursor API has three layers today, and they don't line up

- **Model** (`UserInputModel`, `userInputModel.lua`): the full primitive surface —
  `cursor_left`/`cursor_right`, `cursor_vertical_move`, `move_cursor(y, x, selection)`,
  `jump_home`/`jump_end`/`jump_line_start`/`jump_line_end`, `get_cursor_pos`/`get_cursor_x`/
  `get_cursor_y`/`get_cursor_info`, `set_cursor(c)`. These are invoked **internally**, by the
  model's own `keypressed` local functions (`horizontal()`/`vertical()`), in direct response to
  arrow/Home/End keys — nothing external calls most of them.
- **Controller** (`UserInputController`, `userInputController.lua:108-159`): a **narrower**
  passthrough — only `get_cursor_info`, `get_cursor_pos`, `set_cursor`, `jump_home`. No wrapper for
  `jump_end`, `cursor_left`/`right`, or `move_cursor` — those stay model-internal, unreachable from
  outside without reaching past the controller into `self.input.model` directly.
- **`compy` (project-facing)**: **nothing.** `get_compy_input()` (`consoleController.lua:347-358`)
  exposes only `show`/`hide`. FR-8/FR-9 don't exist in the API surface at all yet — confirmed by
  grep, zero `get_cursor`/`set_cursor` under `compy.*` anywhere in `src/`.

## 2. Two call sites do programmatic (non-keypress) cursor manipulation today — corrected

**Correction (caught in review by the human, who remembered implementing this):** an earlier pass
of this note claimed editor's `load_selection` was the *only* site. Wrong — missed a second one on
the same submit path. Checked again, precisely, by grep for every `move_cursor`/`set_cursor` call
site: there are **two**, both in `editorController.lua`, both live and wired up (not dead code):

1. **`load_selection`** (`editorController.lua:590-604`, Escape/Shift+Escape in edit mode) — goes
   through the **controller** API:
   ```lua
   if add then
     local c = input:get_cursor_info().cursor
     input:add_text(t)
     input:set_cursor(c)          -- restore caret after inserting at point
   else
     input:set_text(t)
     input:jump_home()            -- fresh load, no caret to preserve
   end
   ```
2. **`reject_oversized`** (`editorController.lua:628-633`), called from both `submit()`'s `add` and
   `replace` locals (`:660`, `:690`) when a Lua chunk exceeds the line-length limit on submit — goes
   **straight to the model**, bypassing the controller entirely:
   ```lua
   local reject_oversized = function(chunks, idx)
     local block = chunks[idx]
     if not block or not block.pos then return end
     input.model:move_cursor(block.pos.start, 1)   -- input.model, not input:set_cursor()
     input:update_view()
   end
   ```
   This moves the cursor to the **start of the rejected block** — a real, data-derived target
   position, not a preserve-old-value round-trip like `load_selection`'s. It's also the only current
   site that calls `move_cursor` (not `set_cursor`) externally to the model — and it does so through
   `input.model`, not through any `UserInputController` wrapper (there isn't one for `move_cursor`,
   consistent with §1's narrower controller surface).

Console never calls any of these. Search never does either. The project overlay has no way to
today (§1). Two precedents now, not one — and they don't even agree on layer (controller-API vs.
reach-straight-into-the-model), which is itself a small instance of the same "each mode invented
its own way" pattern found for `reset()` in §5.

## 3. `set_cursor` is a raw, unvalidated assignment — a real gap for the planned API

`UserInputModel:set_cursor(c)` (`userInputModel.lua:499-501`) is just `self.cursor = c` — no bounds
check against text length at all. That's safe today only because **every current caller already
supplies a pre-validated `Cursor`**: either round-tripped from `get_cursor_info()` (inherently
valid — it was just read), or built from `move_cursor`'s own clamped `l`/`x` (which does the bounds
math internally before constructing the `Cursor`). **`compy.input.set_cursor(line, col)` would be
the first caller ever to hand this method an arbitrary, project-supplied pair** — there is no
existing bounds-checking code to model that validation on; it will need to be designed fresh, not
adapted from a `move_cursor`-style precedent, because `move_cursor` computes bounds internally
rather than validating an externally-given position.

## 4. FR-1's "initial cursor position" is not implemented at all — confirmed, not assumed

`UserInputModel.new(cfg, eval, oneshot, custom_label)` (`userInputModel.lua:47-66`) hardcodes
`cursor = Cursor()` (always `(1, 1)`) in the constructor — **no cursor parameter exists**, so a
project (or console/editor) supplying non-empty initial text has no way to place the cursor
anywhere but the start. `UserInputController:show(cfg)`'s `force` reconfigure path
(`userInputController.lua:233-251`) only patches `cfg.text`, never a cursor — so even the one
*mid-session* override path this codebase has today doesn't touch cursor either. This is a
concrete, verified implementation gap against an explicit stakeholder requirement
(`design/requirements.md:68`, "Initial cursor position | Places the cursor at a specified position
within the initial text"), not something already half-built to extend.

## 5. "Reset the prompt" is four bespoke, inconsistent implementations, not one operation

Two genuinely different operations already exist at the controller boundary, and they are **not**
interchangeable:
- `UserInputController:reset(history)` → `model:reset(history)` → `clear_input()` **plus**, if
  `history` is truthy and the model isn't `oneshot`, wipes `History` too.
- `UserInputController:clear()` → `model:clear_input()` **plus** `clear_error()` — content-only,
  history untouched, but *does* also clear an error state (which `reset()` does not).

Each mode invented its own trigger for "reset the prompt," and none of the four match:

| Mode | Trigger(s) | What actually resets |
|---|---|---|
| Console | Ctrl+L | **Terminal only** (`model.output:reset()`) — input untouched |
| Console | Escape (no Ctrl) | `input:cancel()` → content reset, **history preserved** |
| Console | Ctrl+Q (quit project) | Terminal + input content, **history preserved** |
| Console | Ctrl+Shift+R (app reset) | Terminal + input content, **history wiped** (`reset(true)`) |
| Editor | Ctrl+W | `input:clear()` — its own distinct trigger, no console equivalent |
| Editor | successful submit | `input:clear()` (inside `submit()`'s `add`/`replace` locals) |
| Editor | Escape | **Does not reset** — repurposed entirely for `load_selection()` (§2) |
| Search | mode entry/exit | `SearchController:clear()` — see §6, a distinct code path again |
| Project | *(none)* | No `clear()`/`configure()` exposed at all — only `show`/`hide` (§1) |

Console's Escape-cancels-content behavior is worth a specific callout: it is **not** because editor
opts out of some shared default — the *shared* `UserInputController:keypressed`'s own `cancel()`
local (`userInputController.lua:433-437`, `if not Key.ctrl() and k == "escape" then input:cancel()
end`) is only invoked from the **non-editor branch** of that same shared function's own internal
`if love.state.app_state == 'editor' then ... else ... cancel() ... end` fork
(`userInputController.lua:456-479`). That is, **the "shared, context-blind sink" is not fully
context-blind** — it peeks at `app_state` itself, a second, inner fork nested inside the one
`ConsoleController`/`EditorController` already do at the outer level. This is exactly what stops
editor's `load_selection()` (which populates the input on the very same Escape keypress) from being
immediately undone by a `cancel()` that would otherwise also fire on Escape passthrough.

## 6. Search's `clear()` reaches past its own controller into the model layer

`SearchController:clear()` (`searchController.lua:44-47`):
```lua
function SearchController:clear()
  self.model.input:clear_input()  -- Search MODEL's .input field (a UserInputModel) — not self.input!
  self.model:clear()
end
```
`self.input` (a `UserInputController`, the field `SearchController` itself holds) is never touched
here — the call goes straight to `self.model.input` (the `Search` model's own `UserInputModel`
field), skipping the controller wrapper entirely and thus skipping `clear_error()` too (unlike
`UserInputController:clear()`, which pairs the two). Currently harmless — search has no evaluator
(`nil`), so no validator can ever set an error to begin with — but it's a real layering
inconsistency: every other "reset" operation above goes through a controller method; this one
doesn't.

## 7. Why this matters for #77's planned `configure()`/`clear()`/cursor surface

The balloons pain (relabel/reconfigure an active prompt without teardown) and FR-8/FR-9 (cursor
get/set) are two faces of the same currently-missing capability: **today's only project-facing
lifecycle affordance is `show`/`hide`** (§1) — there is nothing between "fresh session" and "fully
torn down." Every mode-specific "reset" trick in §5 is bespoke code living inside the *owning*
controller, reinvented slightly differently each time (terminal-only vs. content vs.
content+history; controller-level vs. model-level; Escape meaning cancel in one mode and load in
another) rather than a single shared, parameterized primitive. That's precisely the gap
`compy.input.configure()`/`clear()`/`get_cursor()`/`set_cursor()` (planned 0.1.0-m7,
`design/design.md` §3) is meant to close — but there is very little existing code to generalize
from: cursor manipulation has exactly one precedent (§2), and it's unvalidated by construction
(§3); "reset" has four precedents, and they actively disagree with each other (§5).

## Follow-up exchange with the human (2026-07-01)

**Q: which controller exposes `get_cursor_info`/`get_cursor_pos`/`set_cursor`/`jump_home`? Which
consumers use it — only editor via `load_selection`?**
A: `UserInputController` (§1). Corrected above (§2): editor uses it twice, not once —
`load_selection` (controller API) and `reject_oversized` (bypasses the controller, calls
`input.model:move_cursor` directly). Console, search, and project use neither today.

**Q: "oversized blocks handling" explicitly moves the cursor — is that in the current branch, or
still up-dev?**
A: Confirmed **in the current branch** — `reject_oversized`, wired to two live submit paths
(§2.2). Not speculative, not future work.

**Human's architectural read: the shared sink checking `app_state` (§5's inner fork) is an
abstraction leak — it should take a configuration flag instead, not consult global app state.**
Recorded as the human's stated position, not just an observation: the shared
`UserInputController:keypressed` reaching into `love.state.app_state` to decide its own Escape
behavior is exactly the same category of thing as `disable_selection` (an existing per-instance
config flag already on this same class) — it could plausibly have been e.g.
`self.suppress_cancel_on_escape` set at construction, instead of a global-state read baked into
shared logic. Relevant beyond this one call site: if console/editor/search's instances ever move
toward the handler-registration style discussed in [[shared-input-widget-singleton]] (or merge into
one reconfigurable object), this is precisely the kind of hardcoded mode-check that would have to
become an explicit per-instance/per-session config field anyway — so it's a small preview of that
larger migration's shape, not an isolated wart.

**Q: on FR-1 (initial cursor position) — the new API isn't built yet, so "not implemented" is
expected; what was actually wanted was the *current-system equivalent* for placing cursor when
loading text.**
A: Fair distinction — §4's finding stands as "the *new* surface doesn't have this yet" (unsurprising
pre-implementation), but here's what the *existing* bespoke code does when loading text, precisely:
- `UserInputModel:set_text(text, keep_cursor)` (`userInputModel.lua:128-146`) has its own built-in
  default: unless `keep_cursor` is passed truthy, it recomputes the cursor via `_update_cursor(true)`
  — **and regardless of `keep_cursor`, it unconditionally calls `self:jump_end()` at the very end**
  (line 145, outside the `keep_cursor` guard). So `set_text`'s own baked-in default cursor placement
  after loading new text is **end of the new text**, always.
- Editor's `load_selection` (non-`add` branch) calls `set_text(t)` and then **explicitly overrides**
  that default with `jump_home()` — because loading a block into edit mode should start the caret at
  the block's beginning, not its end. This override is the closest thing today to "place the cursor
  at a specific position after loading text" — but it's a hardcoded binary choice (model default:
  end: vs. this one caller's override: start), not a parameterized "put it at (line, col) X."
- `reject_oversized`'s `move_cursor(block.pos.start, 1)` (§2.2) is the one place that computes an
  actual **data-derived** target position rather than picking between two hardcoded ends — the
  closest current analog to what a general `set_cursor(line, col)` surface would need to support,
  and notably it reaches past the controller to do it.
So: no current facility exists for "load text and place the cursor at an arbitrary caller-given
position" — only "the model's own end-of-text default," "override to start" (editor), and "compute
and jump to a specific data-derived spot, bypassing the controller" (oversized-block rejection).

**Q/statement: the different `reset()` scenarios look architecturally fragile — would benefit from
unification.**
A: Agreed, and this matches §5/§7's finding independently — recorded here as confirmed, not just
suggested: four modes, four different trigger sets, two non-interchangeable underlying operations
(`reset(history)` vs `clear()`), one layering inconsistency (search bypassing its own controller),
and zero project-facing equivalent at all. This is precisely the shape `compy.input.configure()`/
`clear()` (planned 0.1.0-m7) is meant to replace with one shared, parameterized primitive.

## Side-note: using the `lua-lsp` MCP server this time

Asked whether I'd been using it — hadn't, for the earlier notes (grep/Read sufficed for tracing
known call chains). Used `references`/`definition` here since "who else manipulates the cursor" is
exactly the ambiguous-symbol-space case it's for. Findings: a **qualified** query
(`UserInputModel.reset`, `UserInputModel.clear_input`) was precise and fast. A **bare** name query
(`reset`, plain) was not scoped to the class at all — it matched every `reset` in the tree
(`love.graphics.reset`, `termcolor.reset`, `love.profiler.reset`, a game example's `HUNT.reset`
field, ...) and had to be manually filtered by hand, same problem CLAUDE.md's guidance already
warns about for generic names, just in the "too noisy" direction rather than "too thin." One query
(`UserInputModel.clear`, a name that doesn't exist as a method — the real name is `clear_input`)
came back **matching almost the entire file** and printed it three times over, at real context
cost — worth remembering: an unqualified miss on a common word can be far more expensive than a
plain grep for the same near-name would have been. Net assessment: valuable for the `set_cursor`
query (clean, exact, right the first time) and this note wouldn't have found §2 as fast otherwise;
not obviously better than grep for anything with a generic name, and one bad match was expensive.
