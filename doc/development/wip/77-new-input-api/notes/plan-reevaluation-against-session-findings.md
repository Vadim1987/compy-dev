## What holds up well (checked, not assumed)

- **FR-6 (project key-event starvation).** [[fr2-fr6-fr7-provenance-and-gaps]] found the current
  gate is total and keyboard-only (project's own `love.keypressed`/`textinput` never fire while the
  overlay is active; mouse was never gated). M4's contract (`spec/M4.md:30-33`) removes exactly this
  gate, and M5's three-tier dispatch (`spec/M5.md`) is the direct replacement. Diagnosis-to-fix
  match is precise, not just directionally similar.
- **FR-7 (boundary-hit signal).** Found the signal already threads out of the shared sink as a
  return value and is only dropped at the project-dispatch call site. `spec/M6.md:36-41` plans
  exactly `on_limit_reached(direction, scope)`, firing from the same underlying `is_at_limit`/
  `cursor_vertical_move` machinery already traced. No surprise left for M6 to discover.
- **FR-1's "initial cursor position."** [[cursor-and-reset-operations]] found this unimplemented in
  current code (hardcoded `Cursor()` = `(1,1)` in the constructor). Checked whether the *plan*
  accounts for it: yes — `spec.md:157` and `spec/M2.md:26-28` explicitly define a `cursor` field on
  `show(config)`, applied after `text`. Not a design gap; expected pre-implementation absence,
  correctly scoped for M2.
- **`set_text`'s unconditional `jump_end()` bug and `set_cursor`'s missing bounds validation.**
  Found both as current-code defects in [[cursor-and-reset-operations]] §3–4. Checked the plan:
  `spec/M7.md:29` explicitly requires `set_cursor` to "clamp to valid range," and `spec/M7.md:34`
  names the *exact* `set_text`/`keep_cursor` bug ("skip the unconditional `jump_end()`") as a named
  model fix. Both were already known to the design, not novel discoveries needing escalation.
- **The control-channel/text-channel split.** [[keypressed-vs-textinput]] found this is compy's own
  convention, not a LÖVE2D guarantee, currently implicit (no code enforces it, it's just how the
  `if k == ...` branches happen to be written). The plan makes it explicit and structural: D-6
  ("two independent channels... no suppression, no classification," `spec/M5.md:35-38`) — the plan
  formalizes the existing convention rather than fighting or quietly dropping it.

## Genuine issues, ranked by certainty

### 1. (Highest certainty) M4 promises keyreleased dispatch that M5 never delivers

`spec/M4.md:44-46` (Files section): *"`ProjectInputController` with `keypressed`, `textinput`,
`keyreleased` (basic sink delegation only; **M5 adds dispatch**)."* Checked M5's actual contract
(`spec/M5.md`) end to end: it defines the keypressed three-tier dispatch and the textinput
`on_text_entered` channel — **`keyreleased` does not appear anywhere in it.** Checked the canonical
`spec.md` too: `keyreleased` is mentioned exactly once, only in the `Controller.keys_pressed`
held-set bookkeeping context (§1) — there is no `on_key_released`/`handlers`-for-release concept
anywhere in the canonical contract. So M4's own cross-reference names a deliverable M5 never
actually specifies. Either a stale cross-reference (M5 was descoped after M4 was written and M4
wasn't updated) or a silently dropped scope item — I can't tell which from the record, but it's a
checkable, concrete inconsistency between two milestone specs, not a matter of interpretation.

**Note on severity:** FR-6's own stakeholder wording is about "keys **pressed**," not keyreleased —
so this may not violate any actual requirement. But it does mean the current
[[keyreleased-isrepeat-events]] finding (console gets `keyreleased`, editor/search never do) has no
guarantee of getting cleaner treatment even after the full #77 redesign — `ProjectInputController`
would still only offer "basic sink delegation," same tier as today, with no project-facing surface
ever planned for it. Worth a decision either way (explicitly descope with a one-line note, or add
the missing M5 tier) rather than leaving the M4↔M5 contradiction sitting in the record.

### 2. (High certainty) Search is a total blind spot across the *entire* design corpus, not just the FR-12 walkthrough

[[shared-input-widget-singleton]] found the FR-12 walkthrough table stops at "Ctrl+F → mode switch"
without addressing what happens to search's own nested widget. Checked further this pass: grepped
"search" (case-insensitive) across `design.md`, `spec.md`, and `roadmap.md` in full — **zero
matches, in any of the three.** This isn't a narrow gap in one walkthrough table; the entire
~90KB of primary design documentation never once names the editor's search sub-widget. When the
console/editor migration follow-on is eventually commissioned, whoever picks it up has no design
guidance for this surface at all and will have to rediscover it from scratch — the same failure
shape the `M4-0-04` review caught for the missing editor-keypressed test (a real, load-bearing
surface silently absent from the record someone is relying on being complete).

### 3. (Medium certainty) FR-2's resolution was reinterpreted without a visible stakeholder re-confirmation

Already detailed in [[fr2-fr6-fr7-provenance-and-gaps]]: the early gap-analysis (`context.md:341`)
called for "a project-callable remove path"; the final resolution (`decisions-record.md:107-114`)
instead declares persistence+`hide()` "addresses" FR-2, with no separate `remove()` ever built. I
checked every stakeholder round (SR1/SR2/SR3) again for an explicit sign-off on this substitution
and found none. Not necessarily wrong — the human's own instinct is that stakeholders would be
fine with it — but it's currently the design's own assumption, standing in for a decision, not a
confirmed one. Low urgency (nothing breaks if it's right), but worth a checkbox before treating FR-2
as closed.

### 4. (Lower certainty — a judgment call, not a fact) "Clean follow-on" undersells what console/editor migration will actually have to reconcile

`design.md:415-423` frames the eventual console/editor migration as mechanical: *"it replaces
if-chains ... with handler registrations; the underlying methods ... are unchanged."* This
session's findings suggest the underlying methods are **not** uniform enough for that framing to
hold without decisions being made along the way:
- Four different, non-interchangeable "reset the prompt" implementations across console/editor/
  search ([[cursor-and-reset-operations]] §5) — a migration to shared handler registrations will
  have to pick *one* behavior, not just relabel four.
- The `keyreleased` routing fork gap (console gets it always, editor/search never do,
  [[keyreleased-isrepeat-events]] §2) — currently inert only by coincidence (disable_selection +
  textinput's unconditional error-clear); a migration touching this surface could un-mask it.
  becomes)
- Cursor manipulation split across two layers even *within* editor itself (`load_selection` via the
  controller API vs. `reject_oversized` reaching straight into the model, [[cursor-and-reset-operations]]
  §2) — not just "console vs. editor," inconsistent *within the single controller* the migration
  would touch.
This doesn't mean the migration is unsound — it means "clean, mechanical, no behavior decisions
needed" is optimistic given what's actually there. Recommend the eventual follow-on's own scoping
note acknowledge these as reconciliation points, rather than assume the if-chain-to-registration
swap is purely syntactic.

## Not a gap, just a reconciliation flagged for implementation time

## Revision after human pushback (2026-07-01, same day)

The human corrected the severity/framing on two of the four items above. Both corrections held up
under a second, more careful check — recorded here rather than silently editing the original
findings out.

### Search-gap severity: downgraded, not retracted

**Human's point:** since console/editor migration is *itself* already postponed (a named follow-on,
not part of #77), a design gap that only matters *to that follow-on* isn't urgent now — the actual
priority is FR-6 (project can't receive key combos), which #77 does fix directly.

**Agreed.** The fact stands (zero mentions of "search" anywhere in `design.md`/`spec.md`/
`roadmap.md`) — that's not in question. What was wrong was treating it as a live risk to #77's own
delivery. It isn't: nothing in M1–M8 depends on search, and the gap only becomes load-bearing if/when
someone picks up the console/editor follow-on. Re-ranked accordingly: **real, but low-urgency,
parked alongside the follow-on itself — not a concern for the current milestone chain.**

### FR-2 / "removal": the human's UX argument is very likely correct, and checking the *mechanism*
### surfaces something sharper than the original stakeholder-provenance concern

**Human's argument:** from a UX standpoint, "hide, and stop receiving key input, with no pending
side effects left behind" *is* full functional removal — there's nothing a literal
destroy-the-object teardown would achieve that a sufficiently clean hide doesn't. Any stakeholder
fear of "removal" probably traces to the *current* intertwined architecture (global state leaking
across sessions), not to a genuine need for object destruction — so once #77 delivers a
clean, reliable hide with no dangling state, it *becomes* the thing they meant by "removing."

**This tracks, and it's consistent with the design's own stated intent** — `design.md:107-110`
already frames the sink as doing "work proportional to its activation state (transparent no-op when
hidden, text-editing operations when visible)." That's the same claim: hidden ⇒ no side effects,
full stop.

**But checking whether the *mechanism* actually delivers that guarantee surfaces something new.**
The "no-op when hidden" phrase is backed by concrete acceptance criteria for the `compy.input.*`
**getter/setter surface** — `get_cursor()`/`set_cursor()`/`set_text()`/`configure()` each explicitly
say "no-op when hidden" / "nil when hidden" in `spec.md` and `spec/M7.md`. I could **not** find the
equivalent guarantee specified for the **keypressed/textinput event path itself** — i.e., "the sink
does nothing when a keystroke arrives while hidden" is not named as an acceptance criterion anywhere
in `spec/M2.md`, `spec/M4.md`, or `spec/M5.md`.

**Why this matters, precisely: gate removal is what *creates* the obligation.** Today, the sink is
never even *invoked* while hidden — the outer `if user_input then ... end` gate
(`controller.lua:652-657`, traced in [[keypressed-vs-textinput]]) structurally prevents it. Once
that gate is removed (M4, to fix FR-6 — the actual priority, per the human), `ProjectInputController`
occupies the keypressed slot unconditionally, and tier 3 of the dispatch
(`compy.input.on_key_pressed`, default = the sink) will run on **every keystroke, shown or
hidden**, unless the sink gains a new internal check it never needed before. **Fixing FR-6 is
exactly what makes "is the sink a true no-op when hidden" a newly-live question** — it isn't one
today only because the old gate answers it for free.

So: the human's UX argument for treating hide-with-no-side-effects as full functional removal is
sound, **conditional on** that guarantee actually being built and tested for the keypressed/textinput
path specifically, not just for the four getter/setter calls that already have it. Recommend this
become an explicit acceptance line on **M4** (where the gate removal happens and the obligation is
created) — e.g., "a keystroke delivered while the singleton is hidden produces no model mutation,
no view update, no history/selection/cursor change" — rather than resting on `design.md`'s prose
statement of intent. Once that's a tested guarantee, FR-2's reinterpretation (hide ⇒ removal) stops
being an unconfirmed assumption and becomes simply *true by construction* — which would actually
resolve the stakeholder-provenance concern from §"FR-2" above better than seeking a retroactive
stakeholder sign-off would: the substitution becomes self-evidently correct rather than merely
asserted.

## Bottom line (revised)

No dead ends found. The architecture (persistent singleton, three-tier dispatch, two independent
channels, `on_limit_reached`, cursor clamping) is coherent and, where checked, already anticipates
this session's current-code findings rather than being blindsided by them. Of the four items:
search's blind spot is real but low-urgency (parked with an already-postponed follow-on, not a risk
to #77's own delivery); FR-2's resolution is very likely correct on UX grounds, and the actual
actionable item is narrower than "get stakeholder sign-off" — make "no-op when hidden" a tested M4
acceptance criterion for the keypressed/textinput path specifically (not just the getter/setter
surface), since gate removal is what creates that obligation in the first place. The keyreleased
M4↔M5 cross-reference gap and the console/editor migration's real complexity stand as originally
assessed. The actual priority, as the human notes, is FR-6 (project key-combo reception) — which
the plan gets right.
