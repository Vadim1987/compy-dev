The human is standing up a docker-compose blueprint that spins a `lua-language-server` alongside the
orchestrator / developer / reviewer containers, bridged over `socat`, exposed to agents as an MCP-LSP
backend. Questions: is it worth it per-agent, do we want a separate codebase-Q&A agent (which model),
and is "test the integration" its own operational entrypoint. **Verdict: worth it for the
code-touching agents + a Q&A agent; not for the orchestrator; park it as a low-priority operational
entrypoint (E17), off the #77 critical path.**

## Per-agent value

| Agent | LSP value | Why |
|---|---|---|
| **Orchestrator** (brainlab) | **None** | Works on docs/specs/roadmap; deliberately doesn't read/write feature code. Wiring = surface area for ~zero payoff. |
| **Developer** (Sonnet) | **Bounded-yes** | go-to-def / hover / live diagnostics catch errors before busted runs, cut blind grep/read churn. Lua is dynamically typed → quality hinges on EmmyLua annotations + the server coping with love2d globals and `{M,C,V}` scaffolding. A strong hint, **not** ground truth — keep grep as backstop. |
| **Reviewer** (Opus) | **Highest** | find-references / call-hierarchy = precise impact analysis ("who calls this changed fn"), exactly the cross-cutting reasoning that's expensive without LSP. |

## Separate codebase-Q&A agent

**Yes — the cleanest, lowest-risk use-case.** Read-only, no write tools, "explain don't change" system
prompt; kept distinct from the *mutate* (dev) and *judge* (reviewer) agents. Doubles as the human's own
"ask about the codebase" tool.

- **Model: Sonnet 4.6** — strong enough to chain LSP lookups + synthesize, fast/cheap enough for
  interactive back-and-forth.
- **Haiku 4.5** if questions are mostly mechanical lookups (where's X defined, who calls Y).
- **Not Opus** — overkill/slow/expensive for Q&A; reserve Opus for the reviewer where judgment depth pays.

## Is it overkill for #77?

Two framings:
- As a **#77 blocker** or a from-scratch build justified by #77 alone → **overkill**. The codebase is
  modest; grep + read already suffice for this bounded feature. It must **not** gate the feature.
- As a **project-level, reusable capability** (multi-agent setup already exists; "chat about the
  codebase" is an immediate clear use-case) → **legitimate**, same class as the estimates entrypoints
  (E10/E11): maintained, recurring, but decoupled and low-priority.

"Test the integration" is **not** a separate fourth thing — fold the smoke-test into standing it up.

## Recommended shape (→ E17)

1. Stand up the compose + socat wiring.
2. Smoke-test LSP-over-MCP from the **Q&A agent** (the clear use-case) first.
3. Only then decide whether to wire the developer + reviewer.

Architectural note: sharing one `lua-language-server` across containers over socat is fine; watch
concurrent-edit / shared-workspace state if they operate on the same tree.
