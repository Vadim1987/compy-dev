## Open contradiction (a) — route-restoration lexicon: "slots restored" vs "route/mode switch"

**The suspicion (human, session36):** any "**slots restored** to console" phrasing is
misinterpretation-era. The real `love.*` slots are always occupied by the main controller; what
switches is the **routing mode / active route**, not which slots are hooked.

**The evidence he is right — an internal contradiction in the corpus:**
- Ratified model §0 glossary: `slot / occupancy` = "mutable `love.*` fields — **mechanism,
  non-binding**; … **slot-reconfiguration-as-routing is a replacement candidate** (routing table
  below fixed slots)."
- design §2: "**Mechanism is free.** … slot-swap vs. routing-table realization … all non-binding
  mechanism (ruling 5). `Controller._keyboard_route` (a routing table below **fixed** slots) is the
  **sound direction**, not a requirement."
- **Yet** design §4 ("On project stop: every **slot restores** to the framework default"), R11
  ("`suspend()` **restores all slots** to console"), and spec §8 ("the keyboard/text **slots
  restore** to the console route") all state the contract in the slot-restore mechanism vocabulary
  the model marks non-binding and points *away* from.

**Corroborating inline suite REVIEW comments** (already on disk, guardrail-4 design inputs):
- L718–719: "why all this mechanics with 'named' targets? … How is 'stop' different from project
  exit or inspection? What triggers `cc:stop_project_run()` in production?"
- L487–489: doubts the whole "console secretly/meaningfully processing input while off-screen"
  concept; states his model — **if project/editor is the active route, events travel down through
  it**; whether they end in the widget (shown), a noop (hidden), or a project handler is the
  **route's** responsibility.

**What the cold session must resolve:**
1. Is "slots restored to console" a contract statement or a mechanism leak? If the binding concept
   is the active route/mode over fixed slots, restate spec §8 / design §4 / R11 accordingly (this
   touches Gate-2-**approved** spec.md — a human-owned reopen, not an in-slice edit).
2. Restate the real restore cases in route/mode terms: **project-exit** (non-blocking `main.lua`
   returns → `'project_open'`; only kbd/text change consumer, pointer unchanged, ruling 3);
   **stop** (full reset to framework defaults); **inspect** (R11 — console route active **bound over
   the project env**; project route disconnected; widget unhonoured).
3. Then M5c can state the correct target assertion for the landed `stop names the console as
   restored route` row (L720).

## Open contradiction (b) — assign-replaces-capture

**The claim under suspicion:** "a project assigning the field **replaces** the wrapped native like
any callback" — appears **only** in spec §8 R7. It is **absent** from the ratified model R7 and from
design §5 (both say only "auto-provision as plain tier-3 participants," no replace relationship).

Per the model's own disclaimer ("everything in `design.md`/`spec.md` is elaboration … and can be
wrong without the model being wrong"), this is an un-ratified elaboration. It is *plausible* (the
mutable boundary R3 makes `on_*` assignable; a captured native is its initial value; assigning would
overwrite), but the human wants it **verified against frozen design**, not assumed.

**Corroborating inline REVIEW (L740):** the human's own account of the intended autoprovisioning —
"autoprovisioning was supposed for a different approach — where 'sink' does not even exist as a
first-class thing, and instead *if* the project does not install its own keypressed, the
autoprovisioner installs a standard function that directs the event to the sink" — and his live
doubt that the autoprovisioning concept may be "a bit fragile … maybe three-step
(combos→handler→widget) is better." So the capture→initial-value→replace story is exactly the part
he is not sure the frozen design actually ratified.

**What the cold session must resolve:**
1. Does frozen design intend capture-as-initial-value + assignment-replaces, or a different
   relationship (e.g. autoprovisioner-only-when-absent, no first-class sink)? Reconcile spec §8 R7
   against ratified model R7 + design §5.
2. If the model and spec genuinely diverge, that is a spec defect to correct at the model's
   authority level — again a human-owned reopen.
3. Then M5c AC-36 can (or cannot) assert the replace relationship between the two install paths.

## Resolution (E30, session37 — 2026-07-07)

Cold read of the four authority docs (ratified model, `spec.md`, `design.md`, M5c) + the landed
suite rows + the inline `-- REVIEW:` comments. Human ruled both. Dispositions:

### (a) route-restoration lexicon — RESOLVED, no contract reopen

Finding: the frozen contract **already speaks route/mode**, correctly. **AC-27–30** (M5c) state
project-exit / stop / inspect in active-route terms with no slot lexicon. The "slots restored to
console" phrasing survives only in (i) non-binding mechanism *asides* in `spec.md` §8 / `design.md`
§4 that co-state the correct route-level statement, and (ii) the landed suite row L727
`stop names the console as restored route`.

The suite row is worse than stale — its **target is wrong**: it asserts
`active_keyboard_route() == console` after stop, but "keyboard reaches the console" is the *generic*
not-project-active state (identical for project-exit and inspect), **not** stop-specific. Stop's
distinctive contract is **teardown** (AC-29). This is exactly the L718 REVIEW ("how is stop different
from project exit or inspection?") — answer: for the keyboard-destination question alone, it isn't.

Disposition: **no design.md/spec.md reopen** (AC-27–30 already correct; the prose asides are
non-binding and may stay). Land in M5c only: **retarget the row to AC-29 teardown**, drop the
`active_keyboard_route()` accessor (C23). Suite `-- ESCALATED` marker → converted to a RESOLVED
retarget note.

### (b) assign-replaces-capture — RESOLVED to precedence; minimal spec.md hardening

Finding: the "assignment **replaces** the wrapped native" phrasing lives only in `spec.md` §8 R7 +
§11 #8 (+ M5c AC-31) — absent from the ratified model R7 and design §5, which carry **no** replace
relationship. As literally written it **permits the reverse-override** the human feared: a project
assigning `on_*` early then defining `love.*` later in the chunk → capture-at-load reads the final
`love.*` → native overwrites the explicit `on_*`. And `spec.md` §8 is M5c's cited authority, so a
"fallback, no replace" M5c against a "replace" authority is a live derivation-drift trap.

Human ruling (capture-point): **install the native wrapper only if `on_*` is not set** — the native
is the material for the tier-3 **default participant** that would otherwise be a noop. Resolves to a
**precedence**: explicit `on_*` > captured native > noop; `love.*` read once at load, never
re-consulted, never overrides an `on_*`. This *aligns* spec.md with the ratified model R7 / design
§5 — a realignment, not a new design.

Disposition: human **endorsed hardening the already-closed `spec.md`** — §8 R7 reworded to
precedence + reverse-override foreclosed; §11 #8 updated (drop "assignment-replaces"). M5c AC-31 →
precedence wording; AC-36 "both populate the same slot" → **mutually-exclusive precedence**, and the
10(b) escalation converted to a stated precedence assertion. Suite L749 `-- STALE` marker → precision
line added. **Optional (human add-on):** framework MAY `Log.warn`/error when both a native and an
`on_*` are defined for a channel — advisory only, pursue iff ~3 lines and no test; marginal case.
