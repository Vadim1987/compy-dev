# Codeinspect harness — build justification & resolved architecture

_Generated by LLM(Claude Opus 4.8): 2026-06-19; Approved by human?: direction YES (build commissioned), pending build + smoke-test._

**Verdict:** building the single-container `codeinspect` harness is justified — as the **human's own
comprehension instrument** (current structural navigation + a conversational layer to interrogate it)
plus a CI-matched reproducible toolchain — **not** as a #77 blocker. Keep it E17-class: operational,
decoupled, off the critical path. Supersedes the socat blueprint in [`mcp-lsp-tooling.md`](mcp-lsp-tooling.md).

## Why it's justified (the human's framing strengthens the E17 case)

- The E17 note justified the LSP **per-agent** (dev / reviewer / Q&A). The human reframed the primary
  user as **himself**: the codebase is complex, deps rewind during implementation, and he refuses to
  rebuild the dependency map in his head. He needs (a) reliable structural navigation — defs/refs/impact
  that stays current, not memory — and (b) an interface to ask questions of it. `claude-code` + MCP-LSP
  is exactly that pairing.
- The justification is **agent-independent**: it holds even if he stops delegating and hand-implements
  every spec — his words, *"super-fragile without LSP and interface to query it."*

## Honest caveat — what the harness does NOT uniquely provide

- Pure LSP navigation (go-to-def, find-refs, diagnostics) is already available by running
  `lua-language-server` in his editor — no Docker, no claude. That slice of the need is met more cheaply.
- The harness earns its marginal keep via: (1) the **conversational / impact-analysis layer**
  (natural-language "what breaks if I change X", cross-cutting synthesis); (2) a **CI-matched
  reproducible toolchain** (pinned LuaJIT/luarocks/LÖVE/Node, so diagnostics match CI); (3) it doubles
  as the **agent execution box**. Justified on those — not on raw navigation alone.

## Resolved architecture (supersedes the E17 socat blueprint)

- **Single container `codeinspect`**, human-driven: `compose up -d` → `exec bash` → launch a CLI. The
  earlier multi-container `lua-language-server`-over-`socat` fleet is **dropped as overengineered**.
- **Three interchangeable CLIs** — `claude` / `cursor-agent` / `agy` — each oriented to the project's
  own rule chain (`/repo/CLAUDE.md → AGENTS.md → agents/rules.md` + `orientation.md`), each spawning the
  Lua MCP↔LSP bridge **locally over stdio**.
- **Bridge:** `isaacphi/mcp-language-server` (generic, Go) driving `lua-language-server`. Lifetime = the
  CLI session (one warm server, not per-call), no daemon/supervisor. Zero model tokens; returns compact
  defs/refs vs. pasting whole files.
- **Edit-sync (verified in source, not assumed):** the bridge runs an fsnotify (→ inotify)
  `WorkspaceWatcher`; external edits (the CLI's Edit tool writing to disk) fire `didChangeWatchedFiles`
  → LuaLS reindexes. Reliable here because writer + watcher share one container / kernel / bind-mount on
  native Linux — *not* the Docker-Desktop host→container FUSE case. Async, hence `sleep 1` before query.
- **DevX:** `/impl` symlink → the spec/outcome/review tree; in chat, "implement /impl/prompts/M2.md".
- **Why `nzrsky/lsp-mcp-server` was dropped:** image unpublished (ghcr 403), it's stdio (not TCP), and
  no Lua support.

## Addendum (2026-06-19) — why the "editor-LSP is cheaper" caveat does NOT apply to this human

The caveat above assumes the editor-LSP path is low-overhead. For this human it isn't, and that
**inverts** the conclusion — the harness becomes his *cheapest* LSP surface, not a marginal add-on:

- He's a science-researcher who treats **mindspace cleanliness as a hard constraint** and has used
  **bare vim** (not even neovim) for decades, deliberately, to keep IDE bells-and-whistles from
  competing with code/concept/console-chat navigation. Bolting an LSP plugin into that setup is
  unwelcome; migrating to neovim "is no fun either." So the editor-LSP alternative carries **real
  overhead he won't pay** — it's not actually free for him.
- He's **already fluent and comfortable in agentic chat**. Plugging the LSP into the agentic chat
  surface — which the same harness trivially re-roles into developer-chat or reviewer-chat — means LSP
  power arrives through a tool he *already* uses, at near-zero new cognitive overhead.
- Net: for him, "any other usage of LSP would bring more overhead." The harness is the
  **economically-justified** LSP access path *because of*, not despite, his minimalist toolset — it adds
  zero new editor surface and reuses the chat workflow he's settled on. (Recorded behaviourally in
  `sessions/.../session15/observation.md`.)
