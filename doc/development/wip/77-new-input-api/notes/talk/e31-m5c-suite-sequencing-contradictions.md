## Contradiction F1 — legacy-solicitation green rows orphaned between AC-25 and AC-35

**The facts (all verified):**
- M5c **AC-25 / Scope item 3** delete the `oneshot` flag **and** the `push('userinput')` custom
  event. Confirmed coupling in code: `userInputModel.lua:812-819` pushes `'userinput'` **only**
  `if self.oneshot`; `controller.lua:867` is `handlers.userinput = function() … end` (nulls
  `love.state.user_input` on the next dispatch). design.md §8 row 14: *"deletion rides the
  dispatch-chain slice."* So M5c removes both.
- The **legacy globals** (`input_text`/`user_input`/…) are removed **only at M8**
  (`M8-02-recut.md` Contract; spec.md §9). `M8-02-recut.md` **explicitly accepts** the interim:
  *"The known dev-build window where text-input examples don't run closes here."* — i.e. it opens
  at M5c and closes at M8.
- **AC-35** requires *"the full suite is green"* after M5c.

**The contradiction.** Three landed **GREEN** rows exercise exactly the machinery AC-25 deletes:
- `legacy text solicitation › a submit fills the handle and closes` (L358) — asserts
  `push('userinput')` fired (`closed == true`).
- `widget activation and reset › a oneshot submit deactivates the widget` (L457) — calls
  `F.session.handlers.userinput()` directly (nil after M5c ⇒ error).
- (`legacy text solicitation › a refused solicitation warns` (L373) is borderline — depends on
  `input_text` surviving; it may survive M5c since globals go at M8. Include it in the sweep.)

M5c's suite-reconciliation (**Scope item 10**) names **only** the generic-callback + stop rows.
These legacy rows carry **no `-- REVIEW:` marker**, so **AC-37 misses them** too. Net: the M5c
implementor meets undispositioned green rows that AC-25 breaks — forcing an **in-slice judgment
call (guardrail-1 violation)** or a **silent suite edit**. The M8-accepted dev-window fact never
made it into the M5c suite scope.

**What the cold session must rule (options, not a decision):**
1. **Disposition in M5c:** retarget the submit/close row to the new
   `before_submit → validator → on_text_entered → deactivate → after_submit` path (assert delivery
   via `on_text_entered`, not `push('userinput')`); pend/retarget the `userinput`-coupled row to M8.
2. **Loosen AC-35 for the named window:** allow this explicit, listed set of legacy rows to go
   pending/red across the M5c→M8 window M8-02 already accepts — nothing silently dropped.
3. Confirm whether `input_text`/`user_input` as *public globals* keep working (rewired onto the new
   chain) through the window, or are effectively dead until M8 — the design is currently ambiguous
   (spec.md §5 mechanism note ties the push to *"polling itself (§9)"* = M8, while design.md §8
   row 14 + AC-25 delete it at M5c: an internal-corpus tension to settle).

## Contradiction F2 — two pending rows draft SUPERSEDED semantics; AC-35 greens them, AC-37 misses them

AC-35 mandates greening the pending Bucket-B rows. Two of them carry bodies that **contradict the
ratified model**, and their comments are `OPEN` / `DEFERRED` — **not `-- REVIEW:`** — so **AC-37
does not force reconciliation**, and the mandate's "adapt the body to the landed API shape" license
lets a naive greening re-encode the trap:

- **L806 `on_key_pressed and on_text_entered exist`** drafts `on_text_entered` as a **per-character**
  textinput callback (`F.session.type('Z')` ⇒ `t_got == 'Z'`) and carries a stale OPEN question
  *"does on_text_entered fire per textinput character … or once per submitted block on return?"* —
  **ruling R1 already settled this**: `on_text_entered` is the **widget output** (submit-time,
  assembled text); the per-character chain callback is **`on_text_input`**. Greening as-drafted
  re-encodes the exact R1 trap the whole re-derivation exists to kill.
- **L842 `combo handlers dispatch on the combo`** uses a **flat** `handlers = {['ctrl+s'] = fn}`
  table — the **R14-forbidden** shape (AC-6 requires per-event sub-tables
  `handlers.keypressed['ctrl+s']`).

**What the cold session must rule:** (a) explicitly disposition the two bodies in M5c — split into
`on_key_pressed` (tier-3 keypressed) + `on_text_input` (tier-3 textinput, per-char) + `on_text_entered`
(widget output, submit); per-event handler table for the combo row — and/or (b) **broaden AC-37**
to reconcile `OPEN` / `DEFERRED` design-question comments in the suite, not only `-- REVIEW:`
markers, so stale design questions can't ride a pending body into green.

## Contradiction F3 — no functional test for the highlighter (only settability is asserted)

M5c Scope item 4 puts `highlighter` in-slice as a **live** widget output (design.md §3: it "runs
live for the whole session — `input_code`-style composition is its flagship case"). But the only AC
touching it is **AC-16** (*settable* as a config key / field). **No AC or landed test asserts the
highlighter actually transforms the displayed text as the user types.** The absence of even a
trivial functional test for a real, flagship-case behaviour is suspicious — exactly the kind of gap
that lets a regression land green.

**What the cold session must rule:** add an AC (and a red acceptance test) asserting the highlighter
is *applied* — e.g. a `highlighter` set at `show{}` transforms the rendered/queried text on
composition — not merely that the field accepts a function. Keep it minimal; the point is coverage
of the real functionality, not exhaustiveness.

## Contradiction F4 — mechanism-vocabulary ("occupant"/"slot") used as a *behavioural* assertion

The ratified glossary marks **slot / occupancy as mechanism, non-binding** — "occupy" is acceptable
**only** as shorthand for "currently active route"; asserting *routing behaviour* in slot/occupant
terms is the misinterpretation shape. One landed **green** row does exactly this:
`provisional › a release under a widget reaches the occupant` (L589, comment L583-587 "the raw slot
stands in for the occupant") — it sets a raw `love.keyreleased` and checks it fires, which its own
`-- REVIEW:` (L588) correctly calls a trivial slot test; the design-correct assertion is that the
release **propagates downstream to the active route's consumer (console/editor/project) without
being swallowed**. (Grep `occupant|slot` over the suite: L21/L325 use the terms *correctly*
— defining widget as *not* a slot occupant, asserting behaviour *not on slot identity*; L280/L776/
L823 are benign mechanism description; **L583-589 is the misoriented behavioural usage**, plus the
already-flagged L710 STALE comment.)

**What the cold session must rule (human-directed, session38):** any misoriented test that uses
`occupant`/`slot` terminology in a meaning **not prescribed by the design doc** must be **explicitly
targeted by M5c** — either **rewritten** (assert downstream propagation, per the L588 REVIEW) or
**requalified** (relabelled as a mechanism/NFR guard if that is what it truly is) — **or** covered by
a **generic acceptance criterion**, e.g.: *"No green behavioural test asserts routing in terms of
`slot`/`occupant` except where the glossary prescribes (`occupy` = shorthand for the active route);
every remaining mechanism-vocabulary usage is either mechanism-guard-labelled or rewritten to
route/chain terms."* The generic-AC option is preferred — it catches the class, not just this row,
and future rows can't reintroduce the leak.

## Resolution (human rulings, brainlab session39, 2026-07-07)

The owner ruled F1/F2/F4 directly in-plane (redirecting E32 from a separate cold session) and
deferred F3. Rulings folded into `M5c-dispatch-chain.md` as AC-39/40/41 + a Scope-10(c)
disposition; the deprecated-marking (F1 step 1) landed in the suite this session. Owner commits.

**F1 — legacy-solicitation retirement lifecycle → AC-39.** The rows exercising the deleted
`oneshot`/`push('userinput')` machinery (`a submit fills the handle and closes` L358; `a oneshot
submit deactivates the widget` L457) follow a lifecycle: **(1)** tagged `#deprecated` **now** (design
plane, this session); **(2)** go red when AC-25 deletes the machinery; **(3)** demoted to `pending()`
once red — **busted has no xfail/expected-fail primitive; `pending()` is its skipped state**;
**(4)** deleted once the same behaviour is green through the new chain (submit → validator →
`on_text_entered(text)` → deactivate). Because they end the slice `pending()`-or-deleted they never
stand red at the boundary ⇒ **AC-35 holds without loosening**. `a refused solicitation warns` (L373)
rides `input_text` (survives to M8, spec §9) — **stays** this slice. The submit→`on_text_entered`→
deactivate behaviour MUST get a live red acceptance row (test-first) — the new chain re-proves it.
**Internal-corpus tension — RESOLVED (owner-accepted, folded session39; awaiting owner commit).**
The push/oneshot *contract* dies at M5c (AC-25, design.md §8 row 14) but spec.md §5 L234 read
"dissolves with polling itself (§9 = M8)" — a Gate-2 phrasing collision. Resolved by decoupling: the
push **producer** dies at M5c (`on_text_entered` replaces the notification), the polling **consumer**
idiom (`input_text`/`user_input` reftable loop) dies at M8/§9; between them, legacy polling examples
get no notification — exactly M8-02-recut's accepted dev-build window. spec.md §5 L234 **reworded**
in the working tree to state producer-m5c / consumer-m8 (header amendment note added; owner commits
the Gate-2 file).

**F2 — superseded semantics → AC-40 + AC-41.** L806: `on_text_input` (tier-3 textinput generic
callback, per-character, AC-8) and `on_text_entered` (widget submit output, once at Enter with
assembled text, AC-17/R1) are **distinct**, each gets a red row; the row's stale per-char-vs-block
OPEN question is settled by R1; re-drafted to the split (naive per-char greening forbidden). L842:
the R14-forbidden flat `handlers={['ctrl+s']=fn}` table is rewritten/expanded to **three rows** —
one per per-event sub-table (`handlers.keypressed`/`.textinput`/`.keyreleased`), each asserting
dispatch on the normalised combo. Both become ACs per the owner.

**F4 — mechanism-vocabulary behavioural row → Scope-10(c).** L589 is **superseded** by AC-36 on the
keyreleased channel (case (a) = invoked regardless of widget-shown state; (b)/(c)/(d) = downstream
propagation-without-swallowing, i.e. exactly the L588 REVIEW's "correct test"). **Deleted the moment
AC-36's keyreleased rows land green** — not before (no coverage gap).

**F3 — RESOLVED (owner ruling) → AC-42.** In-slice functional AC, generalised: a settable
text-processing widget output is proven to actually execute against the live/submitted text, not
just accepted as a field. (a) custom `highlighter` **transforms** the composed text (e.g. `upper()`
— asserted via `get_highlight()`/viewdata); (b) custom `validator` **validates** the submitted text
(gates accept→`on_text_entered` / reject→lock). Mechanism: `userInputModel:highlight()` calls
`ev.highlighter(text)` on every `text_change` and memoizes for the view — so a red row sets a
transforming highlighter, types, and asserts the queried highlight reflects it.

**Meta-rule — no silent test retirement → AC-43 (owner ruling).** Tests are never retired silently
unless replaced by a green equivalent. Lifecycle: `#deprecated` (now) → red → `pending()`/skipped
(busted has no xfail) → **delete only when equivalent new tests are green**. Governs the whole
M4→M8 suite evolution; AC-39 is its first instance.
