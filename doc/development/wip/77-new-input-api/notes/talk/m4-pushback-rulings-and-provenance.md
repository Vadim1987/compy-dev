## Provenance finding: the flip happened inside the first design pass

Commit `207bb01` (2026-06-03, first committed design corpus, LLM-assisted) contains **both models
simultaneously, contradicting each other**:

- `notes/solution_sketch.md` §4 (the architect's first principle, upstream note): **four-level
  chain** — `framework_handlers[combo]` → `compy.handlers[combo]` → `compy.on_key_pressed`
  (**default: noop + log**) → `UserInputController:keypressed` (**universal sink, always last**);
  truthy return = consumed/stop ("DOM `preventDefault()` equivalent"); *"the default (sink always
  runs) is correct for the majority of keys and projects."* Plus an implementation aside:
  *"Invocation of `UserInputController:keypressed` **could also be** the default value of
  `compy.on_key_pressed` rather than a hardcoded final step."*
- `design.md` §4 (derived doc, **same commit**): **three-level** — *"`compy.input.on_key_pressed`
  has no separate tier below it — its default value **is** the sink. A project that overrides it
  **replaces the default entirely**."*

So the semantics were neither *forgotten later* nor *platform-forced*: they were **mutated in
derivation** — the sketch's "could also be" implementation shortcut was promoted into the contract
by the derived doc, changing observable behaviour (the two formulations are equivalent **only**
while no project overrides the callback). `spec.md` §3 inherited the mutated version; the sketch
kept the original; no pass ever diffed the two. The architect green-lighted the stack top-down and
the contradiction sat *between two files of one commit* from day one. The M4 implementor then
faithfully built the mutated (canonical-by-position) version.

**Failure mode named:** multi-document LLM generation does not guarantee cross-document semantic
consistency; "supposedly coherent" (the commit message's own hedge) was never verified
claim-by-claim. Guardrail implication → derived docs need a claims-diff against their upstream
(see pushback artifact, Step 3).

## Platform-compatibility check (architect's Q: forgotten vs incompatible; is the platform the confuser?)

- **LÖVE itself is simple and consistent:** `love.handlers.*` gateway → mutable `love.*` slots.
  Nothing in it forces replace-semantics; the chain model is fully implementable.
- **The complexity is incumbent-codebase mechanism, not platform:** sandboxed `userlove`,
  `save_user_handlers`, slot-swapping-as-routing, console-as-permanent-baseline, `app_state`
  branching, `{M,C,V}` handles. Doc A already rules all of this **MECHANISM — non-binding**.
  The architect's "routing table below fixed slots" model is realizable (M4's
  `Controller._keyboard_route` is already a one-entry routing table; the slot-swap beside it is
  the incumbent mechanism, free to change).
- **The one real behavioural tradeoff** hiding behind D-9's lifecycle-split: under a pure chain,
  a legacy project's native handler receives keys **while the widget is shown** (typing into an
  overlay prompt would also move the pong paddle) unless something stops them. D-9's
  "reproduce today's gated behaviour with zero example changes" is what forced the split — a
  **BC requirement, not a platform constraint**. Reconciliation consistent with the architect's
  own T8 suggestion: express the legacy accommodation as an **auto-provisioned chain participant**
  (a default project-handler that returns truthy while the widget is shown), not as a routing
  rule. Chain stays the universal principle; D-9 becomes one handler policy inside it.

## Architect rulings (2026-07-05, chat; to be folded into the re-derived design)

1. **Dispatch semantics — RULED: the chain.** combos → handlers → userinput sink, sink
   **internally** noop-with-warn when hidden; truthy = stop-propagation. Ratified as first
   principle *"on the premise it does not contradict the platform architecture fundamentally"*
   (provenance + platform check above: it does not). Supersedes `design.md` §4 / `spec.md` §3
   replace-semantics; restores `solution_sketch.md` §4.
2. **Q2 as posed was rejected** ("too much spec jargon, too little first principles"). The ruling
   given instead is a **design meta-rule**: *any consolidated/universal/transparent/predictable
   behaviour wins over ad-hoc specific surprising conditions; any 'special' scenario demotable to
   a variation of a common principle must be demoted.* Applied to D-9: the lifecycle-split must be
   re-expressed as a chain participant (see above), not as a special routing mode.
3. **`project_open` — RULED: PIC simply not connected outside `'running'`** ("less special-casing —
   surprised it even needs discussion"). Requires a `spec.md` §6 design-change (occupancy clause).
   One deferred consequence to settle during re-derivation, with a quick platform check: whether
   any example relies on project handlers staying live after a non-blocking run returns
   (`sine`/`life`-class; flagged by M4 outcome for M5a commissioning).
4. **`keyreleased` — RULED: just an event type; unify processing.** Lifts the 2026-07-02
   descope-with-note ruling; release joins the same chain shape. (The original descope's *why* was
   never recorded — that provenance failure is itself a lesson: rulings carry a recorded why or
   they get re-litigated.)
5. **Vocabulary — RULED: internal jargon acceptable iff it serves the ratified model.** "sink" as
   shorthand for *last element of the processing chain* — fine; "sink" as a first-class routing
   decision — rejected. "occupy" as shorthand for *currently active route, switched by mode* —
   fine; slot-reconfiguration *as the routing mechanism* (instead of a routing table below fixed
   slots) — suspicious, mechanism-level, non-binding, candidate to replace. Glossary becomes
   binding; implementors do not mint architectural nouns outside it.
