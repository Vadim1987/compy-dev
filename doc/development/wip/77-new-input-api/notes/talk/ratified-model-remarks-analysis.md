## Cluster A — the project-facing API surface (R1, R2, R3)

**R1 — what is `on_text_entered`? (suspected: submit-time callback)**
Finding: in the old corpus it is the **per-character textinput-channel callback** —
`compy.input.on_text_entered(text, keys_pressed)`, "default value is the textinput sink"
(`spec.md` §3, `spec/M5.md`). It is **not** the submit notification; that is FR-5, served by the
framework Enter handler + the `before_submit → submit → after_submit` chain (`solution_sketch.md`
§5). The architect's own reading ("fired when text is assembled and submitted by Enter") is the
opposite semantic — **the name is a proven trap; it just trapped its author.** There is also a
parked suite `pending` on exactly this ("per-char vs per-block", m5a).
**Proposed:** rename the per-char callback so it cannot read as submit — e.g. `on_text_input`
(mirrors `love.textinput`, the event it rides). Submit stays a distinctly-named surface (the
submit chain / `on_submit`). Decision: naming ruling at this gate; semantics are not in question.

**R2 — do `textinput`/`keyreleased` get `on_{event}` analogues?**
Finding: yes — that is ruling 4's content ("just an event type; unify"): every keyboard/text event
runs the same chain; tier 3 is the per-event generic callback. Old corpus defined only two
channels (`on_key_pressed`, `on_text_entered`); the release callback was the M4↔M5 cross-reference
gap (doc A §7.4) — ruling 4 closes it with a symmetric callback.
**Proposed:** the trio `on_key_pressed(k, keys_pressed, isrepeat)` /
`on_text_input(text, keys_pressed)` / `on_key_released(k, keys_pressed)`. One open sub-point:
does the **combo tier** (tier 2) apply to releases? Recommendation: press-only by default
(release combo dispatch would double-fire actions; the E9 fresh-only ruling
`handlers[isrepeat][combo]` already keys the combo tier to presses). Chain *shape* stays uniform;
a tier that has no participants simply falls through — consistent with the collapse rule.

**R3 — mutable handlers on `compy.input` blur the API boundary; better `compy.input.handlers`?**
Finding: combos already live at `compy.input.handlers[combo]` (metatable-normalised — old
`spec.md` §3, kept-valid round-2 material); the `on_*` callbacks sit as sibling fields directly on
`compy.input`, mixed with immutable API (`show`/`hide`/…). The concern is real.
**Options:**
1. **Group everything mutable under one table:** `compy.input.handlers` = the single mutable
   surface — `handlers['ctrl+s']` (combos) + reserved callback keys, or substructure
   (`handlers.combos[…]`, `handlers.on_key_pressed`). Cleanest boundary; costs either reserved-key
   mixing inside a normalised combo table or the loss of the flat `handlers['ctrl+s'] = fn`
   ergonomics.
2. **Keep shape, enforce the boundary mechanically:** `compy.input.handlers[combo]` + `on_*`
   fields stay as-is, but `compy.input` is `table.protect`-ed except the whitelisted mutable set —
   assigning anything else errors loudly. Boundary enforced, not lexical; zero ergonomic cost;
   the mutable set is exactly documented.
3. Registration functions (`compy.input.set_handler(combo, fn)`) — most rigid; least Lua-idiomatic,
   breaks the assignment idiom students know from `love.keypressed = fn`.
**Proposed:** rule at model level only "one clearly-bounded, documented mutable set; the rest of
`compy.input` is immutable and protected"; pick 1-vs-2 as a Stage-2 spec decision (recommendation:
option 2 — the boundary the human wants, without resyntaxing the round-2-reviewed combo surface).

## Cluster B — platform fact (R4)

**R4 — textinput arriving while a modifier is held (`ctrl+v`)?**
Finding (doc A §2 / `assessment/keypressed-vs-textinput.md`): `love.textinput` fires **only** for
OS-processed character-producing input. Ctrl+letter chords produce **no** textinput event — SDL
suppresses text for Ctrl combos; `ctrl+v` arrives solely as `keypressed('v')` with ctrl in
`keys_pressed`. So interception happens exactly where assumed: tier 2 (`handlers['ctrl+v']`) or
tier 3 (`on_key_pressed`) on the **keypressed** chain; there is no competing textinput to race.
The widget's own paste is likewise a keypressed-channel action (sink Ctrl+V), per compy's
channel convention.
Two spec-level caveats to record (not model problems): Shift+letter *does* produce textinput
(uppercase — Shift is not a shortcut modifier); AltGr layouts emit textinput with (folded) alt
held — a combo like `'alt+…'` could shadow real text entry on such layouts; the combo-fold table
folding `ralt` into `alt` predates #77 and stays as-is, flagged in the spec.
**Proposed:** no model change; add both caveats to the Stage-2 spec's combo section.

## Cluster C — run lifecycle (R5, R6)

**R5 — sapper/pen-and-paper: is playable-after-return a mistake? (+ drawdebug deleted)**
Findings:
- **Inspect is already clean:** `ConsoleController:suspend()` (`consoleController.lua:809-826`)
  calls `set_default_handlers`, which reinstalls **all** slots including pointer — sapper is *not*
  clickable during inspect. The census's asymmetry exists only in `'project_open'`.
- **Pen-and-paper is a designed mode**, not an accident: `doc/development/drawing_system.md`
  names sapper its canonical example ("all drawing happens in click handlers… board drawn once at
  setup, partially updated per user action"). So sapper-playable-in-`project_open` is today's
  intended shape of that mode — but the *state name* contradicts it (an interactive game in a
  state called "not running"), which is the wrinkle the remark caught.
- drawdebug deletion removes the `singleclick`-in-`project_open` dependency; balloons/clock etc.
  hook update/draw and stay `'running'` — unaffected.
**The actual design question:** what ends a run? Options:
  - **(A)** status quo: `update`/`draw` presence decides; keyboard/text disconnect at
    `project_open`, pointer stays — asymmetric (offends the predictability rule).
  - **(B)** a project is `'running'` while it has **any** live interactive surface (any handler
    registered, pointer included) — sapper stays running; symmetric disconnect of *all* channels
    at run end; costs the type-REPL-commands-over-a-playable-board ability (Ctrl+S first).
  - **(C)** interactivity must hold the run open **explicitly** (pen-and-paper projects add a
    trivial `love.update` or a future `compy.hold()`) — `project_open` becomes truly inert,
    everything disconnects; costs a one-line migration to sapper.
**Proposed model rule (either way):** **one boundary for all event types** — when the run ends,
the project route disconnects wholly; no per-channel asymmetry. A/B/C picks *where* the boundary
sits — the human's product call, requested at this gate.

**R6 — balloons not responding to stop shortcuts?**
Finding: statically unsupported in current code. Global shortcuts run at the **gateway**, before
any route/widget dispatch (`controller.lua:688-793`); balloons hooks update+draw so it stays
`'running'`, where Ctrl+S → `stop_project_run` and Ctrl+Q → `quit_project` unconditionally fire.
Balloons is the "widget-permanently-shown" class (persistent `input_text` prompt + polling) —
pre-M4 that diverted all *route* keys to the widget, but never the gateway shortcuts above.
If the memory is real it was either a since-fixed historical state or the separately-tracked
balloons end-of-game overlay redraw bug (`internals/user_input.md:227` side-thread).
**Proposed:** add balloons to the M0 manual check list (with sine/sapper/life); no model impact.

## Cluster D — legacy natives / D-9 (R7, R8)

**R7 — "why not just wrap into the provisional `compy.input` hook and use the same chain? or
break the examples — we have the mandate."**
Clarification first: the proposal **is** the wrap-into-tier-3 — "auto-provisioned chain
participant" = the native wrapped and assigned as the `on_key_pressed` participant, dispatched by
the ordinary chain. The *only* extra logic was the shown→suppress-native gating inside that
wrapper, whose sole purpose was preserving today's turtle/maze behaviour (widget shown ⇒ natives
silent) — i.e. the D-9 zero-example-changes BC requirement.
The mandate check the remark asks for: SR1's break is "only TEXT FIELDS break; native keyboard
handling must keep working". The two exposed examples (turtle, maze — the only ones with natives
**and** widget solicitation) are text-field users, hence **inside** the break mandate; pure-native
projects (pong, life, paint, clock, keyboard) never show the widget and are unaffected by
de-gating.
**Proposed — adopt the remark's direction:** drop the gating entirely. The accommodation becomes
*pure wrap*: native handlers auto-provision as plain tier-3 participants, no widget-awareness, no
custom logic — fully inside the chain, predictability rule intact. Migrate **turtle and maze** to
the new API in the legacy-removal slice (they must migrate by M8 anyway — both poll). Note the
new-API semantic this cements is FR-6's own letter: project handlers see every event, widget shown
or not; a project wanting widget-exclusive typing checks widget state in its handler (or simply
has no reason to care, post-migration).

**R8 — what is the "yield form"?**
Terminology mishap, mine: "yield" meant *return falsey so the event falls through to the next
tier* — plain DOM-style return-value bubbling, nothing coroutine-shaped. The truthy-vs-yield
question was only about what the legacy wrapper does *while the widget is shown* (call the widget
itself + return truthy, vs. return nil and let the terminal sink do it). **Under R7's pure-wrap
resolution the entire question dissolves** — there is no shown-gating in the wrapper at all. The
"returns truthy while shown" phrasing in the rulings note was session-32 chat-materialization
wording (mine), not the architect's verbatim — nothing to preserve.

## Cluster E — smaller confirmations (R9, R10, R11)

**R9 — `before_submit` veto by return value, "maybe in the future".**
Recorded as a future extension: submit chain stays call-order-only now; the design must not
preclude a veto return later. Note the validator (FR-1) already covers the principal
"block bad input at submit" case.

**R10 — leave the path open for pointer unification, if low-cost.**
It is low-cost: the chain is defined per-event-type generically (tier tables keyed by event), so
pointer events can adopt the same shape later without model change. R5's one-boundary rule
already pulls pointer into the *lifecycle* model now; dispatch-shape adoption stays a future
slice. Proposed: one line in the model stating the shape is event-agnostic by construction.

**R11 — can `inspect` be served by the same fundamental model?**
Yes — verified against current implementation: `suspend()` swaps **all** slots to console
defaults and the REPL evaluates in the project env. In model vocabulary that is exactly:
**`inspect` is a mode whose active route is the console** (bound over the project environment);
the project route is disconnected (ruling 3's own shape); the project widget is route-owned and
its route is inactive, so it is not honoured — natural consequence, zero special rules.
**Proposed:** state inspect in the model as a mode→route line (no longer deferred at the routing
level); what stays deferred is only the future question of inspect adopting the migrated
console surface.

## Round-2 rulings (human, 2026-07-05 chat) — folded into `ratified-model.md`

- **R1 — RULED, and it inverts the corpus reading:** `on_text_entered` is **widget vocabulary**,
  not chain vocabulary — the important syntactic sugar is *"show a soliciting input configured
  with callbacks (validator, highlighter, on_text_entered)"*; it fires when text is assembled and
  submitted. Verbatim framing: *"strictly speaking, it's not about routing **into** the widget —
  it's about routing **out of** it."* This reading comes from an early design note that may not
  even be in the current corpus; it is a **soft target** ("not a hard ruling… if we find a way to
  do it, it will both prove our design and be a nice achievement"). Name preserved on the widget
  surface; the per-char chain callback takes the distinct name (`on_text_input`). Model gains a
  "widget outputs" element (submit / limit / validator / highlighter — outbound callbacks), and
  the simple-use path: `show{…callbacks…}` with zero chain knowledge (NFR-4).
- **R2 — RULED broader than proposed:** the combo tier is a **uniform mechanism on every
  channel** (press combos the obvious case; release/text combos "conceptually possible and
  sometimes useful while less likely"). Projects decide what to use. My press-only default is
  overruled as a *mechanism restriction*; per-channel tables, all channels served.
- **R3 — RULED = option 2:** `on_*` keys resettable, `.handlers` a writable table, anything else
  callable and not overridable (protected). Rationale: *"stakeholders don't consider syntax
  set-in-stone — they'd need to see the implementation to feel if it fits; most dev-friendly
  format wins; naming tweakable later, simpler when implemented."*
- **R4 — RULED: mark it in code whatever we decide.** Disposition: textinput callbacks DO carry
  `keys_pressed` (uniformity, cheap — same proxy); the channel caveats (Ctrl-chords emit no
  textinput; Shift/AltGr do) get in-code comments at the dispatch site.
- **R5 — RULED = status quo as natural design constraint** (no genuine product ruling available,
  so status quo wins by default): `update`/`draw` presence keeps `'running'`; project route
  (kbd/text) connected only while `'running'`; pointer natives slot-hooked until stop. The
  asymmetry is recorded as characterized status quo, unification future work. Options B/C and the
  one-boundary-for-all-events rule are NOT adopted.
- **R6 — human allows he may have just forgotten the shortcuts while testing balloons.** Manual
  test combos (M0 image): run `balloons`, then **Ctrl+S** = stop run (back to console, project
  stays open); **Ctrl+Q** = quit project; also available: Ctrl+Pause = BREAK/inspect,
  Ctrl+Escape (release) = quit app. Expected: both Ctrl+S and Ctrl+Q respond immediately even
  with the balloons prompt shown. Not critical.
- **R99 (new) — cursor management API accounted for?** Yes: FR-8/9/10 → **M7 slice**
  (`spec/M7.md`): `compy.input.get_cursor/set_cursor/set_text/configure/clear` under D-8's 2D
  `(line,col)` cursor contract; doc A §6.6 records today's cursor mess (four reset impls,
  two-layer split) as exactly what M7 replaces. Survives in the Stage-3 re-cut as the separable
  M7 slice. Under R1's framing these are **widget-surface** API, consistent.
- **R7 — RULED (round 3): pure wrap + break-and-fix.** Verbatim reasoning: in the stakeholder
  input *"we're not only mandated but **expected** to break-and-fix examples that are affected;
  doing otherwise would increase effort and ceremony and would actually be a resources burn."*
  Natives auto-provision as plain tier-3 participants, no widget-gating; turtle + maze migrate.
  R8 (yield-vs-truthy) is thereby moot; the revalidation doc §3 carries a supersession fence.
  **Stage-3 note:** the behaviour change arrives with the dispatch-chain slice, so turtle/maze
  migration must ride that slice (or land immediately adjacent), not wait for M8 — else an
  interim window ships misbehaving examples.
- **R11 — RULED (round 3): correct resolution, no doubts.** Inspect folded into the model as
  the mode→route line (console route over project env; project route disconnected; widget
  unhonoured because its owning route is inactive).

## Round-4 remarks (human, 2026-07-05 chat, delivered WITH ratification) — folded

The human ratified the model and simultaneously injected three remarks framed as "cosmetic /
formal clarifications aimed to prevent future misinterpretation (like the one which caused the
arch drift)". Checked; none surfaces a misunderstanding; all three incorporated (no contest).

- **R12 — sink description: "returns limit signal" → widget outputs.** Incorporated, and it is
  a correctness fix, not cosmetics: "returns limit signal" leaked today's implementation (UIC
  `keypressed` returning `ret` up the call stack) into the model AND collided with the chain
  return convention — the sink is terminal, so its return value can have no chain meaning.
  Model now says: boundary/submit conditions surface through the widget's own outputs
  (`on_limit_reached`, `on_text_entered`…), never through chain return values. Today's console
  limit→history behaviour becomes the console route wiring `on_limit_reached` → history nav —
  a proof case for the widget-outputs surface (R1), not an exception.
- **R13 — consuming ≠ removing.** Incorporated. "Overriding tier 3 NEVER removes tier 4" was
  ambiguous in exactly the drift-causing direction (readable as "tier 4 always runs" — the
  sketch-aside that mutated into replace-semantics). Precise statement now in the diagram:
  **configuration is permanent, flow is per-event** — truthy at any tier stops the event
  travelling further (sink included) *for that event*; no override ever removes a lower tier
  from configuration; replace-semantics exists nowhere.
- **R14 — combo tiers keyed event-type-first.** Incorporated as a binding structure rule:
  `handlers.keypressed[combo]` / `handlers.keyreleased[combo]` / `handlers.textinput[combo]`
  (and `framework_handlers.*` likewise). Was presumed ("per-channel tables") but never pinned;
  the old spec's flat `handlers[combo]` is precisely the shape a derivation would collapse back
  into — now explicitly forbidden as a known drift attractor. Naming per R3 stays tweakable;
  the structure does not.

## Gate 2 — round-1 remarks (2026-07-06)

Human reviewed the Gate-2 surface (design.md §8+§9, spec.md §11) and raised three questions
plus one written `>> REVIEW` remark before greenlighting. Ledger continues here (this note is
now the running remarks record for all E29 gates).

- **G2-R1 — `oneshot` precision (written remark in design.md §8).** Incorporated. The gloss
  "oneshot simply calls hide on the widget itself after submission" is right at the behavioural
  level with two mechanical nuances: (1) in current code the flag *also* gates submit ownership
  — `oneshot=false` (console/editor) makes the widget's `submit()` a deliberate no-op so the
  controller above handles Enter; (2) the self-dismiss is `push('userinput')`, not a `hide()`
  call (no `hide()` exists pre-M2). Claims-diff row 14 rewritten to state both jobs and where
  each goes: submit ownership → per-route `framework_handlers.keypressed['return']`; self-close
  → the unconditional deactivate step of the submit sequence (spec §5) — the `oneshot=true`
  behaviour kept, no longer flag-gated. Non-breaking, as the remark hoped. REVIEW marker
  removed from design.md.
- **G2-Q2 — callback teardown across project/route changes (chat question).** Already covered
  by spec §8 Stop (full reset of slots + `handlers.*` + every mutable field) and §10 edge case;
  made explicit as a named **teardown invariant** in spec §8: no callback, combo entry, or
  widget configuration survives its creating project; disconnected routes receive nothing;
  a widget whose owning route is inactive goes unhonoured (R11 inspect = the model case).
  Editor-as-singleton-user remains part of the console/editor migration follow-on; the
  invariant is what that migration must preserve.
- **G2-Q3 — framework Enter/Escape only-while-shown: status quo? (chat question).** Confirmed
  empirically from notes/enter_escape_routing.md: today, project running with no overlay ⇒
  Enter/Escape go straight to the project's own `love.keypressed` (no framework involvement
  beyond global shortcuts); overlay shown ⇒ the widget consumes them. The new tier-1
  engage-only-while-shown rule preserves exactly this. The one deliberate change is ruled:
  Escape now genuinely dismisses (known-limitation fix, sketch §5 / D-4). Ctrl+Escape quit
  stays a global shortcut on keyrelease, untouched.
- **G2-Q4 — continuous input sessions (balloons case).** Supported, via idiom rather than
  mode: deactivate-on-submit stays unconditional (a keep-open flag would be `oneshot` reborn,
  polarity flipped); a project re-activates from `after_submit` with `compy.input.show{prompt=…}`
  — fresh activation starts empty (clear for free), callbacks/handlers persist (only stop
  resets), re-show runs before the frame draws (no visible gap). Pinned in spec §5 + §11 row 12.
  Balloons census: today it re-shows via `input_text()` on every hint write and polls the
  reftable each `update` — under the new API that whole loop becomes `show` once +
  `configure{prompt=…}` + `on_text_entered`/`after_submit`. If the human prefers a keep-open
  config key instead, that is a D-a-adjacent ruling — recommendation stands against it.
- **G2-Q5 — `push('userinput')` purpose + disposition.** Census: oneshot submit fills the
  reftable synchronously, then pushes the custom `'userinput'` event; `handlers.userinput`
  nulls `love.state.user_input` on the NEXT event dispatch — i.e. deferred dismissal, so the
  overlay never tears itself down inside its own `keypressed` call stack (plus the polling
  loop gets one frame with reftable filled + overlay still up). Disposition: **dissolved** —
  notify job → `on_text_entered` (polling removed with legacy API), deferral job → the
  deactivate step of the submit sequence; sync-vs-deferred realization is mechanism,
  non-binding (ruling 5). Contract fixes only observable order: `on_text_entered` sees the
  session active, `after_submit` sees it deactivated (or re-activated by the hook itself).
  Pinned in spec §5 mechanism note.
- **G2-Q6 — always-ephemeral project input vs future console/editor persistence (least
  astonishment).** Resolved by scoping, not redesign. Assessment: the contradiction lives in
  a mis-attribution the docs permitted — deactivate-on-submit could be read as *widget*
  nature, when it is **project-route tier-1 policy**. The uniform binding part of submit is
  its shape (widget never owns submit; the owning route's framework handler does, wrapped in
  the D-4 hook chain — the per-controller split enter_escape_routing.md already names:
  console evaluates-and-stays, editor flushes-and-stays, project delivers-and-closes). At
  migration, console/editor mint their own middle steps: **true persistence** — the widget
  session simply continues; the re-show idiom is the project-route minority path, never the
  migration template. Least astonishment holds where users experience it: within a context
  submit is invariant; across contexts Enter has always meant different things — now
  route-owned and explicit instead of flag-encoded (oneshot). A persistent project-route
  option remains an additive reserved extension (R9-adjacent). This was drift-shaped
  ambiguity worth fixing at the gate: design.md §3 gained the scoping block, spec §5 a
  binding scope note, D-a amended, spec §11 row 13 added.
- **G2-Q7 — what are set_cursor/highlighter for if project input is ephemeral?** Ephemeral ≠
  momentary: a session spans the whole composition (minutes for input_code-style entry).
  Consumers: live highlighter while composing (flagship: input_code); validator-reject
  error-jump (today's evaluate-fail path already moves the cursor to the error line/col);
  on_limit_reached → set_text/set_cursor flows (history navigation — console proof case,
  available to projects); draft restore (show{text,cursor}); console/editor migration the
  heaviest future consumer (editor Escape load-selection = set_text). "Only for wrong
  inputs" undersells — error-jump is one consumer among several. Pinned in design.md §3
  (cursor bullet) + spec §6 consumers note.
