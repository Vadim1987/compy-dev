## Attestation — the proto-method → SDLC lineage (a design confirmation)

- **Human:** the canonical SDLC method was **born as a generalization of this very
  proto-method** (feature #77's ad-hoc design process) **plus one more problem-solving session
  inspired by it**.
- **Therefore:** the fact that this original proto-method **fits cleanly back into the SDLC
  shape** (E4 reshaped it with no residual structural deviation — see
  [`../../design/agents/process.md`](../../design/agents/process.md) §3) is **confirmation of
  SDLC's design success** — a generalization that round-trips onto its own progenitors is a good
  generalization.
- **Why it matters / how to apply:** treat this E4 reshape as **evidence for the SDLC design**,
  not just a topic cleanup. If a *future* topic's bespoke process resists the SDLC shape, that
  resistance is a **signal worth examining** (either a real gap in SDLC or a genuinely different
  control loop) — the same lens that produced deviations #1/#2 here and then dissolved them.

## Insight — layered pipelines (design feeds sprints) is fresh

- The **two-chained-lifecycle** structure — a `design/` SDLC whose **outcome (roadmap +
  per-milestone specs) becomes the input** of N downstream `sprintNN/` SDLC instances — is a
  **fresh insight** from this topic, **not** something inherited from the proto-method or baked
  into canonical SDLC.
- It nonetheless **closely follows real-life SDLC/agile practice** (a planning/design phase
  feeding iterative delivery sprints), which is a point in its favour.
- **How to apply:** the clean handoff edge is `design.outcome → sprint.requirements`
  (see topic [`../../README.md`](../../README.md)). This layering is a **candidate
  generalization** back into the library — *can SDLC instances chain, one's `outcome` being the
  next's `requirements`?* — worth weighing if a second multi-phase topic appears. Related:
  [[session-decisions]] (the two-lifecycle architecture decision).
