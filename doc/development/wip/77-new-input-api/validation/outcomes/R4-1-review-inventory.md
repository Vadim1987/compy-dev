## Notable findings (beyond the tally)

1. **`projectInputController.lua:197` is the redesign's own headline example of a REVIEW note it discusses at length — and still does not resolve.** Delta-spec §2 quotes it verbatim under "Considered alternative (deferred, not adopted)" and gives a concrete engineering reason for declining it. It would be a mistake to tag this resolved-by-redesign just because it's discussed; the actual dispatch code stays staged-`if` based, not OR-chained. Flagged still-open, cross-referenced.
2. **`projectInputController.lua:47`'s host function (`run_hook`) is deleted, but its concern isn't.** `run_hook` is in §2's explicit deletion list, yet its replacement `run_callback` (§3) is specified as "today's shape, unchanged" — same if/else pattern, same underlying question. A naive "grep for the old line number, cross it off" sweep would silently drop a still-valid concern along with dead code.
3. **`userInputController.lua:391`'s suspicion checks out as a genuine, independent dead-code finding:** grepping all of `src/` turns up no live setter for the `result` config key (the "legacy poll reftable") — only defensive nils in teardown/test-fixture code. Neither delta doc touches it; it's real tech debt outside R4's scope, worth flagging to Phase C on its own.
4. **Three separate remarks converge on the same "singleton/widget identity used as a shown/hidden check" question** (`userInputController.lua:433`, `userInputView.lua:297`, `main.lua:360`), but only `main.lua:360` is explicitly named and answered in the delta-design text. The other two ask essentially the same question from different code sites and are *not* resolved by the same text — a risk that a less careful pass would over-generalize the `main.lua:360` resolution onto all three.
